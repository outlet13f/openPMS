예산마다 잡는 실수가 다릅니다.

- **시간 예산**은 느린 기계에서도 넘지 않게 잰 값의 약 5배로 잡았습니다. 큰 회귀만 잡는 선입니다.
- **SQL 수**는 기계와 상관없이 같습니다. 그래서 잰 값에 3만 더해 잡았습니다.
  - 20건과 100건의 SQL 수가 같다는 것은 작업 수만큼 쿼리가 늘지 않는다(N+1 없음)는 뜻입니다.
- **응답 크기**는 응답에 필드를 마구 붙이는 실수를 잡습니다.

같은 클래스에는 고정 검사 테스트도 있습니다(`noRequestKeepsItsCarrierThreadWhileWaiting`).

- 가상 스레드 20개가 위 요청을 동시에 보내는 동안 JFR의 `jdk.VirtualThreadPinned`를 받습니다.
- 우리 코드에서 난 고정이 하나라도 있으면 실패합니다(아래 BUG-012 참고).
- 고치기 전 코드로 돌리면 실패하는 것을 확인했습니다.

`NoPinningTest`는 `src/main/java`에 `synchronized`가 없는지 봅니다.

**보드**
- 열마다 카드를 50장만 먼저 그리고 나머지는 **100장 더 보기**로 그립니다.
- 열 머리의 개수는 전체 장수를 보여 줍니다.
- 열 자체에 카드를 놓으면 보이는 마지막 자리에 들어갑니다(숨은 카드 뒤가 아님).

**압축과 캐시**
- `server.compression`이 JSON·HTML·CSS·JS·SVG·CSV에 적용됩니다(2 KB 이상).
- 이름에 해시가 붙은 `/assets/*`는 `Cache-Control: max-age=31536000, public, immutable`입니다.
- `index.html`과 화면 주소는 `no-cache`라 새 버전이 다음 접속에 바로 보입니다.

**가상 스레드 고정** (BUG-012)
- `Snapshot`의 지연 로더(`synchronized`)와 `shares`(`ConcurrentHashMap.computeIfAbsent`) 안에서 DB를 기다리면, Java 21에서는 가상 스레드가 캐리어 스레드를 놓지 않았습니다.
- CPU 수만큼 있는 캐리어가 모두 묶이자 커넥션을 쥔 요청도 실행되지 못했습니다.
- `ReentrantLock`으로 바꾸고, 조회를 맵 밖에서 하도록 고쳤습니다.
- 로그인은 비밀번호 해시를 확인하는 동안(약 0.1초) 커넥션을 잡지 않습니다.

**권장 사양** (위 실측에서 나온 값)
- **동시에 화면을 누르는 사람 100명까지** (가입자로는 보통 수백 명)
  - 앱 컨테이너 CPU 2개·메모리 1 GB, DB 컨테이너 CPU 2개·메모리 1 GB면 충분합니다. 위 측정에서 앱은 1.2코어·430 MiB, DB는 0.4코어·140 MiB를 넘지 않았습니다.
  - 서버 한 대라면 **4 vCPU · 4 GB 메모리**를 권장합니다. OS와 여유분을 더한 값입니다.
  - 50명 이하라면 2 vCPU · 2 GB로도 됩니다. 50명일 때 앱 0.6코어·410 MiB, DB 0.2코어·130 MiB였습니다.
- **한계**
  - CPU 2개 앱의 한계는 쉬지 않는 요청 기준 화면 약 90번/초(요청 약 160개/초)입니다.
  - 사람이 화면 사이에 2초 쉰다고 보면 동시 사용자 약 180명에 해당합니다. 이 수치는 위 표의 처리량에서 계산한 값이며, 180명은 직접 재지 않았습니다.
  - 그보다 많으면 앱 컨테이너에 CPU를 더 주세요.
- **디스크**: 측정 DB(작업 1,000건)는 19 MB입니다. 첨부 파일과 백업(종류마다 5개)이 대부분을 차지합니다.

**측정하지 않은 것**

- 작업 1만 건 이상
- 첨부 파일 업로드·내보내기(Excel·PDF)의 부하
- 알림 메일 발송량
- 여러 앱 인스턴스
- 빌드된 화면에서의 포털 홈·내 승인함(2.5, 개발 서버에서만 잼)
