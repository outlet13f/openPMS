## 1. 개요

### 1.1 목적

openPMS의 웹 화면(SPA)과 API 서버 사이의 REST 인터페이스, 사내 시스템이 API 토큰으로 부르는 같은 REST 인터페이스, 그리고 openPMS가 호출하는 외부 시스템(SMTP, OpenID Connect 공급자, 웹훅 수신 시스템) 인터페이스를 정의합니다.

### 1.2 작성 기준

- `backend/src/main/java/com/openpms/` 아래 모든 `@RestController`를 읽고, 매핑 애너테이션이 있는 경로를 빠짐없이 적었습니다. 코드에 없는 경로는 적지 않았습니다.
- 경로는 코드에 적힌 그대로입니다. 모든 컨트롤러 경로가 `/api/v1`로 시작합니다.

### 2.2 인증

| 항목 | 내용 |
| --- | --- |
| 세션 쿠키 | `OPENPMS_SESSION`. HttpOnly, SameSite=Lax, Secure(운영 기본). 로그인(`IF-AUTH-001`), 초대 수락(`IF-AUTH-008`), (v2.2) 임시 비밀번호의 새 비밀번호 정하기(`IF-AUTH-009`), SSO 콜백으로 발급 |
| 세션 저장 | 서버 DB(Spring Session JDBC). 유지 시간 `OPENPMS_SESSION_TIMEOUT`(기본 8h) |
| CSRF | 서버가 `XSRF-TOKEN` 쿠키를 내려 주고, 클라이언트는 GET·HEAD 이외의 모든 요청에 `X-XSRF-TOKEN: <쿠키 값>` 헤더를 붙입니다. 없거나 틀리면 403 |
| 인증 불필요 경로 | `/api/v1/auth/login`, `/api/v1/auth/password-reset`, `/api/v1/auth/password-reset/confirm`, `/api/v1/auth/password-change`(v2.2), `/api/v1/auth/password-policy`, `/api/v1/auth/invitations/**`, `/api/v1/auth/sso-providers`, `/api/v1/auth/oidc/**`, `/api/v1/openapi.json`(v1.4) |
| 인증 불필요 경로(v2.7) | `POST /api/v1/hooks/cicd/{hookKey}`(`IF-CICD-007`, CI/CD 웹훅). `SecurityConfig`가 이 경로의 POST만 `permitAll`로 열고 CSRF 검사에서 뺍니다. 세션을 만들지 않고, 대신 도구의 서명을 검사합니다(3.21). 같은 경로의 GET은 401, 더 깊은 경로의 POST는 403 |
| 그 밖 | `/api/**`는 로그인(세션) 또는 API 토큰 필요. 세션이 없거나 사용자 상태가 `active`가 아니면 401 |
| 요청 예 | `PATCH /api/v1/work-packages/42`<br/>`Cookie: OPENPMS_SESSION=<세션 ID>; XSRF-TOKEN=<토큰>`<br/>`X-XSRF-TOKEN: <토큰>` |

API 토큰 인증(v1.4, `auth/ApiTokenFilter`·`ApiTokens`)

사내 시스템이 openPMS API를 부를 때 씁니다. 토큰은 사람마다 계정 설정에서 만듭니다(`IF-TOK-002`).

| 항목 | 내용 |
| --- | --- |
| 헤더 | `Authorization: Bearer opms_<무작위 43자>`. 쿠키를 보내지 않습니다 |
| 처리 | `ApiTokenFilter`가 CSRF 필터보다 먼저 `/api/` 요청의 Bearer 헤더를 봅니다. 맞는 토큰이면 그 요청 하나만 토큰 주인으로 인증합니다(세션을 만들지 않음). Bearer 요청에는 CSRF 검사를 하지 않습니다(쿠키가 없어 막을 대상이 없음) |
| 권한 | 토큰 주인의 권한 그대로(관리자가 만든 토큰은 관리자 권한). 프로젝트·작업 권한 검사는 세션 요청과 같음 |
| 범위 `read` | GET·HEAD·OPTIONS와 읽기용 POST 세 개(`/api/v1/work-packages/query`, `/api/v1/work-packages/export`, `/api/v1/work-packages/export/count`)만. 그 밖은 403 "읽기 전용 토큰입니다." |
| 범위 `write` | 주인이 화면에서 할 수 있는 모든 요청(아래 막힌 경로 제외) |
| 막힌 경로 | (v2.3) 필터는 요청 경로를 Spring이 라우팅하는 것과 같게 디코딩한 뒤 비교하므로 `/api/v1/me/%61pi-tokens`처럼 글자를 퍼센트 인코딩해도 같은 경로로 보고 막음(BUG-015). `/api/v1/auth/**`(단 `/api/v1/auth/me`는 허용), `/api/v1/me/password*`, `/api/v1/me/api-tokens*`, `/api/v1/admin/api-tokens*`, 연동 설정 `/api/v1/admin/settings/api`·`/api/v1/admin/webhooks*`·`/api/v1/admin/webhook-deliveries*`(dfde416, 관리자의 토큰도), (v2.2) `/temporary-password`로 끝나는 경로(`IF-TPW-001`·`002`)와 `POST /api/v1/admin/users`의 `method: temporaryPassword`(필터가 아니라 컨트롤러가 거절. 퍼센트 인코딩한 경로로도 피할 수 없음), (v2.7) `/api/v1/admin/cicd/`, (v2.9·v3.0) `^/api/v1/projects/[^/]+/(cicd/(environments\|pipelines)\|releases)(/.*)?$`(환경 설정·빌드 기록 정리와 릴리스 검증·기록, GET 포함) → 403 "API 토큰으로는 로그인·비밀번호·토큰·연동 설정을 다룰 수 없습니다." |
| 401 | 형식이 틀림·없는 토큰·만료·폐기·주인이 활성 아님·로그인 실패 잠금 중 → "API 토큰이 올바르지 않거나 만료되었습니다.". 관리자가 토큰을 꺼 두면(`api.tokens_enabled=false`) → "API 토큰을 쓰지 않도록 설정되어 있습니다." |
| 요청 제한 | 토큰마다 분당 300회, 넘으면 429(2.10) |
| 저장 | DB에는 토큰의 SHA-256만 둡니다(`api_tokens.token_hash`). 원문은 만들 때 응답에 한 번만 나옵니다. `last_used_at`은 최대 1분에 한 번 기록 |
| 요청 예 | `GET /api/v1/work-packages/42`<br/>`Authorization: Bearer opms_<토큰>` |

버전 정책(v1.4, 도움말 · API 문서): 경로는 `/api/v1` 아래입니다. v1 안에서는 응답 필드를 더하기만 하고, 필드를 빼거나 뜻을 바꾸는 변경은 `/api/v2`로 냅니다. 연동은 모르는 필드를 무시하도록 만듭니다. 주요 경로의 요청·응답 모양은 `IF-TOK-008`(OpenAPI 3.1)에 있습니다.

### 2.5 오류 형식

RFC 9457 문제 상세(`application/problem+json`)입니다.

| 필드 | 타입 | 필수 | 내용 |
| --- | --- | --- | --- |
| `type` | string | 예 | 항상 `about:blank` |
| `title` | string | 예 | 화면에 보여 줄 한국어 제목 |
| `status` | number | 예 | HTTP 상태 코드 |
| `detail` | string | 아니요 | 추가 설명 |
| `errors` | `{field, message}[]` | 아니요 | 422 필드 오류. 일괄 처리 실패는 `field`가 `#번호` |
| `current` | object | 아니요 | 409 낙관적 잠금 충돌일 때 현재 작업 패키지(`WorkPackage`). (v2.2) `POST /auth/login`의 403·401에서는 `{code, changeToken?}`(임시 비밀번호) |

422 필드 오류 예

```json
{
  "type": "about:blank",
  "title": "입력값을 확인하세요.",
  "status": 422,
  "detail": "프로젝트 이름을 입력하세요.",
  "errors": [{ "field": "name", "message": "프로젝트 이름을 입력하세요." }]
}
```

409 충돌 예

```json
{
  "type": "about:blank",
  "title": "다른 사람이 먼저 수정했습니다.",
  "status": 409,
  "detail": "최신 내용을 불러온 뒤 다시 저장하세요.",
  "current": { "id": "…", "number": 42, "lockVersion": 7, "…": "…" }
}
```

임시 비밀번호로 로그인한 403 예(v2.2)

```json
{
  "type": "about:blank",
  "title": "새 비밀번호를 정해야 합니다.",
  "status": 403,
  "detail": "임시 비밀번호로는 바로 쓸 수 없습니다. 새 비밀번호를 정하세요.",
  "current": { "code": "password_change_required", "changeToken": "…" }
}
```

기한이 지난 임시 비밀번호는 401, 제목 "임시 비밀번호가 만료되었습니다.", 상세 "관리자에게 다시 발급을 요청하세요.", `current` `{ "code": "temporary_password_expired" }`입니다.

필드 오류의 `field` 값은 요청 필드 이름과 다를 수 있습니다(예: 요청 `statusId` → 오류 `status`, 요청 `parentNumber` → 오류 `parent`). 화면은 `errors[].field`로 입력란을 찾습니다.

### 2.6 페이지네이션

페이지를 나누는 경로와 방식은 경로마다 다릅니다.

| 경로 | 요청 | 응답 | 한도 |
| --- | --- | --- | --- |
| `GET /projects` | `page`(기본 1), `pageSize`(기본 20) 쿼리 파라미터 | `Page<Project>` = `{items, total, page, pageSize}` | pageSize 1~100 |
| `POST /work-packages/query` | 본문 `page`(기본 1), `pageSize`(기본 20) | `QueryResult` = `{rows, total, page, pageSize, relations, groups, sums}` | pageSize 1~1000 |

### 2.7 날짜·시간 형식

| 종류 | 형식 | 예 | 쓰는 곳 |
| --- | --- | --- | --- |
| 날짜 | ISO-8601 `YYYY-MM-DD` | `2026-10-10` | 시작일, 완료일, 버전 기간, 휴무일, 알림 일시 중지 |
| 순간 | ISO-8601 날짜·시각, 오프셋 포함 | `2026-10-10T01:23:45.123Z` | createdAt, updatedAt, lastLoginAt 등. 서버 기본 시간대에 따라 오프셋 표기가 `Z` 또는 `+00:00` 등이 될 수 있음(확인 필요: 운영 JVM 시간대) |
| 시각 | `HH:MM`(24시간) | `08:00` | 요약 메일 시각(사용자 시간대 기준) |
| 시간대 | IANA ID | `Asia/Seoul` | 사용자 시간대 |
| 요일 | ISO 요일 번호 1(월)~7(일) | `[1,2,3,4,5]` | 근무 요일 |
| dev 작업 시각 | ISO-8601 Instant | `2026-10-10T00:00:00Z` | `IF-DEV-001`의 `at` |

관리자가 정한 표시 형식(`IF-MSC-003`·`004`)은 API 값의 형식을 바꾸지 않습니다. 위 형식은 항상 그대로이고, 화면이 표시 형식을 받아 날짜·시각을 그립니다. 서버가 사람이 읽을 글로 만드는 날짜(사용자 정의 필드 값의 `text`, 활동 기록 `details`의 시작일·완료일 `from`·`to`, 날짜 알림 `summary`)는 관리자의 날짜 형식(기본 `2026.10.21`)을 따르고, 요약 메일 항목의 시각은 날짜 형식과 12/24시간제를 함께 따릅니다(예: `2026.10.21 15:05`, `2026.10.21 오후 3:05`). 날짜 필터 `this_week`의 범위는 주 시작 요일을 따릅니다(기본 일요일~토요일). 내보내기 파일(`IF-EXP-002`)의 시각만 `yyyy-MM-dd HH:mm`로 고정입니다.

### 2.9 낙관적 잠금

작업 패키지 수정(`IF-WP-008`)은 본문에 `lockVersion`이 반드시 있어야 하고, 현재 값과 다르면 409와 `current`를 돌려줍니다. 이동(`IF-WP-002`)은 `lockVersion`을 보내면 같은 검사를 합니다. 보드 카드 이동(`IF-BRD-009`)은 받은 `lockVersion`을 작업 수정에 그대로 넘깁니다(기본 보드는 작업을 바꾸지 않으므로 쓰지 않음).

클라이언트 주소는 연결한 쪽의 주소이고, 믿는 프록시(`OPENPMS_TRUSTED_PROXIES`)에서 온 요청이면 `X-Forwarded-For`를 오른쪽부터 읽어 믿는 프록시를 건너뛴 첫 주소입니다(384a2f9). 앞에 다른 주소를 붙여 보내도 프록시가 붙인 주소를 씁니다. 버킷은 앱 인스턴스 메모리에 있습니다(토큰 버킷도 같음. 인스턴스를 늘리면 인스턴스마다 따로 셈).


### 2.11 생성 요청의 재시도 (`Idempotency-Key`, v1.5)

93d1a74, `common/IdempotencyFilter`, V16 `idempotency_keys`. 응답을 받지 못한 생성 요청을 다시 보내도 한 번만 만들어지게 합니다.

| 항목 | 내용 |
| --- | --- |
| 대상 | `/api/`로 시작하는 POST 중 요청 헤더 `Idempotency-Key`가 있는 것. 로그인(세션 또는 API 토큰)한 요청만. `multipart/form-data`(첨부 업로드)는 대상이 아님 |
| 요청 헤더 | `Idempotency-Key: <요청마다 새 임의 값>`(앞뒤 공백을 뺀 1~255자, 권장: UUID) |
| 범위 | 키는 사람마다 따로입니다(PK = 사용자 + 키). 같은 키라도 다른 사람의 응답은 받지 않습니다 |
| 같은 키·같은 요청 | 메서드·경로(쿼리 포함)·본문의 SHA-256이 같으면 처음 2xx 응답(상태 코드·`Content-Type`·본문)을 그대로 돌려주고 응답 헤더 `Idempotent-Replayed: true`를 붙임. 컨트롤러는 다시 실행하지 않음 |
| 같은 키·다른 요청 | 422 "같은 Idempotency-Key를 다른 요청에 썼습니다. 요청마다 새 키를 쓰세요." |
| 처음 요청이 처리 중 | 409 "같은 요청을 아직 처리하고 있습니다. 잠시 뒤 다시 시도하세요." |
| 키 형식 오류 | 빈 값이거나 255자 초과 → 422 "Idempotency-Key는 1~255자여야 합니다." |
| 보관하지 않는 경우 | 2xx가 아닌 응답(실패한 요청은 고쳐서 같은 키로 다시 보낼 수 있음), 1MB 넘는 응답 |
| 대상에서 빼는 경로(v2.2) | `POST /admin/users`(`IF-ADM-025`)와 `POST /admin/users/{id}/temporary-password`(`IF-TPW-001`)는 헤더가 있어도 필터를 거치지 않음. 응답에 임시 비밀번호가 들어 있어 보관하면 `idempotency_keys`에 하루 남기 때문. (v2.7) 같은 이유로 `POST /admin/cicd/connections`(`IF-CICD-002`)와 `POST /admin/cicd/connections/{id}/secret`(`IF-CICD-004`)도 뺌(웹훅 비밀 평문). 퍼센트 인코딩한 글자가 든 경로로도 피할 수 없게 디코딩한 경로로 비교. 화면은 사용자 만들기에 키를 붙이지 않음 |
| 보관 기간 | 24시간. 같은 키가 오면 24시간 지난 행을 먼저 지우고, 나머지는 예약 작업 `token-cleanup`(매일 03:30)이 지움 |
| 헤더 없는 요청 | 지금처럼 매번 실행 |
| 화면 | 프로젝트 만들기(`IF-PRJ-003`)·복사(`IF-PRJ-025`), 작업 만들기(`IF-WP-005`)·복사(`IF-WP-001`), 코멘트(`IF-WP-012`)에 `crypto.randomUUID()` 키를 붙이고, 연결이 끊기면 0.8초 뒤 같은 키로 한 번 더 보냄(`frontend/src/api/http.ts`) |
| 문서 | `IF-TOK-008`(OpenAPI)에 헤더 안내가 있음(부록 6.3 주의 참고) |

요청 예

```http
POST /api/v1/projects/web-platform/work-packages
Authorization: Bearer opms_<토큰>
Content-Type: application/json
Idempotency-Key: 6f1c2b7e-0d1a-4b4e-9a0c-2f7d8e3b5a91

{"subject": "배포 점검", "typeId": "…"}
```

같은 요청을 다시 보낸 응답 예: `201`, `Idempotent-Replayed: true`, 본문은 처음 응답과 같음(같은 `number`).

`QueryGroup`

| 필드 | 타입 | 내용 |
| --- | --- | --- |
| `key` | string | 그룹 값의 id(유형·상태·우선순위·사람·버전·프로젝트), 사용자 정의 필드는 값(여러 값은 정렬해 쉼표로 이음). 값이 없는 그룹은 `""` |
| `label` | string | 그룹 이름(값 없는 그룹은 `""`) |
| `color` | string 또는 null | 유형·상태·우선순위 그룹의 색. 그 밖은 null |
| `count` | number | 그룹의 작업 수(전체 기준) |
| `sums` | `{열: 수}` 또는 null | `sums`가 켜졌을 때 그룹 합계 |

- 합계 대상은 `columns` 중 `work`, `remainingWork`, `doneRatio`, 정수·소수 형식 사용자 정의 필드(`cf:<id>`)입니다. 값은 소수(`BigDecimal`)이고, 합할 값이 없으면 null입니다.
- `work`·`remainingWork` 합계는 맞는 모든 작업을 더합니다.
- `doneRatio` 합계는 작업의 ∑ 합계처럼 진행률 설정(`progress.totals`)을 따르고, 합계 제외 상태(`excludedFromTotals`, 시드: 취소)의 작업은 뺍니다(384a2f9).
  - `weighted`: (작업량 합 − 남은 작업 합) × 100 ÷ 작업량 합, 반올림, 0 이상. 작업량이 있고 남은 작업이 비어 있는 작업은 남은 작업 = 작업량(시작 전)으로 셉니다(31e39bd). 작업량 합이 없거나 0이면 null.
  - `simple_average`: 완료 %가 있는 작업들의 평균, 반올림. 그런 작업이 없으면 null.
- 그룹 순서는 그 값의 순서(상태 순서·이름 등)이고, `sort`의 첫 기준이 그룹 기준과 같고 `desc`이면 거꾸로입니다. 그룹 안에서는 `sort`를 따릅니다.
- 그룹화하면 `hierarchy`가 켜져 있어도 평면 목록(`depth` 0, 맥락 행 없음)입니다.

`NotificationCounts`(v1.5) = `{all, byReason: {이유: 수}, projects: [{identifier, name, unread}], allProjects}`. `all`·`byReason`은 고른 프로젝트 안에서(이유 조건은 무시), `projects`·`allProjects`는 고른 이유 안에서(프로젝트 조건은 무시) 셉니다. 그래서 이유 선택 상자와 프로젝트 선택 상자가 서로의 선택을 반영한 수를 보여 줍니다. `projects`는 한국어 이름순, 읽지 않은 알림이 있는 프로젝트만. 헤더 배지(`IF-NTF-002`)는 볼 수 있는지와 상관없이 셉니다.

알림 이유(`reason`): mentioned, assigned, responsible, watched, created, commented, status_changed, priority_changed, dates_changed, shared, date_alert_start(시작 N일 전), date_alert_due(완료 N일 전), date_alert_overdue(기한 지남), (v3.0) verification_failed(릴리스 검증 실패: 작업의 담당자·공동 담당자에게, 남긴 본인 제외, 요약 "{이름}님이 {환경} 검증을 실패로 남겼습니다").

(v2.1) `assigned`는 담당자 목록의 모든 사람이 받습니다(각자의 알림 설정에서 담당 작업 알림을 켰을 때). 주 담당자로 지정된 사람의 요약은 전처럼 "…님이 나를 담당자로 지정했습니다", 주 담당자가 아니라 목록에 새로 들어간 사람은 "…님이 나를 공동 담당자로 지정했습니다"입니다. 날짜 알림(`date_alert_*`)도 담당자 목록의 모든 사람에게 갑니다.

### 4.8 표준 알림 형식 (v2.9)

Jenkins·Argo CD 연동이 `IF-CICD-007`로 보내는 JSON 하나입니다(본문 1 MiB까지). 필드는 아래뿐이고 다른 필드는 무시합니다. 그 알림이 이벤트를 만들지 않고 202 `{accepted: 0}`이 되는 것(어느 필드인지 알리지 않음): 본문이 JSON 객체가 아님, 필수 필드(`type`·`repository`·`id`·`status`·`at`, 배포는 `environment`)가 없거나 문자열이 아니거나 길이를 넘음, `type`·`status`가 정해진 값이 아님, `at`이 시각이 아님, 선택 필드 `image`·`ref`·`name`이 문자열이 아니거나 길이를 넘음, 빌드인데 `sha`가 16진수 7~64자가 아님. 그 밖은 버리지 않습니다: `url`이 문자열이 아니거나 2,000자를 넘으면 ""로, 배포의 `sha`가 맞지 않으면 없는 것(null)으로 보고 `image`에서 뽑습니다. `at`이 2000-01-01부터 지금 + 1일 밖이면 받기는 하지만(202) 처리할 때 그 이벤트가 `failed`가 됩니다.

| 필드 | 필수 | 형식 |
| --- | --- | --- |
| `type` | ✓ | `pipeline` 또는 `deployment`. Argo CD 연동은 `deployment`만(그 밖은 0건) |
| `repository` | ✓ | 저장소 경로 `group/name`, 300자까지. 이 연동의 허용 프로젝트에 붙은(떼지 않은) GitLab·GitHub 저장소의 `fullPath`와 대소문자 무시로 맞춤. 없으면 버리고, 둘 이상이면 버리고 WARN(연동 id와 건수만) |
| `id` | ✓ | 도구 쪽 빌드·배포 id, 200자까지. `(저장소, 연동 종류:id)`가 한 행 |
| `status` | ✓ | `pipeline`: `running`·`success`·`failed`·`canceled`. `deployment`: `running`·`success`·`failed` |
| `at` | ✓ | ISO 8601 시각(64자까지). 처리할 때 2000-01-01부터 지금 + 1일 밖이면 그 이벤트는 `failed`. 배포 시각·더 새로운 소식 판단에 씀 |
| `sha` | `pipeline` ✓ | 16진수 7~64자(대문자는 소문자로). `deployment`는 선택이고, 없으면 `image`에서 이미지 태그 규칙으로 뽑음 |
| `environment` | `deployment` ✓ | 도구 쪽 환경 이름, 100자까지. 프로젝트 환경의 이름·별칭과 대소문자 무시로 맞춤(못 맞추면 환경 미지정) |
| `image` |  | 이미지, 500자까지 |
| `ref` |  | 브랜치, 255자까지(빌드 배지가 MR 원본 브랜치와 맞출 때) |
| `name` |  | 빌드 이름, 200자까지(배지가 이름마다 최신을 모음). 없으면 "" |
| `url` |  | 빌드·배포 화면 주소, 2,000자까지. 연동의 `toolUrl`과 같은 출처가 아니면 "" |

서명 헤더(둘 중 하나가 맞아야 함, 아니면 다른 실패와 같은 404):

| 헤더 | 받는 연동 | 값 |
| --- | --- | --- |
| `X-OpenPMS-Signature` | Jenkins, Argo CD | `sha256=` + 본문 바이트의 HMAC-SHA256(키: 웹훅 비밀) 16진수 소문자. 상수 시간 비교 |
| `X-OpenPMS-Token` | Argo CD만 | 웹훅 비밀 그대로(Argo CD Notifications 웹훅은 고정 헤더만 보낼 수 있음). 상수 시간 비교 |

- 전달 키: `pipeline:std:<repository 소문자>:<id>:<status>:<at(초)>`, `deployment:std:…`. 같은 알림을 다시 보내면 한 번만 저장되고, 같은 상태를 다른 시각에 보내면(다시 실행) 새 소식입니다.
- 키·페이로드의 문자열에 NUL·짝 없는 서로게이트 문자가 있으면 저장하지 않습니다(0건).
- 예(배포): `{"type":"deployment","repository":"web/portal","id":"portal-2026-10-16T06:20:00Z","image":"registry.example.com/web/portal:1a2b3c4d","environment":"production","status":"success","url":"https://argocd.example.com/applications/portal","at":"2026-10-16T06:21:30Z"}`

| 쌓기 | 변경과 같은 트랜잭션에서 `webhook_deliveries`에 본문까지 쌓음(변경이 롤백되면 보낼 일도 없음). 삭제 이벤트도 지우기 전에 쌓으므로 작업이 없어진 뒤에도 보냄 |
| 보관 | 성공·실패로 끝난 전송 기록은 만든 지 30일 지나면 예약 작업 `token-cleanup`(매일 03:30)이 지움(dfde416) |
| 받는 주소 | 관리자가 정함. 링크 로컬(169.254.x, [fe80:…])과 metadata.google.internal은 등록할 수 없음(422, dfde416, v1.5부터 이름이 그 주소로 풀려도). 사내·루프백 주소는 기본 허용, `OPENPMS_WEBHOOK_BLOCK_PRIVATE=true`면 거부(v1.5). 보낼 때도 DNS를 다시 풀어 같은 검사를 하고, 막히면 보내지 않고 그 시도를 오류 "보내지 않음: …"으로 기록(재시도 규칙은 같음) |
| 보내기 | 예약 작업 `webhook-delivery`가 15초마다(앞 실행이 끝난 뒤 15초) 때가 된 것을 오래된 순으로 최대 50건 |
| 성공 | 2xx 응답. 그 밖의 응답·연결 실패는 1분, 5분, 30분, 120분 뒤 다시 보내고, 다섯 번째 시도도 실패하면 `failed` |
| 제한 | 리다이렉트를 따라가지 않음(3xx는 실패), 연결 5초, 응답 10초. 응답 본문은 읽지 않음 |
| 내부 코멘트 | 보내지 않음 |
| 받는 쪽 확인 | 받은 본문 그대로를 서명 키로 HMAC-SHA256 해 헤더 값과 비교합니다. 같은 이벤트가 두 번 올 수 있으므로(적어도 한 번) `X-OpenPMS-Delivery`로 중복을 거릅니다 |

### 5.6 IF-EXT-009 GitLab·GitHub 웹훅 (도구 → openPMS, v2.7)

| 항목 | 내용 |
| --- | --- |
| 주소 | 연동마다 다름: `OPENPMS_BASE_URL` + `/api/v1/hooks/cicd/{hookKey}`(`hookKey`는 서버가 만든 난수). 관리 · CI/CD 연동에서 만들 때 한 번 보여 주고, 목록에도 주소는 보임 |
| 인증 | 로그인·CSRF 없음. GitLab은 `X-Gitlab-Token` 값이 웹훅 비밀과 같아야 하고, GitHub는 `X-Hub-Signature-256: sha256=<본문의 HMAC-SHA256(웹훅 비밀) 16진수>`가 맞아야 함. 둘 다 상수 시간 비교 |
| 받는 이벤트 | GitLab `X-Gitlab-Event: Push Hook`(커밋들)·`Merge Request Hook`, GitHub `X-GitHub-Event: push`·`pull_request`. 그 밖의 이벤트(예: `ping`, 태그 푸시)는 202 `{accepted: 0}`. (v2.9) GitLab `Pipeline Hook`(파이프라인 id·이름·sha·ref·상태·시작·끝)·`Deployment Hook`(배포 id·환경·상태·`status_changed_at`·`deployable_url`, 커밋은 `commit_url`의 전체 sha, 없으면 `short_sha`), GitHub `workflow_run`(실행 id·워크플로 이름·`head_sha`·`head_branch`·`status`/`conclusion`·시각)·`deployment_status`(상태의 `created_at`, 환경, 배포의 sha, `inactive`는 버리고 `error`는 실패). 병합된 MR/PR은 병합 커밋(GitLab `squash_commit_sha` → `merge_commit_sha`, GitHub `merge_commit_sha`)도 저장 |
| 쓰는 필드 | 저장소 id(GitLab `project.id`, GitHub `repository.id`), 커밋의 id(sha)·메시지·작성자 이름·메일·시각·주소, MR/PR의 번호·제목·설명·상태(초안 포함)·소스/대상 브랜치·작성자·병합/갱신 시각·주소. 나머지는 저장하지 않음 |
| 중복 | 같은 커밋(`commit:<저장소 id>:<sha>`)과 같은 MR/PR 갱신(`mr:<저장소 id>:<번호>:<갱신 시각(초)>`)은 한 번만. (v2.9) 빌드·배포는 `pipeline:<저장소>:<id>:<상태>:<그 소식의 시각(초)>`처럼 상태 뒤에 시각을 붙여, 다시 실행한 같은 상태도 받음(웹훅과 폴링이 같은 상태를 두 번 저장할 수 있으나 더 새로운 소식만 반영). 도구의 전달 id 헤더(`X-GitHub-Delivery`, `X-Gitlab-Event-UUID`)는 기록·중복 판단에 쓰지 않음 |
| 응답 | 202 `{accepted}`, 실패는 모두 404 "찾을 수 없습니다."(연동이 있는지 드러내지 않음), 1 MiB 넘으면 413, 분당 600회 넘으면 429. 도구는 404·413을 실패로 보고 다시 보낼 수 있음 |
| 처리 시점 | 요청 안에서는 저장만. 작업에 이어지는 것은 다음 `cicd-process`(15초) 뒤. 저장소가 아직 붙지 않았으면 그 이벤트는 처리 때 지워지고, 붙인 뒤 폴링이 7일치를 다시 채움 |
| 본문 예시 | 두 도구의 공개 문서를 보고 직접 쓴 시험용 본문이 `backend/src/test/resources/cicd/*.json`에 있습니다 |

### 5.7 IF-EXT-010 GitLab·GitHub API (openPMS → 도구, v2.7)

| 항목 | 내용 |
| --- | --- |
| 기본 주소 | GitLab `<연동 주소>/api/v4`. GitHub는 연동 주소가 `https://github.com`이면 `https://api.github.com`, 아니면(Enterprise Server) `<연동 주소>/api/v3` |
| 인증 | GitLab `PRIVATE-TOKEN: <토큰>`, GitHub `Authorization: Bearer <토큰>`. 읽기 전용 토큰을 권함(GitLab `read_api`, GitHub Contents·Pull requests 읽기) |

| 실패 | 2xx가 아니면 그 저장소만 건너뛰고 cursor를 그대로 둠. 로그에는 연동·저장소 id와 고정 문구만(주소·토큰 없음). 연결 확인은 `{ok: false, status}` |
| 토큰이 없을 때 | 폴링·찾기·붙이기를 하지 않음(웹훅만 받음). (v2.9) 그 저장소의 배포는 비교할 수 없어 곧바로 확인 실패(`no_token`) |
| (v2.9) 빌드·배포 폴링 | GitLab `GET /projects/{id}/pipelines?updated_after=`·`/deployments?updated_after=`, GitHub `GET /repositories/{id}/actions/runs?created=>=…`·`/deployments`(배포마다 `/deployments/{id}/statuses`, 실행마다 저장소당 30개까지). 403·404는 빈 목록으로 보고 커밋·MR 폴링과 cursor는 그대로 진행 |
| (v2.9) 배포 비교 | 예약 작업 `cicd-process`가 배포마다 두 번: GitLab `GET /projects/{id}/repository/compare?from=&to=`(diff를 담아 크므로 본문 8 MiB까지, 넘으면 같은 범위를 `repository/commits?ref_name=<from>..<to>`로 다시 읽음), GitHub `GET /repositories/{id}/compare/{base}...{head}`(첫 쪽의 `total_commits`를 보고 뒤쪽 쪽만 읽어 최신 1,000개, 8 MiB를 넘으면 다시 시도 없이 확인 실패). 첫 배포의 조상 확인: GitLab `GET /projects/{id}/repository/merge_base?refs[]=&refs[]=`(결과가 그 커밋이면 포함), GitHub `compare/{그 커밋}...{배포}`의 `status`가 `ahead`·`identical`이면 포함. 조상 확인이 404(GitHub는 422도)이면 그 실행에서 저장소마다 한 번 GitLab `GET /projects/{id}`·GitHub `GET /repositories/{id}`로 저장소를 조회해, 보이면 포함 안 됨, 보이지 않거나 조회가 실패하면 그 질문의 실패(2.9 후속 수정). 실패는 1·2·4·8분 뒤 다시, 다섯 번째에 확인 실패. 토큰은 저장소가 붙은 GitLab·GitHub 연동의 것(GitHub는 Contents 읽기) |

## 6. 부록 A. 계획 문서 대비 경로 차이

`replica/architecture.md` §4.2의 처음 설계(134개)와 구현(186개)의 차이입니다. architecture.md는 527323b에서 '총 145개(설계 134 + 사내 SSO 7 + 보드 카드 3 + 날짜 형식 1)'로, 384a2f9 반영 때 비밀번호 만들기를 더해 '총 146개'로, v1.3 갱신(5d641d1 반영)에서 전역 역할 배정을 더해 '총 147개'로, v1.4 갱신(86e58a9 반영)에서 프로젝트 복사 1·API 토큰 8·웹훅 8을 더해 '총 164개'로, v1.5 갱신(99e0287 반영)에서 알림 건수 1을 더해 '총 165개'로, v1.6 갱신(3f9d5c0 반영)에서 시간 기록 12를 더해 '총 177개'로 구현 기록을 덧붙였지만, 아래 표는 처음 설계를 기준으로 합니다. 177개와 186개의 차이는 처음 설계에 없던 구현 경로(6.2의 v1.0 행들)와 설계에만 있는 경로(6.1)가 섞여 있기 때문입니다.
