## 1. 개요

### 1.1 목적

openPMS의 웹 화면(SPA)과 API 서버 사이의 REST 인터페이스, 사내 시스템이 API 토큰으로 부르는 같은 REST 인터페이스, 그리고 openPMS가 호출하는 외부 시스템(SMTP, OpenID Connect 공급자, 웹훅 수신 시스템) 인터페이스를 정의합니다.

### 1.2 작성 기준

| 항목 | 내용 |
| --- | --- |
| 기본 경로 | `/api/v1` |
| 주소 | `OPENPMS_BASE_URL`과 같은 출처. 예: `https://pms.example.co.kr/api/v1/...` |
| 전송 | 브라우저 ↔ 리버스 프록시는 HTTPS, 프록시 ↔ 앱은 HTTP(`127.0.0.1:8090`) |
| 프록시 헤더 | 프록시는 `X-Forwarded-For`·`X-Forwarded-Proto`를 보냅니다. 앱은 `OPENPMS_TRUSTED_PROXIES`(기본: 이 호스트 127.x·::1, Docker 브리지 172.16–31.x, Podman 네트워크 10.88–89.x)에서 온 요청의 헤더만 믿고, 그 클라이언트 주소로 요청 제한을 셉니다(2.10). `OPENPMS_FORWARD_HEADERS=none`이면 헤더를 무시합니다 |

| CORS | 없음(같은 출처 전용) |

### 2.2 인증

| 항목 | 내용 |
| --- | --- |
| 세션 쿠키 | `OPENPMS_SESSION`. HttpOnly, SameSite=Lax, Secure(운영 기본). 로그인(`IF-AUTH-001`), 초대 수락(`IF-AUTH-008`), (v2.2) 임시 비밀번호의 새 비밀번호 정하기(`IF-AUTH-009`), SSO 콜백으로 발급 |
| 세션 저장 | 서버 DB(Spring Session JDBC). 유지 시간 `OPENPMS_SESSION_TIMEOUT`(기본 8h) |
| CSRF | 서버가 `XSRF-TOKEN` 쿠키를 내려 주고, 클라이언트는 GET·HEAD 이외의 모든 요청에 `X-XSRF-TOKEN: <쿠키 값>` 헤더를 붙입니다. 없거나 틀리면 403 |
| 인증 불필요 경로 | `/api/v1/auth/login`, `/api/v1/auth/password-reset`, `/api/v1/auth/password-reset/confirm`, `/api/v1/auth/password-change`(v2.2), `/api/v1/auth/password-policy`, `/api/v1/auth/invitations/**`, `/api/v1/auth/sso-providers`, `/api/v1/auth/oidc/**`, `/api/v1/openapi.json`(v1.4) |
| 그 밖 | `/api/**`는 로그인(세션) 또는 API 토큰 필요. 세션이 없거나 사용자 상태가 `active`가 아니면 401 |
| 요청 예 | `PATCH /api/v1/work-packages/42`<br/>`Cookie: OPENPMS_SESSION=<세션 ID>; XSRF-TOKEN=<토큰>`<br/>`X-XSRF-TOKEN: <토큰>` |

API 토큰 인증(v1.4, `auth/ApiTokenFilter`·`ApiTokens`)

사내 시스템이 openPMS API를 부를 때 씁니다. 토큰은 사람마다 계정 설정에서 만듭니다(`IF-TOK-002`).

| 항목 | 내용 |
| --- | --- |
| 헤더 | `Authorization: Bearer opms_<무작위 43자>`. 쿠키를 보내지 않습니다 |
| 처리 | `ApiTokenFilter`가 CSRF 필터보다 먼저 `/api/` 요청의 Bearer 헤더를 봅니다. 맞는 토큰이면 그 요청 하나만 토큰 주인으로 인증합니다(세션을 만들지 않음). Bearer 요청에는 CSRF 검사를 하지 않습니다(쿠키가 없어 막을 대상이 없음) |
| 권한 | 토큰 주인의 권한 그대로(관리자가 만든 토큰은 관리자 권한). 프로젝트·작업 권한 검사는 세션 요청과 같음 |
| 범위 `read` | GET·HEAD·OPTIONS와 읽기용 POST 세 개(`/api/v1/work-packages/query`, `/api/v1/work-packages/export`, `/api/v1/work-packages/export/count`)만. 그 밖은 403 "읽기 전용 토큰입니다." |
| 범위 `write` | 주인이 화면에서 할 수 있는 모든 요청(아래 막힌 경로 제외) |
| 막힌 경로 | (v2.3) 필터는 요청 경로를 Spring이 라우팅하는 것과 같게 디코딩한 뒤 비교하므로 `/api/v1/me/%61pi-tokens`처럼 글자를 퍼센트 인코딩해도 같은 경로로 보고 막음(BUG-015). `/api/v1/auth/**`(단 `/api/v1/auth/me`는 허용), `/api/v1/me/password*`, `/api/v1/me/api-tokens*`, `/api/v1/admin/api-tokens*`, 연동 설정 `/api/v1/admin/settings/api`·`/api/v1/admin/webhooks*`·`/api/v1/admin/webhook-deliveries*`(dfde416, 관리자의 토큰도), (v2.2) `/temporary-password`로 끝나는 경로(`IF-TPW-001`·`002`)와 `POST /api/v1/admin/users`의 `method: temporaryPassword`(필터가 아니라 컨트롤러가 거절. 퍼센트 인코딩한 경로로도 피할 수 없음) → 403 "API 토큰으로는 로그인·비밀번호·토큰·연동 설정을 다룰 수 없습니다." |
| 401 | 형식이 틀림·없는 토큰·만료·폐기·주인이 활성 아님·로그인 실패 잠금 중 → "API 토큰이 올바르지 않거나 만료되었습니다.". 관리자가 토큰을 꺼 두면(`api.tokens_enabled=false`) → "API 토큰을 쓰지 않도록 설정되어 있습니다." |
| 요청 제한 | 토큰마다 분당 300회, 넘으면 429(2.10) |
| 저장 | DB에는 토큰의 SHA-256만 둡니다(`api_tokens.token_hash`). 원문은 만들 때 응답에 한 번만 나옵니다. `last_used_at`은 최대 1분에 한 번 기록 |
| 요청 예 | `GET /api/v1/work-packages/42`<br/>`Authorization: Bearer opms_<토큰>` |

버전 정책(v1.4, 도움말 · API 문서): 경로는 `/api/v1` 아래입니다. v1 안에서는 응답 필드를 더하기만 하고, 필드를 빼거나 뜻을 바꾸는 변경은 `/api/v2`로 냅니다. 연동은 모르는 필드를 무시하도록 만듭니다. 주요 경로의 요청·응답 모양은 `IF-TOK-008`(OpenAPI 3.1)에 있습니다.

### 2.5 오류 형식

RFC 9457 문제 상세(`application/problem+json`)입니다.

| 필드 | 타입 | 필수 | 내용 |
| --- | --- | --- | --- |
| `type` | string | 예 | 항상 `about:blank` |
| `title` | string | 예 | 화면에 보여 줄 한국어 제목 |
| `status` | number | 예 | HTTP 상태 코드 |
| `detail` | string | 아니요 | 추가 설명 |
| `errors` | `{field, message}[]` | 아니요 | 422 필드 오류. 일괄 처리 실패는 `field`가 `#번호` |
| `current` | object | 아니요 | 409 낙관적 잠금 충돌일 때 현재 작업 패키지(`WorkPackage`). (v2.2) `POST /auth/login`의 403·401에서는 `{code, changeToken?}`(임시 비밀번호) |

422 필드 오류 예

```json
{
  "type": "about:blank",
  "title": "입력값을 확인하세요.",
  "status": 422,
  "detail": "프로젝트 이름을 입력하세요.",
  "errors": [{ "field": "name", "message": "프로젝트 이름을 입력하세요." }]
}
```

409 충돌 예

```json
{
  "type": "about:blank",
  "title": "다른 사람이 먼저 수정했습니다.",
  "status": 409,
  "detail": "최신 내용을 불러온 뒤 다시 저장하세요.",
  "current": { "id": "…", "number": 42, "lockVersion": 7, "…": "…" }
}
```

임시 비밀번호로 로그인한 403 예(v2.2)

```json
{
  "type": "about:blank",
  "title": "새 비밀번호를 정해야 합니다.",
  "status": 403,
  "detail": "임시 비밀번호로는 바로 쓸 수 없습니다. 새 비밀번호를 정하세요.",
  "current": { "code": "password_change_required", "changeToken": "…" }
}
```

기한이 지난 임시 비밀번호는 401, 제목 "임시 비밀번호가 만료되었습니다.", 상세 "관리자에게 다시 발급을 요청하세요.", `current` `{ "code": "temporary_password_expired" }`입니다.

필드 오류의 `field` 값은 요청 필드 이름과 다를 수 있습니다(예: 요청 `statusId` → 오류 `status`, 요청 `parentNumber` → 오류 `parent`). 화면은 `errors[].field`로 입력란을 찾습니다.

### 2.7 날짜·시간 형식

| 종류 | 형식 | 예 | 쓰는 곳 |
| --- | --- | --- | --- |
| 날짜 | ISO-8601 `YYYY-MM-DD` | `2026-10-10` | 시작일, 완료일, 버전 기간, 휴무일, 알림 일시 중지 |
| 순간 | ISO-8601 날짜·시각, 오프셋 포함 | `2026-10-10T01:23:45.123Z` | createdAt, updatedAt, lastLoginAt 등. 서버 기본 시간대에 따라 오프셋 표기가 `Z` 또는 `+00:00` 등이 될 수 있음(확인 필요: 운영 JVM 시간대) |
| 시각 | `HH:MM`(24시간) | `08:00` | 요약 메일 시각(사용자 시간대 기준) |
| 시간대 | IANA ID | `Asia/Seoul` | 사용자 시간대 |
| 요일 | ISO 요일 번호 1(월)~7(일) | `[1,2,3,4,5]` | 근무 요일 |
| dev 작업 시각 | ISO-8601 Instant | `2026-10-10T00:00:00Z` | `IF-DEV-001`의 `at` |

관리자가 정한 표시 형식(`IF-MSC-003`·`004`)은 API 값의 형식을 바꾸지 않습니다. 위 형식은 항상 그대로이고, 화면이 표시 형식을 받아 날짜·시각을 그립니다. 서버가 사람이 읽을 글로 만드는 날짜(사용자 정의 필드 값의 `text`, 활동 기록 `details`의 시작일·완료일 `from`·`to`, 날짜 알림 `summary`)는 관리자의 날짜 형식(기본 `2026.10.21`)을 따르고, 요약 메일 항목의 시각은 날짜 형식과 12/24시간제를 함께 따릅니다(예: `2026.10.21 15:05`, `2026.10.21 오후 3:05`). 날짜 필터 `this_week`의 범위는 주 시작 요일을 따릅니다(기본 일요일~토요일). 내보내기 파일(`IF-EXP-002`)의 시각만 `yyyy-MM-dd HH:mm`로 고정입니다.

### 2.9 낙관적 잠금

작업 패키지 수정(`IF-WP-008`)은 본문에 `lockVersion`이 반드시 있어야 하고, 현재 값과 다르면 409와 `current`를 돌려줍니다. 이동(`IF-WP-002`)은 `lockVersion`을 보내면 같은 검사를 합니다. 보드 카드 이동(`IF-BRD-009`)은 받은 `lockVersion`을 작업 수정에 그대로 넘깁니다(기본 보드는 작업을 바꾸지 않으므로 쓰지 않음).

### 2.10 요청 제한

| 대상 | 기준 | 한도 |
| --- | --- | --- |
| `IF-AUTH-001` 로그인 | 클라이언트 주소 | 분당 20회(설정 `openpms.logins-per-minute`) |
| `IF-AUTH-004` 재설정 메일 | 클라이언트 주소 | 분당 5회 |
| `IF-AUTH-009` 임시 비밀번호의 새 비밀번호 정하기(v2.2) | 클라이언트 주소(로그인과 같은 버킷) | 분당 20회(설정 `openpms.logins-per-minute`) |
| `IF-ACC-002` 비밀번호 변경 | 사용자 | 분당 10회 |
| `IF-ACC-009` 비밀번호 만들기 링크 | 사용자 | 분당 3회 |
| API 토큰을 쓰는 모든 요청(v1.4) | 토큰 | 분당 300회 |

초과하면 429 "요청이 너무 많습니다."입니다.

클라이언트 주소는 연결한 쪽의 주소이고, 믿는 프록시(`OPENPMS_TRUSTED_PROXIES`)에서 온 요청이면 `X-Forwarded-For`를 오른쪽부터 읽어 믿는 프록시를 건너뛴 첫 주소입니다(384a2f9). 앞에 다른 주소를 붙여 보내도 프록시가 붙인 주소를 씁니다. 버킷은 앱 인스턴스 메모리에 있습니다(토큰 버킷도 같음. 인스턴스를 늘리면 인스턴스마다 따로 셈).


### 2.11 생성 요청의 재시도 (`Idempotency-Key`, v1.5)

93d1a74, `common/IdempotencyFilter`, V16 `idempotency_keys`. 응답을 받지 못한 생성 요청을 다시 보내도 한 번만 만들어지게 합니다.

| 항목 | 내용 |
| --- | --- |
| 대상 | `/api/`로 시작하는 POST 중 요청 헤더 `Idempotency-Key`가 있는 것. 로그인(세션 또는 API 토큰)한 요청만. `multipart/form-data`(첨부 업로드)는 대상이 아님 |
| 요청 헤더 | `Idempotency-Key: <요청마다 새 임의 값>`(앞뒤 공백을 뺀 1~255자, 권장: UUID) |
| 범위 | 키는 사람마다 따로입니다(PK = 사용자 + 키). 같은 키라도 다른 사람의 응답은 받지 않습니다 |
| 같은 키·같은 요청 | 메서드·경로(쿼리 포함)·본문의 SHA-256이 같으면 처음 2xx 응답(상태 코드·`Content-Type`·본문)을 그대로 돌려주고 응답 헤더 `Idempotent-Replayed: true`를 붙임. 컨트롤러는 다시 실행하지 않음 |
| 같은 키·다른 요청 | 422 "같은 Idempotency-Key를 다른 요청에 썼습니다. 요청마다 새 키를 쓰세요." |
| 처음 요청이 처리 중 | 409 "같은 요청을 아직 처리하고 있습니다. 잠시 뒤 다시 시도하세요." |
| 키 형식 오류 | 빈 값이거나 255자 초과 → 422 "Idempotency-Key는 1~255자여야 합니다." |
| 보관하지 않는 경우 | 2xx가 아닌 응답(실패한 요청은 고쳐서 같은 키로 다시 보낼 수 있음), 1MB 넘는 응답 |
| 대상에서 빼는 경로(v2.2) | `POST /admin/users`(`IF-ADM-025`)와 `POST /admin/users/{id}/temporary-password`(`IF-TPW-001`)는 헤더가 있어도 필터를 거치지 않음. 응답에 임시 비밀번호가 들어 있어 보관하면 `idempotency_keys`에 하루 남기 때문. 퍼센트 인코딩한 글자가 든 경로로도 피할 수 없게 디코딩한 경로로 비교. 화면은 사용자 만들기에 키를 붙이지 않음 |
| 보관 기간 | 24시간. 같은 키가 오면 24시간 지난 행을 먼저 지우고, 나머지는 예약 작업 `token-cleanup`(매일 03:30)이 지움 |
| 헤더 없는 요청 | 지금처럼 매번 실행 |
| 화면 | 프로젝트 만들기(`IF-PRJ-003`)·복사(`IF-PRJ-025`), 작업 만들기(`IF-WP-005`)·복사(`IF-WP-001`), 코멘트(`IF-WP-012`)에 `crypto.randomUUID()` 키를 붙이고, 연결이 끊기면 0.8초 뒤 같은 키로 한 번 더 보냄(`frontend/src/api/http.ts`) |
| 문서 | `IF-TOK-008`(OpenAPI)에 헤더 안내가 있음(부록 6.3 주의 참고) |

요청 예

```http
POST /api/v1/projects/web-platform/work-packages
Authorization: Bearer opms_<토큰>
Content-Type: application/json
Idempotency-Key: 6f1c2b7e-0d1a-4b4e-9a0c-2f7d8e3b5a91

{"subject": "배포 점검", "typeId": "…"}
```

같은 요청을 다시 보낸 응답 예: `201`, `Idempotent-Replayed: true`, 본문은 처음 응답과 같음(같은 `number`).

공동 담당자(v2.1, f494f76, `wp/Assignees`, `replica/fixes.md` #6)

작업 하나를 여러 사람이 맡고 사람마다 예상 시간을 적습니다. 목록의 첫 사람이 주 담당자이고, 응답의 `assignee`와 DB의 `work_packages.assignee_id`는 언제나 그 사람입니다(아무도 없으면 null).

| 필드 | 타입 | 내용 |
| --- | --- | --- |
| `key` | string | 그룹 값의 id(유형·상태·우선순위·사람·버전·프로젝트), 사용자 정의 필드는 값(여러 값은 정렬해 쉼표로 이음). 값이 없는 그룹은 `""` |

- 그룹 순서는 그 값의 순서(상태 순서·이름 등)이고, `sort`의 첫 기준이 그룹 기준과 같고 `desc`이면 거꾸로입니다. 그룹 안에서는 `sort`를 따릅니다.
- 그룹화하면 `hierarchy`가 켜져 있어도 평면 목록(`depth` 0, 맥락 행 없음)입니다.

`NotificationCounts`(v1.5) = `{all, byReason: {이유: 수}, projects: [{identifier, name, unread}], allProjects}`. `all`·`byReason`은 고른 프로젝트 안에서(이유 조건은 무시), `projects`·`allProjects`는 고른 이유 안에서(프로젝트 조건은 무시) 셉니다. 그래서 이유 선택 상자와 프로젝트 선택 상자가 서로의 선택을 반영한 수를 보여 줍니다. `projects`는 한국어 이름순, 읽지 않은 알림이 있는 프로젝트만. 헤더 배지(`IF-NTF-002`)는 볼 수 있는지와 상관없이 셉니다.

알림 이유(`reason`): mentioned, assigned, responsible, watched, created, commented, status_changed, priority_changed, dates_changed, shared, date_alert_start(시작 N일 전), date_alert_due(완료 N일 전), date_alert_overdue(기한 지남), (v2.4) sla_warning(SLA 임박), sla_breached(SLA 위반).

(v2.1) `assigned`는 담당자 목록의 모든 사람이 받습니다(각자의 알림 설정에서 담당 작업 알림을 켰을 때). 주 담당자로 지정된 사람의 요약은 전처럼 "…님이 나를 담당자로 지정했습니다", 주 담당자가 아니라 목록에 새로 들어간 사람은 "…님이 나를 공동 담당자로 지정했습니다"입니다. 날짜 알림(`date_alert_*`)도 담당자 목록의 모든 사람에게 갑니다.

| IF-APR-004 | POST | `/api/v1/portal/approvals/{id}/decision` | 승인 또는 반려. 반려는 사유가 필수이고 사유는 일반 텍스트(서식 없음, 특수문자는 이스케이프, 줄마다 문단)로 승인자 이름의 공개 코멘트에 남아 요청자가 읽고 반려한 행의 `comment`에도 남음(처리자 승인 패널에 보임). 승인 의견(선택)은 그 행에만 남고 요청자에게 보이지 않음. 작업 활동에 "{n}단계 {이름} 승인·반려"가 남고 상태 이동의 작성자는 결정한 승인자 | 로그인(본인의 `pending` 행) | `{decision: approve·reject, comment?}` | 200 `{decision: "approved"·"rejected"}` | 404 "승인 요청을 찾을 수 없습니다.", 409 "이미 처리된 승인입니다."(이미 결정한 내 행, 또는 동시에 진 쪽), 422 `decision`("승인 또는 반려를 고르세요." — 먼저 내 행인지 확인한 뒤이므로 남의 행은 값과 상관없이 404), 422 `comment`("반려 사유를 입력하세요.") |

승인자에게 나가는 메일(`approval-mail`: 차례가 온 승인 요청, 3근무일 뒤 독촉)은 경로가 아니라 예약 작업이 보냅니다(5.2, 03-아키텍처설계서 8.5.2, 8.17).

## 6. 부록 A. 계획 문서 대비 경로 차이

`replica/architecture.md` §4.2의 처음 설계(134개)와 구현(186개)의 차이입니다. architecture.md는 527323b에서 '총 145개(설계 134 + 사내 SSO 7 + 보드 카드 3 + 날짜 형식 1)'로, 384a2f9 반영 때 비밀번호 만들기를 더해 '총 146개'로, v1.3 갱신(5d641d1 반영)에서 전역 역할 배정을 더해 '총 147개'로, v1.4 갱신(86e58a9 반영)에서 프로젝트 복사 1·API 토큰 8·웹훅 8을 더해 '총 164개'로, v1.5 갱신(99e0287 반영)에서 알림 건수 1을 더해 '총 165개'로, v1.6 갱신(3f9d5c0 반영)에서 시간 기록 12를 더해 '총 177개'로 구현 기록을 덧붙였지만, 아래 표는 처음 설계를 기준으로 합니다. 177개와 186개의 차이는 처음 설계에 없던 구현 경로(6.2의 v1.0 행들)와 설계에만 있는 경로(6.1)가 섞여 있기 때문입니다.
