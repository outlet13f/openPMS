## 1. 개요

### 1.1 목적

openPMS를 사내 서버에 설치·배포하고, 백업·업그레이드·감시·장애 대응을 하고, 관리 화면에서 사용자와 업무 규칙을 관리하는 절차를 설명합니다.

### 1.2 시스템 구성

| 구성 요소 | 내용 |
| --- | --- |
| `app` 컨테이너 | 이미지 하나에 웹 화면(SPA)과 API가 같이 들어 있습니다. Spring Boot가 빌드된 화면을 같은 출처에서 제공합니다. 컨테이너 안 포트 8090 |
| `db` 컨테이너 | PostgreSQL 17 (`docker.io/library/postgres:17`). 호스트에 포트를 열지 않고 `app`만 접속합니다 |
| 볼륨 `db` | 데이터베이스 파일 (`/var/lib/postgresql/data`) |
| 볼륨 `files` | 첨부 파일 (`/data/files`) |

```
[사용자 브라우저] --HTTPS--> [사내 리버스 프록시: TLS]
                                   |
                                   v  127.0.0.1:8090
                     [app: SPA + /api/v1, 예약 작업, /data/files]
                                   |
                                   v
                     [db: PostgreSQL 17]
```

- 이미지는 3단계로 만듭니다: 웹 화면 빌드(Node 24) → jar 빌드(JDK 21) → 실행용 이미지(JRE 21만).
- 두 컨테이너 모두 `restart: unless-stopped`입니다. 서버를 재부팅하면 다시 뜹니다(Docker 데몬 또는 Podman 서비스가 켜져 있을 때).
- `app`은 `db`의 헬스 체크(`pg_isready`)가 통과한 뒤 시작합니다.
- 앱 안에서 예약 작업(날짜 알림, 알림 메일, 정리 작업, 웹훅 전송)이 돕니다(`OPENPMS_JOBS_ENABLED`).
- 1.4부터 외부와 주고받는 것이 둘 늘었습니다: 사내 시스템이 API 토큰으로 openPMS를 부르는 것(들어옴, 프록시를 거침), openPMS가 웹훅 받는 주소로 보내는 것(나감, `app` 컨테이너에서 바로).
- 1.5부터 무언가를 만드는 요청(프로젝트·작업·코멘트·복사)에 `Idempotency-Key`를 붙이면 응답을 못 받아 다시 보내도 한 번만 만들어집니다. 화면은 이 키를 자동으로 붙입니다(9.15.3).

## 2. 설치

### 2.1 요구 사항

| 항목 | 내용 |
| --- | --- |
| 컨테이너 런타임 | Docker + Compose, 또는 Podman (`podman compose`) |
| 빌드 메모리 | 2GB면 충분합니다(Gradle 힙을 768MB로 제한) |
| 실행 메모리 | JVM은 컨테이너 메모리의 75%까지 씁니다(`-XX:MaxRAMPercentage=75`) |
| 디스크 | 이미지 약 405MB(2026-10-10 측정. 1.4에서 PDF용 글꼴 TTF 약 5MB와 PDFBox가 더해져 조금 커짐, 다시 재지 않음), 그 밖에 DB·첨부 파일·백업 공간 |
| 빌드 시 네트워크 | 베이스 이미지(node, eclipse-temurin, postgres)와 npm·Gradle 의존성을 내려받습니다. 사내 미러를 쓴다면 미리 맞춰 둡니다 |
| 리버스 프록시 | TLS를 끝내는 사내 프록시(nginx 등). 업로드 한도 30MB 이상(첨부 한도 25MB, 앱 요청 한도 30MB) |
| SMTP | 사내 SMTP 릴레이(초대·비밀번호 재설정·알림 메일) |
| 실행 시 나가는 네트워크 | SMTP, SSO를 쓰면 IdP, **웹훅을 쓰면 받는 주소**(9.15). `app` 컨테이너에서 그 주소로 나가는 연결을 방화벽에서 열어 둡니다. 웹훅을 쓰지 않으면 열 필요가 없습니다 |

### 2.2 설치 절차

1. 저장소를 서버에 받고 저장소 최상위 폴더로 이동합니다.
2. 설정 파일을 만들고 권한을 줄입니다.

   ```bash
   cp .env.example .env
   chmod 600 .env
   ```

3. `.env`를 채웁니다(3장). 꼭 채울 값: `OPENPMS_BASE_URL`, `OPENPMS_DB_PASSWORD`, SMTP 값, `OPENPMS_MAIL_FROM`, `OPENPMS_ADMIN_EMAIL`. DB 비밀번호는 길고 무작위로 만듭니다(예: `openssl rand -base64 32`).
4. 이미지를 빌드하고 띄웁니다.

   ```bash
   docker compose up -d --build
   ```

   Podman이면 `docker` 자리에 `podman`을 씁니다(`podman compose up -d --build`).
5. 리버스 프록시가 공개 주소(https)를 `http://127.0.0.1:8090`으로 넘기도록 설정합니다(3.4).
6. 첫 관리자를 설정합니다(2.3).
7. 헬스 체크로 확인합니다: `curl -s http://127.0.0.1:8090/actuator/health` → `{"status":"UP"}`.

### 2.3 첫 관리자 설정 링크

openPMS에는 기본 관리자 비밀번호가 없습니다. 첫 기동 때 로그에 일회용 설정 링크가 한 번 나옵니다.

1. 로그에서 링크를 찾습니다.

   ```bash
   docker compose logs app | grep "No administrator yet"
   ```

   다음과 같은 줄이 나옵니다(주소와 토큰은 예시).

   ```
   No administrator yet. Set up admin@example.co.kr within 24 hours: https://pms.example.co.kr/invitations/<토큰>
   ```

2. 링크를 브라우저에서 엽니다. "openPMS 관리자 계정을 설정합니다. 이름과 비밀번호를 정하면 바로 시작합니다." 화면에서 **이름**, **새 비밀번호**를 정하고 **수락하고 시작하기**를 누릅니다. 이 계정이 첫 관리자입니다.
3. 이후 사용자는 **관리 → 사용자 → 사용자 초대**로 초대합니다(9.2).

링크 규칙:

- 활성 관리자가 없고 `OPENPMS_ADMIN_EMAIL`이 있을 때만 만듭니다.
- 24시간 유효하고 한 번만 쓸 수 있습니다.
- 관리자가 생기기 전에는 앱을 다시 시작할 때마다 새 링크가 나오고, 이전 링크는 쓸 수 없게 됩니다(410).
- 관리자가 생긴 뒤에는 다시 시작해도 링크가 나오지 않습니다.
- 그 주소가 이미 초대 상태가 아닌 계정(활성 등)이면 바꾸지 않고 경고만 남깁니다(`OPENPMS_ADMIN_EMAIL ... not changing it`).
- 링크가 유효한 24시간 동안 이 링크를 가진 사람은 관리자 계정을 만들 수 있습니다. 로그 접근을 제한하고, 설정을 마치면 바로 확인합니다.

## 3. 환경 설정

### 3.1 `.env` 환경 변수

`.env`는 `compose.yaml` 옆에 둡니다. `app`은 `.env` 전체를 받고, `db`는 `OPENPMS_DB_PASSWORD`만 받습니다.

| 변수 | 뜻 | `.env.example` 값 | 비고 |
| --- | --- | --- | --- |
| `OPENPMS_BASE_URL` | 사용자가 여는 공개 주소. 메일 속 링크, 첫 관리자 링크, SSO 콜백 주소에 씁니다. 예: `https://pms.example.co.kr` | 비어 있음 | 필수 |
| `OPENPMS_DB_PASSWORD` | 함께 뜨는 PostgreSQL의 `openpms` 사용자 비밀번호 | 비어 있음 | 필수. 비어 있으면 compose가 시작을 거부 |
| `OPENPMS_SMTP_HOST` | 사내 SMTP 릴레이 주소 | 비어 있음 | 필수 |
| `OPENPMS_SMTP_PORT` | SMTP 포트 | `25` | |
| `OPENPMS_SMTP_USER` | SMTP 사용자 | 비어 있음 | 인증이 없으면 비워 둠 |
| `OPENPMS_SMTP_PASSWORD` | SMTP 비밀번호 | 비어 있음 | 인증이 없으면 비워 둠 |
| `OPENPMS_SMTP_STARTTLS` | STARTTLS 사용 | `false` | |
| `OPENPMS_MAIL_FROM` | 보내는 사람. 예: `openPMS <no-reply@example.co.kr>` | 비어 있음 | 필수 |
| `OPENPMS_ADMIN_EMAIL` | 첫 관리자 이메일 | 비어 있음 | 첫 설치에 필수 |
| `OPENPMS_PORT` | 호스트에서 앱이 듣는 포트(127.0.0.1에만) | `8090` | 선택 |
| `OPENPMS_SESSION_TIMEOUT` | 로그인 세션 유지 시간 | `8h` | 선택 |
| `OPENPMS_SECURE_COOKIES` | 세션 쿠키에 `Secure`를 붙임 | `true` | 선택. 프록시가 평문 http일 때(시험용)만 `false` |
| `OPENPMS_JOBS_ENABLED` | 날짜 알림·알림 메일·정리 작업을 이 인스턴스에서 돌림 | `true` | 선택. 웹만 도는 추가 인스턴스는 `false` |
| `OPENPMS_TRUSTED_PROXIES` | `X-Forwarded-For`·`X-Forwarded-Proto`를 믿을 프록시 주소(정규식). 넣으면 기본값을 통째로 바꿈 | 주석(기본값 사용) | 선택. 기본: 이 호스트(127.x, ::1), Docker 브리지(172.16–31.x), Podman 네트워크(10.88.x, 10.89.x). 3.4 |
| `OPENPMS_FORWARD_HEADERS` | 프록시 헤더 처리. `native`(기본)는 위 주소의 헤더를 씀, `none`은 무시 | 주석(`native`) | 선택. 프록시 없이 앱에 바로 붙을 때만 `none` |
| `OPENPMS_WEBHOOK_BLOCK_PRIVATE` | `true`면 웹훅을 루프백·사설 주소(127.x, 10.x, 172.16–31.x, 192.168.x, 100.64.0.0/10, fc00::/7, 0.0.0.0)로 보내지 않음. 클라우드 메타데이터(169.254.x 등)는 이 값과 상관없이 늘 막음 | 주석(`false`) | 선택(1.5). 받는 사내 시스템이 사설 주소에 있으면 켜지 않음. 9.15.2 |

주의: `.env`에 변수 줄을 두고 값을 비우면 빈 문자열이 들어갑니다. `application.yml`의 기본값(예: 보내는 사람 `openPMS <no-reply@example.com>`, 기본 주소 `http://localhost:8090`)은 변수가 아예 없을 때만 쓰입니다. 필수 값은 반드시 채웁니다.

### 3.4 리버스 프록시·TLS

- 앱은 호스트의 `127.0.0.1:${OPENPMS_PORT}`(기본 8090)에서만 듣습니다. 다른 서버에서 바로 들어올 수 없습니다.
- TLS는 사내 리버스 프록시가 끝내고, 프록시가 `http://127.0.0.1:8090`으로 넘깁니다.
- `OPENPMS_BASE_URL`은 반드시 사용자가 브라우저에 치는 공개 주소(https)로 둡니다. 틀리면 메일과 설정 링크가 엉뚱한 곳(예: localhost)을 가리키고, SSO 로그인이 `failed`가 됩니다.
- `OPENPMS_SECURE_COOKIES=true`(기본)이면 세션 쿠키가 https에서만 갑니다. 평문 http로 시험할 때만 `false`로 바꾸고, 운영에서는 다시 `true`로 둡니다.
- 프록시 업로드 한도(nginx의 `client_max_body_size`)는 30MB 이상으로 둡니다.
- `/actuator/**`(헬스 체크)는 로그인 없이 응답합니다. 외부에 열 필요가 없으면 프록시에서 막는 것을 권합니다.
- **프록시는 `X-Forwarded-For`와 `X-Forwarded-Proto`를 꼭 보냅니다.** 앱은 이 헤더로 사람마다 로그인 요청 제한을 셉니다. 헤더가 없으면 모든 사람이 프록시 주소 하나로 보여 1분에 20회 한도를 함께 씁니다(10.5). nginx 예:

  ```nginx
  location / {
      proxy_pass http://127.0.0.1:8090;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      proxy_set_header X-Forwarded-Proto $scheme;
      client_max_body_size 30m;
  }
  ```

- 앱은 `OPENPMS_TRUSTED_PROXIES`에 맞는 주소에서 온 요청의 헤더만 믿습니다. 기본값은 이 호스트(127.x, ::1), Docker 브리지(172.16–31.x), Podman 네트워크(10.88.x, 10.89.x)입니다. 이 호스트의 프록시가 compose 포트로 들어오면 앱에는 보통 compose 네트워크의 게이트웨이 주소(Docker)나 컨테이너 자신의 주소(rootless Podman, 예: 10.89.1.3)로 보이므로 기본값으로 맞습니다.
- compose 네트워크가 이 대역이 아니면(Docker가 192.168.x 풀을 쓰는 경우 등) `.env`에 정규식을 넣습니다. 네트워크 게이트웨이는 `docker network inspect <프로젝트>_default`로 봅니다. 예: `OPENPMS_TRUSTED_PROXIES=127\.\d+\.\d+\.\d+|0:0:0:0:0:0:0:1|::1|192\.168\.\d+\.\d+`. 넣은 값이 기본값을 대신하므로 127.x 등도 같이 적습니다.
- 프록시 앞에 부하 분산기가 하나 더 있으면 그 주소도 정규식에 넣습니다.
- 정규식을 넓게(모든 주소) 잡지 않습니다. 누구나 헤더로 주소를 바꿔 요청 제한을 피할 수 있게 됩니다.
- 프록시 없이 앱에 바로 붙는 시험 구성에서는 `OPENPMS_FORWARD_HEADERS=none`으로 둡니다.
- API 토큰을 쓰는 사내 시스템도 같은 공개 주소(https)로 들어옵니다. 프록시가 `Authorization` 헤더를 지우거나 바꾸지 않게 둡니다(nginx는 기본으로 그대로 넘김). `/api/v1/openapi.json`은 로그인 없이 열립니다(내용은 경로 설명뿐).

## 5. 백업과 복원

백업 대상은 **DB 덤프**와 **`files` 볼륨(첨부 파일)** 두 가지입니다. 둘을 같은 시각에 받습니다.

### 5.1 DB 백업

```bash
docker compose exec -T db pg_dump -U openpms -Fc openpms > openpms-$(date +%F).dump
```

- `-Fc`는 PostgreSQL 사용자 지정 형식(압축)입니다. 복원은 `pg_restore`로 합니다.
- 파일로 받을 때는 반드시 `-T`(TTY 끄기)를 붙입니다. TTY가 붙으면 바이너리 덤프가 깨질 수 있습니다(`compose.yaml` 머리말 주석에는 `-T`가 있습니다).
- 매일 받도록 호스트 cron에 등록합니다.

### 5.2 첨부 파일 백업

```bash
docker compose exec -T app tar czf - -C /data/files . > files-$(date +%F).tar.gz
```

### 5.3 백업 파일 관리

- DB 덤프에는 SSO 클라이언트 시크릿(평문), 웹훅 서명 키(평문, 1.4), 사용자 정보, 비밀번호 해시, API 토큰 해시, 하루 동안 만든 작업·코멘트의 응답(`idempotency_keys`, 1.5)이 들어갑니다. 백업 파일은 `.env`처럼 다룹니다: 접근할 수 있는 사람을 줄이고, 암호화된 곳에 보관합니다.
- 보관 기간과 위치는 사내 백업 정책을 따릅니다.

### 5.4 DB 복원

앱을 멈추고 DB를 새로 만든 뒤 덤프를 넣습니다.

```bash
docker compose stop app
docker compose exec -T db dropdb -U openpms openpms
docker compose exec -T db createdb -U openpms -O openpms openpms
docker compose exec -T db pg_restore -U openpms -d openpms --no-owner < openpms-2026-10-10.dump
docker compose start app
```

### 5.5 복원 연습 (운영 DB를 건드리지 않음)

정기적으로 새 DB에 넣어 보고 지웁니다.

```bash
docker compose exec -T db createdb -U openpms restore_check
docker compose exec -T db pg_restore -U openpms -d restore_check --no-owner < openpms-2026-10-10.dump
docker compose exec -T db psql -U openpms -d restore_check -c "select count(*) from projects; select count(*) from work_packages;"
docker compose exec -T db dropdb -U openpms restore_check
```

### 5.6 첨부 파일 복원

```bash
docker compose exec -T app tar xzf - -C /data/files < files-2026-10-10.tar.gz
```

## 6. 업그레이드

1. **먼저 백업합니다**(DB와 첨부 파일 모두, 5장).
2. 새 소스를 받습니다(`git pull` 등).
3. 이미지를 다시 빌드하고 띄웁니다.

   ```bash
   docker compose up -d --build
   ```

4. 앱이 시작할 때 Flyway가 새 DB 마이그레이션을 자동으로 적용합니다. 로그와 헬스 체크로 확인합니다.

   ```bash
   docker compose logs -f app
   curl -s http://127.0.0.1:8090/actuator/health
   ```

5. 브라우저로 로그인해 홈·작업 목록·관리 화면이 열리는지 확인합니다.

- 마이그레이션이 실패하면 앱이 뜨지 않습니다. 원인을 고치거나, 이전 소스로 되돌려 빌드하고 백업에서 DB를 복원합니다(5.4).
- 세션은 DB에 있으므로 재시작해도 사용자는 다시 로그인하지 않아도 됩니다.
- 운영 웹 빌드는 `frontend/.env.production`(`VITE_API=http`)이 없으면 실패합니다. 빌드가 `production build without VITE_API=http`로 실패하면 8장을 봅니다.

## 7. 모니터링과 헬스 체크

### 7.1 헬스 체크 경로

앱이 127.0.0.1에만 열려 있으므로 호스트에서 확인합니다.

| 경로 | 용도 |
| --- | --- |
| `/actuator/health` | 전체 상태 (`UP`/`DOWN`) |
| `/actuator/health/liveness` | 살아 있는지(프로세스 재시작 판단용) |
| `/actuator/health/readiness` | 요청을 받을 준비가 됐는지 |

```bash
curl -s http://127.0.0.1:8090/actuator/health
# {"status":"UP"}
```

- 사내 감시 도구가 위 경로를 주기적으로 호출하도록 등록합니다.
- 메일 헬스는 일부러 껐습니다. `DOWN`이면 메일이 아니라 DB 연결 같은 다른 원인을 먼저 봅니다.
- actuator는 `health`(위 세 경로)만 엽니다. 메트릭(`/actuator/prometheus` 등) 경로는 없습니다(3.3).

| `OPENPMS_ADMIN_EMAIL ... not changing it` | 첫 관리자 주소가 이미 다른 상태의 계정 | 8장 |
| `SSO sign-in through <식별자> refused: <코드>` | SSO 로그인 거부(정상적인 거부 포함) | 9.13.6 |
| `SSO sign-in failed: ...` | IdP와의 실패(토큰 교환, 서명 등) | 9.13.6 |
| `OpenID provider <식별자> unavailable: ...` | 발견 문서를 읽지 못함 | 네트워크·DNS·인증서 |
| 메일 발송 실패 | SMTP 릴레이 응답 없음(10초 뒤 실패) | SMTP 설정. 알림 메일은 예약 작업이 다시 보냄 |
| `webhook delivery <전송 id> to <웹훅 id> not accepted: <오류>` (INFO) | 웹훅 받는 쪽이 2xx를 주지 않았거나 연결 실패(오류는 `HTTP 500`, `ConnectException…` 등). 정해진 간격으로 다시 보냄 | 9.15.2 전송 기록, 8장 "웹훅이 늘 실패" |
| `webhook-delivery: N` (INFO) | 웹훅 전송 작업이 이번에 다룬 건수(0건이면 남기지 않음) | 계속 많으면 받는 쪽이 느리거나 죽은 것. 1.5부터 근무일 변경 직후에는 자동 일정으로 밀린 작업 수만큼 늘 수 있음 |

## 8. 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| `set OPENPMS_DB_PASSWORD in .env` 오류로 시작이 안 됨 | `.env`가 `compose.yaml` 옆에 있는지, `OPENPMS_DB_PASSWORD`를 채웠는지 |
| 로그에 설정 링크가 없음 | `OPENPMS_ADMIN_EMAIL`이 비어 있지 않은지. 이미 활성 관리자가 있으면 나오지 않습니다. 그 주소가 이미 활성 계정이면 `not changing it` 경고만 나옵니다 |
| 설정 링크가 410(만료) | 24시간이 지났거나, 이미 썼거나, 그 뒤 앱을 다시 시작해 새 링크로 바뀐 경우. 관리자가 아직 없으면 `docker compose restart app` 후 로그의 새 링크를 씁니다 |
| 메일·설정 링크가 localhost 등을 가리킴 | `OPENPMS_BASE_URL`을 공개 주소로 고치고 `docker compose up -d` |
| 로그인해도 곧바로 로그인 화면으로 돌아옴 | 평문 http로 접속 중인데 `OPENPMS_SECURE_COOKIES=true`인지. 운영은 https로 접속합니다 |
| 로그인 상태인데 화면이 로그인 페이지에 머묾, 저장이 안 됨 | 화면이 실제 API가 아닌 브라우저 안 가짜 데이터로 빌드된 경우. 최신 소스로 이미지를 다시 빌드합니다 |
| 빌드가 `production build without VITE_API=http`로 실패 | `frontend/.env.production`이 빌드에 들어가지 않음. 파일이 있는지, `.dockerignore`의 `!frontend/.env.production` 줄이 있는지 |
| 헬스가 `DOWN` | `docker compose ps`로 `db`가 healthy인지, `docker compose logs app`에서 DB 연결 오류. SMTP는 원인이 아닙니다(메일 헬스 꺼짐) |
| 메일이 오지 않음 | SMTP 값(`HOST`·`PORT`·`USER`·`PASSWORD`·`STARTTLS`)과 `OPENPMS_MAIL_FROM`. 알림 메일은 `OPENPMS_JOBS_ENABLED=true`일 때만 나갑니다 |
| 큰 파일 업로드 실패 | 프록시 업로드 한도(30MB 이상). 앱의 첨부 한도는 25MB |
| `.env`의 DB 비밀번호를 바꿨더니 앱이 DB에 못 붙음 | PostgreSQL 이미지는 `db` 볼륨을 처음 만들 때만 비밀번호를 정합니다. DB 안에서 `ALTER USER openpms PASSWORD '...'`를 먼저 하고 `.env`를 같은 값으로 고칩니다 |
| 사용자가 "잠긴 계정입니다. 관리자에게 잠금 해제를 요청하세요."를 봄 | 관리자 잠금이거나 로그인 실패 잠금 시간 중입니다. 9.2.4 |
| 여러 사용자가 동시에 로그인 오류(요청이 너무 많음, 429) | 모든 사람이 프록시 주소 하나로 보이는 경우입니다. 프록시가 `X-Forwarded-For`·`X-Forwarded-Proto`를 보내는지, 프록시가 들어오는 주소가 `OPENPMS_TRUSTED_PROXIES`(기본 127.x·::1·172.16–31.x·10.88–89.x)에 맞는지 봅니다(3.4, 10.5). 한도는 1분 뒤 풀립니다 |
| 사용자 목록에 **일시 잠김** "로그인 실패가 많아 {시각}까지" | 비밀번호를 연속으로 틀려 잠금 시간 중입니다. 기다리거나 행 메뉴 **잠금 해제**(9.2.4) |
| SSO 사용자가 "비밀번호 만들기" 메일을 받지 못함 | SMTP 설정(위 "메일이 오지 않음"), 계정 이메일 주소. 같은 사람은 1분에 3번까지 요청할 수 있습니다(9.13.5) |
| 관리 화면 대신 "볼 수 없는 화면입니다 / 관리자만 볼 수 있는 화면입니다." | 관리자가 아닌 계정입니다. 다른 관리자가 **관리자로 지정**합니다(9.2) |
| SSO 관련 오류 | 9.13.6 오류 코드표 |
| PDF 내보내기가 "PDF로 내보내기에는 작업이 너무 많습니다." | PDF는 한 번에 1,000건까지입니다. 필터로 줄이거나 CSV·Excel(5,000건까지)을 씁니다 |
| PDF에 일부 글자가 `?`로 나옴 | 내장 글꼴(Pretendard)에 없는 문자(일부 이모지·특수 기호)입니다. 파일은 그대로 만들어지며 고칠 설정은 없습니다 |
| 내보내기 대화상자에서 PDF가 안 된다는 안내 | 브라우저 안 가짜 데이터로 빌드된 화면입니다(PDF는 서버가 만듦). 운영 이미지를 다시 빌드합니다(위 "로그인 상태인데 화면이…" 줄) |
| 웹훅이 늘 "실패" | 9.15.2 **최근 전송 기록**의 오류를 봅니다. 연결 오류면 `app` 컨테이너에서 받는 주소로 나가는 방화벽·DNS, https면 받는 쪽 인증서를 JRE가 믿는지(사내 CA는 이미지에 없음). `HTTP 3xx`면 리다이렉트를 따라가지 않으므로 최종 주소를 넣습니다. 받는 쪽은 10초 안에 2xx로 답해야 합니다 |
| 연동 시스템이 API에서 401 | 토큰 폐기·만료, 토큰 주인이 잠김·삭제됨, 관리자가 **API 토큰 쓰기**를 끔(응답 문구로 구분: "API 토큰을 쓰지 않도록 설정되어 있습니다." / "API 토큰이 올바르지 않거나 만료되었습니다."). 9.15.1 |
| 연동 시스템이 API에서 403 | "읽기 전용 토큰입니다."(바꾸는 요청에 읽기 전용 토큰), "API 토큰으로는 로그인·비밀번호·토큰·연동 설정을 다룰 수 없습니다."(닫힌 경로. 관리자 토큰으로 웹훅·토큰 스위치를 바꾸려 해도 이 문구, 관리자가 로그인해서 화면으로 바꿈), 그 밖은 토큰 주인에게 그 권한이 없음 |
| 연동 시스템이 API에서 429 | 토큰마다 1분에 300회를 넘었습니다. 1분 뒤 풀립니다. 요청을 나누거나 토큰을 나눕니다 |
| 연동 시스템이 만들기 요청에서 409 "같은 요청을 아직 처리하고 있습니다." | 같은 `Idempotency-Key`의 처음 요청이 아직 끝나지 않았습니다. 잠시 뒤 같은 키로 다시 보냅니다. 하루 내내 409면 처음 요청 도중 앱이 멈춘 경우이므로 새 키로 보냅니다(9.15.3) |
| 연동 시스템이 만들기 요청에서 422 "같은 Idempotency-Key를 다른 요청에 썼습니다." 또는 "Idempotency-Key는 1~255자여야 합니다." | 연동이 요청마다 새 키를 만들지 않고 재사용하거나, 키가 너무 깁니다. 연동 담당자에게 요청마다 새 UUID를 쓰게 합니다 |
| 웹훅 전송 기록에 "보내지 않음: 사내망·루프백 주소로는 보낼 수 없습니다…" | `OPENPMS_WEBHOOK_BLOCK_PRIVATE=true`인데 받는 주소(또는 그 이름이 가리키는 주소)가 사설·루프백입니다. 받는 쪽 주소를 바꾸거나 스위치를 끄고 `docker compose up -d`(9.15.2) |
| 프로젝트 메뉴에 **공수 보고서**가 없음, 작업에 **시간** 탭이 없음 | 그 프로젝트의 **프로젝트 설정 → 모듈**에서 **시간 기록**이 꺼져 있거나, 그 사람의 역할에 **시간 기록 보기**(보고서), **내 시간 기록**·**시간 기록 보기**(시간 탭)가 없습니다. 참관자에게는 기본으로 없습니다(9.16) |
| **내 공수**에서 저장하면 "저장하지 않았습니다." | 한 칸이라도 안 되면 그 주의 변경 전체가 저장되지 않습니다. 빨간 칸의 이유를 봅니다: "이 작업에 시간을 기록할 권한이 없습니다."(그 프로젝트의 역할·모듈), "여러 건으로 기록된 칸입니다. 작업의 시간 탭에서 고치세요.", "하루에 24시간을 넘게 기록할 수 없습니다."(그날 다른 작업까지 합한 시간) |
| 하루 합계가 빨간 글자로 보임 | 그날 합계가 **하루 근무 시간**(9.11.1, 기본 8)을 넘었다는 경고입니다. 저장은 됩니다. 막는 것은 하루 24시간뿐입니다 |
| 시간 기록할 때 원하는 활동이 없음 | 관리 · 달력과 날짜의 **시간 기록 활동**에서 꺼져 있거나 없습니다(9.11.4) |
| 알림 화면의 이유·프로젝트별 읽지 않은 수가 헤더 배지 수와 다름 | 선택지의 수는 지금 볼 수 있는 프로젝트의 알림만 셉니다(1.5). 헤더 배지는 볼 수 없게 된 프로젝트의 읽지 않은 알림까지 셉니다. 그 프로젝트에서 빠진 사람이면 정상입니다 |

## 9. 관리 화면 운영 절차

### 9.1 관리 화면 공통

- 들어가는 곳: 위 헤더의 계정 메뉴 → **관리**, 또는 사이드바의 **관리**(관리자에게만 보임). 주소 `/admin`.
- 관리 첫 화면은 다음 묶음으로 메뉴를 보여 줍니다.

| 묶음 | 메뉴 (주소) | 설명 |
| --- | --- | --- |
| 작업 설정 | **유형** (`/admin/types`) | 작업 유형과 색, 마일스톤 여부 |
| | **상태** (`/admin/statuses`) | 상태 이름과 닫힘·읽기 전용 규칙 |
| | **워크플로** (`/admin/workflows`) | 역할별로 허용하는 상태 전환 |
| | **우선순위** (`/admin/priorities`) | 우선순위 목록과 기본값 |
| | **사용자 정의 필드** (`/admin/custom-fields`) | 작업에 더하는 회사 고유 항목 |
| | **진행률 추적** (`/admin/progress`) | 완료 %를 계산하는 방식과 상위 작업의 합계 |
| 사람과 권한 | **사용자** (`/admin/users`) | 초대, 잠금, 관리자 지정, 전역 역할 |
| | **그룹** (`/admin/groups`) | 사람을 묶어 멤버십을 한 번에 |
| | **역할 및 권한** (`/admin/roles`) | 역할마다 할 수 있는 일 |
| | **로그인·비밀번호** (`/admin/authentication`) | 비밀번호 규칙, 로그인 실패 잠금, 재설정·초대 링크, 사내 SSO |
| 달력 | **달력과 날짜** (`/admin/calendar`) | 근무 요일과 공휴일, 날짜·시간 형식과 주 시작 요일 |
| 연동 (1.4) | **API와 웹훅** (`/admin/integrations`) | 사내 연동용 API 토큰 켜기·끄기와 전체 토큰, 다른 시스템에 변경을 알리는 웹훅(9.15) |

- 접근 권한: 관리자만 볼 수 있습니다. **사용자**·**그룹** 화면은 전역 권한 "사용자·그룹 관리"(`global.manage_users`)를 가진 사람도 엽니다. 관리자가 아닌 사람이 열면 "관리자만 볼 수 있는 화면입니다."가 나옵니다(API도 403).
- 목록 행 끝의 **…**(`{이름} 메뉴`) 버튼에 **수정**, **삭제** 같은 행 동작이 있습니다.
- 순서가 있는 목록(유형·상태·우선순위·사용자 정의 필드)은 행의 순서 메뉴에서 **맨 위로**, **위로**, **아래로**, **맨 아래로**로 순서를 바꿉니다.
- 색을 고르는 칸은 `#RRGGBB` 형식이고, 흰 배경 대비를 보여 줍니다. 4.5:1 미만이면 "흰 배경에서 글자로 읽기 어려운 색입니다(4.5:1 미만). 더 진한 색을 고르세요."가 나옵니다. 더 진한 색을 고릅니다.
- 저장하지 않은 변경이 있는 화면에서 다른 곳으로 가면 브라우저가 떠날지 묻습니다.
- 관리 화면을 나갈 때는 사이드바의 **관리 나가기**를 누릅니다.

### 9.2 사용자 (`/admin/users`)

목록 열: **이름**, **이메일**, **상태**, **전역 역할**, **프로젝트 수**, **최근 로그인**. 관리자에게는 "관리자", 내 계정에는 "나" 표시가 붙습니다. **전역 역할** 칸에는 그 사람이 가진 전역 역할 이름이 배지로 보이고, 없으면 `-`입니다.

- **상태로 거르기**: 전체 / 활성 / 초대됨 / 잠김(관리자 잠금과 로그인 실패로 일시 잠긴 사람 모두)
- **이름이나 이메일로 찾기**: 검색

#### 9.2.1 사용자 초대

1. **사용자 초대**를 누릅니다.
2. **이름**, **이메일**을 입력합니다. 관리자로 만들 사람이면 **관리자로 지정**을 체크합니다.
3. **초대 보내기**를 누릅니다. "{이메일}로 초대를 보냈습니다"가 나옵니다.
4. 상대가 초대 메일의 링크로 이름과 비밀번호를 정하면 계정이 활성이 됩니다. 초대 링크 유효 시간은 9.12의 **초대 링크 유효 시간(시간)**(기본 168시간)입니다.
5. 프로젝트를 보려면 프로젝트 관리자가 그 사람을 프로젝트 멤버로 추가해야 합니다(프로젝트 → 멤버 → **멤버 추가**).

#### 9.2.2 초대 다시 보내기

- 상태가 **초대됨**인 사람의 행 메뉴 → **초대 다시 보내기**. 이전에 보낸 링크는 더 이상 쓸 수 없습니다.
- 초대를 수락하기 전에는 관리자가 계정을 활성으로 바꿀 수 없습니다.

#### 9.2.3 관리자 지정·해제

- 행 메뉴 → **관리자로 지정** / **관리자 해제**. 관리자만 할 수 있고, 내 계정에는 이 메뉴가 없습니다.
- 관리자는 최소 2명 이상 두는 것을 권합니다. 마지막 활성 관리자는 잠그거나 삭제할 수 없습니다("마지막 관리자입니다.").

#### 9.2.4 잠그기·잠금 해제

- 퇴사·휴직·계정 도용 의심 시: 행 메뉴 → **잠그기**. "{이름}님의 계정을 잠갔습니다"가 나오고, **그 사람의 모든 세션이 즉시 끝납니다.** 잠긴 계정은 폼 로그인(423)도 SSO(`locked`)도 거부됩니다.
- 해제: 상태가 **잠김** 또는 **일시 잠김**인 행 메뉴 → **잠금 해제**. "{이름}님의 잠금을 풀었습니다"가 나오고, 로그인 실패 횟수와 실패 잠금 시간도 함께 초기화됩니다.
- 내 계정은 잠글 수 없습니다.
- **로그인 실패 잠금(자동 잠금)**: 9.12의 횟수만큼 비밀번호를 틀리면 **잠금 시간(분)** 동안 로그인이 거부됩니다. 이때 사용자 목록의 상태 칸에 **일시 잠김** 배지와 "로그인 실패가 많아 {시각}까지"가 보이고, **잠김** 필터로도 찾을 수 있습니다. 계정 상태 자체는 활성 그대로입니다. 잠금 시간이 지나면 저절로 풀립니다. 기다리지 않고 풀려면 행 메뉴의 **잠금 해제**를 누르거나(1.1까지의 **잠그기** → **잠금 해제** 우회는 필요 없음), 본인이 비밀번호 재설정을 마치면 풀립니다. 이미 열어 둔 목록은 잠금 시간이 지나도 새로 고칠 때까지 **일시 잠김**으로 남을 수 있습니다.

#### 9.2.5 사용자 삭제

1. 행 메뉴 → **삭제**.
2. 확인 대화상자 "사용자를 삭제할까요?": "{이름}님의 계정은 '삭제된 사용자'로 익명화됩니다. 활동 기록은 남고, 멤버십·주시·담당은 모두 풀립니다. 되돌릴 수 없습니다." → **삭제**.
- 삭제는 익명화입니다. 이름은 "삭제된 사용자", 이메일은 무효 주소로 바뀌고 비밀번호와 관리자 권한이 지워집니다. 멤버십, 주시, 공유, 알림, 그룹 소속, 담당자·책임자 지정이 풀리고 세션이 끝납니다. 작업 활동(저널)과 작성자 기록은 남습니다.
- 감사 목적상 기록을 남겨야 하면 삭제 대신 **잠그기**를 씁니다.
- 내 계정과 마지막 관리자는 삭제할 수 없습니다.

#### 9.2.6 전역 역할 주기·회수

전역 역할은 프로젝트와 상관없이 쓰는 권한입니다(예: 기본 역할 "프로젝트 생성자" = **프로젝트 만들기**, 직접 만든 역할에 **사용자·그룹 관리**). 역할 자체는 9.4에서 범위를 **전역 역할**로 정해 만들고, 여기서 사람에게 줍니다.

1. 사람의 행 메뉴 → **전역 역할**. 이 메뉴는 관리자에게만 보입니다.
2. "{이름}님의 전역 역할" 대화상자에서 줄 역할을 체크하고, 뺄 역할은 체크를 풉니다. 역할마다 그 역할의 권한 이름이 함께 보입니다.
3. **저장**. "저장했습니다"가 나오고 목록의 **전역 역할** 칸이 바뀝니다.

- 바로 적용됩니다. 그 사람이 이미 로그인해 있어도 다음 화면 이동(다음 요청)부터 새 권한으로 동작합니다. 예: "프로젝트 생성자"를 받은 사람은 프로젝트 목록의 **새 프로젝트**로 프로젝트를 만들 수 있고, 회수하면 다시 만들 수 없습니다.
- 대화상자는 고른 목록으로 **전체를 바꿉니다**. 모두 풀고 저장하면 전역 역할이 하나도 없게 됩니다.
- 전역 역할은 **관리자만** 줄 수 있습니다. "사용자·그룹 관리" 권한만 가진 사람은 사용자 화면은 열지만 이 메뉴가 없고, API로 시도해도 "관리자만 전역 역할을 줄 수 있습니다."(403)입니다. 사용자 관리자가 자기 권한을 넓히는 것을 막기 위함입니다.
- 대화상자에 역할이 없으면 "아직 전역 역할이 없습니다. 관리 · 역할 및 권한에서 범위를 '전역'으로 정해 만드세요."가 나옵니다. 9.4.1로 먼저 만듭니다.
- 관리자(9.2.3)는 전역 역할과 상관없이 모든 전역 권한을 가집니다. 관리자에게 전역 역할을 줄 필요는 없습니다.
- 사용자를 삭제(익명화)해도 전역 역할 배정은 지워지지 않고 남습니다. 삭제된 계정은 로그인할 수 없으므로 권한을 쓸 수는 없습니다.

### 9.3 그룹 (`/admin/groups`)

팀 단위로 사람을 묶어 두면 프로젝트 멤버를 한 번에 추가할 수 있습니다. 목록 열: **이름**, **멤버**(명 수).

| 작업 | 절차 |
| --- | --- |
| 그룹 만들기 | **그룹 만들기** → **이름** → **저장** |
| 멤버 관리 | 행 메뉴 → **멤버 관리** → "{그룹} 멤버" 대화상자에서 활성 사용자를 체크·해제 → **저장** |
| 이름 바꾸기 | 행 메뉴 → **이름 바꾸기** → **저장** |
| 삭제 | 행 메뉴 → **삭제** → "'{그룹}' 그룹을 삭제합니다. 사람 계정은 그대로 남습니다." → **삭제** |

- 프로젝트에 그룹을 추가하는 것은 프로젝트 → 멤버 → **멤버 추가**에서 "추가할 사람과 그룹"으로 그룹을 고르고 **역할**을 정합니다.
- 프로젝트에서 그룹을 빼면 그 그룹 구성원은 그룹을 통해 받은 권한을 잃습니다. 따로 멤버로 추가된 사람은 그대로 남습니다.

### 9.4 역할 및 권한 (`/admin/roles`)

목록 열: **이름**, **범위**(프로젝트 역할 / 전역 역할), **권한 수**, **멤버십 수**. 내장 역할에는 "내장" 표시가 붙습니다.

#### 9.4.1 역할 추가

1. **역할 추가**를 누릅니다.
2. **이름**을 입력하고 **범위**를 고릅니다.
   - **프로젝트 역할**: 프로젝트 멤버에게 붙는 역할입니다.
   - **전역 역할**: 프로젝트와 상관없이 사람에게 붙는 역할입니다(프로젝트 만들기 등).
3. **만들기**. 만든 뒤 바로 그 역할의 권한 편집 화면으로 이동합니다. 프로젝트 역할은 "프로젝트 보기"·"작업 보기"가 미리 체크되어 있습니다.

#### 9.4.2 권한 편집

1. 행 메뉴 → **권한 편집**.
2. 권한 묶음(프로젝트, 작업, 보기, 보드, 시간 기록(1.6), 전역)별 체크박스를 체크·해제합니다. 묶음 전체는 **이 묶음 모두**.
3. **저장**.

- 내장 역할 "비멤버"는 공개 프로젝트를 멤버가 아닌 사람이 볼 때 쓰는 역할입니다. 이름은 바꿀 수 없고 권한만 고칠 수 있습니다.
- 새 프로젝트 역할을 만들면 워크플로(9.7)도 정해야 그 역할의 사람이 상태를 바꿀 수 있습니다.
- 권한 목록과 기본 역할의 권한은 부록 B.

#### 9.4.3 역할 삭제

- 행 메뉴 → **삭제** → "'{역할}' 역할과 그 워크플로가 지워집니다. 이 역할을 가진 멤버가 있으면 삭제할 수 없습니다." → **삭제**.

#### 9.4.4 전역 역할 배정과 권한 보고서

- 1.2까지는 전역 역할을 사람에게 배정하는 화면이 없었습니다. 1.3부터 **사용자** 화면의 행 메뉴 **전역 역할**로 줍니다(9.2.6). 여기 **역할 및 권한**에서는 전역 역할을 만들고 권한을 고칩니다.
- 전역 권한은 두 가지입니다: **프로젝트 만들기**(`global.create_projects`), **사용자·그룹 관리**(`global.manage_users`). 사용자·그룹 관리를 가진 사람은 사용자 초대·잠금·삭제, 그룹 관리를 할 수 있지만 관리자 지정과 전역 역할 배정은 할 수 없습니다.
- 누가 어떤 전역 역할을 가졌는지는 **사용자** 목록의 **전역 역할** 칸으로 봅니다.

**권한 보고서**(1.4, `/admin/roles/report`): **역할 및 권한** 화면의 **권한 보고서** 링크로 엽니다. "모든 역할의 권한을 한 표에서 보고 고칩니다. 바꾼 역할만 저장됩니다."

1. 프로젝트 역할 표와 전역 역할 표가 있습니다. 행은 권한, 열은 역할입니다. 칸마다 체크박스(화면 읽기 프로그램에는 "{역할}: {권한}")가 있습니다.
2. 바꿀 칸을 누릅니다. 여러 역할을 한꺼번에 고칠 수 있습니다.
3. **역할 N개 저장**을 누르면 바꾼 역할만 저장되고 "역할 N개의 권한을 저장했습니다"가 나옵니다.

- 저장은 역할마다 권한 편집(9.4.2)과 같아서 그 역할을 가진 사람에게 다음 요청부터 바로 적용됩니다. 저장하지 않고 떠나면 바꾼 칸은 버려집니다.
- 권한 감사(분기 점검 등)에 이 표를 씁니다. 표 자체를 파일로 내보내는 기능은 없습니다.

#### 9.4.5 보드 권한과 보드 관리

보드는 관리 메뉴가 아니라 각 프로젝트의 **보드** 화면에서 관리합니다. 관리자는 역할의 보드 권한(권한 묶음 "보드")으로 누가 무엇을 할 수 있는지 정합니다. 사용자용 절차는 「07-사용자매뉴얼」 7.2·11.8에 있습니다.

| 권한 (화면 이름) | 할 수 있는 일 |
| --- | --- |
| **보드 보기** (`board.view`) | 보드 목록·보드 보기, 카드 옮기기(상태별·담당자별·버전별 보드에서 작업 편집 권한이 있을 때), **필터**로 저장하지 않고 걸러 보기, **저장된 필터로 되돌리기** |
| **보드 관리** (`board.manage`) | 보드 만들기(종류 **상태별**·**담당자별**·**버전별**·**빈 보드**·**하위 프로젝트별**·**상위-하위**), 보드 이름 바꾸기·삭제, 열 추가·순서·이름·빼기, 빈 보드에 작업 넣기(**기존 작업 넣기**)·빼기(카드의 X)·옮기기, 빈 보드 열에서 새 작업 만들기, **필터 저장** |

- **빈 보드**: 만들면 **할 일** 목록 하나로 시작합니다. 목록 이름은 1~60자, 열은 보드마다 30개까지입니다. 빈 보드에 카드를 넣고·옮기고·빼는 것은 보드 배치만 바꾸며 작업 패키지는 바뀌지 않습니다(작업의 활동 기록에도 남지 않음). 넣을 수 있는 작업은 그 프로젝트의 작업뿐입니다.
- **열에서 새 작업 만들기**: 상태별·담당자별·버전별 보드의 열 + 로 만든 작업은 그 열의 상태·담당자·버전을 받고, 유형은 프로젝트의 기본 유형(없으면 첫 유형)입니다. 작업 만들기 권한(`wp.create`)이 필요하고, 일반 작업 생성과 같은 규칙과 권한 검사를 거칩니다.
- **보드 필터**: 작업 목록과 같은 필터(제목 검색 포함)로 모든 열의 카드를 좁힙니다. **필터 저장**한 필터는 그 보드를 보는 모든 사람에게 적용됩니다. 저장하지 않은 필터는 본인 화면에서만 쓰이고 새로 고치면 사라집니다.
- **하위 프로젝트별**(1.3): 열마다 이 프로젝트 바로 아래의 하위 프로젝트 하나(만드는 사람이 볼 수 있고 보관되지 않은 것), 카드는 그 하위 프로젝트의 작업입니다. 카드를 다른 열로 옮기면 **작업이 그 하위 프로젝트로 옮겨집니다**(하위 작업도 함께, 작업 메뉴의 **이동**과 같은 규칙. 옮길 사람에게 작업 이동 권한과 대상 프로젝트의 작업 만들기 권한이 필요). 열의 + 로 만든 작업은 그 하위 프로젝트에 생기고, 그 프로젝트가 쓰지 않는 유형이면 그 프로젝트의 기본 유형이 됩니다. 하위 프로젝트에 **보드** 모듈이 꺼져 있어도 상위 프로젝트 보드의 열로는 나옵니다.
- **상위-하위**(1.3): 열마다 상위 작업 하나, 카드는 그 하위 작업입니다. 처음에는 하위 작업이 있는 작업 6개(번호순)로 시작하고, **열 추가** → "상위 작업을 열로 추가" 대화상자에서 제목이나 #번호로 찾아 더합니다(같은 프로젝트의 작업만). 카드를 옮기면 작업의 상위가 바뀌고(작업의 활동 기록에 남음), 열의 + 로 만든 작업은 그 작업의 하위가 됩니다.
- 하위 프로젝트별·상위-하위 보드의 열 이름은 그 프로젝트·작업의 이름을 따르므로 바꿀 수 없습니다.
- 보드를 지우거나 열·카드를 빼도 작업 패키지는 지워지지 않습니다.

#### 9.4.6 내부 코멘트 권한 (1.4)

내부 코멘트는 특정 역할만 읽는 코멘트입니다(예: 관리자끼리의 메모). 두 가지가 모두 있어야 씁니다.

1. 프로젝트에서 켜기: 프로젝트 → 프로젝트 설정 → 작업 설정 → **내부 코멘트** → **이 프로젝트에서 내부 코멘트 쓰기**(프로젝트 수정 권한). 기본은 꺼져 있습니다.
2. 역할 권한: **내부 코멘트 쓰기**(`wp.add_internal_comments`)가 있는 사람만 코멘트를 쓸 때 **내부 코멘트**를 체크할 수 있고, **내부 코멘트 보기**(`wp.view_internal_comments`)가 있는 역할만 그 코멘트를 봅니다. 기본으로는 프로젝트 관리자만 두 권한을 가집니다(부록 B).

- 보기 권한이 없는 사람에게는 활동 탭, 검색 결과, 알림 어디에도 내부 코멘트가 나오지 않습니다. 웹훅으로도 보내지 않습니다(9.15.2).
- 내부 코멘트에는 "내부" 배지와 다른 배경이 붙습니다.
- 프로젝트에서 다시 끄면 새 내부 코멘트를 쓸 수 없습니다. 이미 쓴 내부 코멘트는 계속 내부로 남습니다(보기 권한이 있는 역할만 봄).
- 멤버 역할에 보기 권한을 주면 그 역할의 모든 사람이 읽게 되므로, 역할 권한을 바꿀 때 권한 보고서(9.4.4)로 확인합니다.

### 9.5 유형과 양식 구성

#### 9.5.1 유형 (`/admin/types`)

목록 열: **순서**, **이름**, **마일스톤**, **새 프로젝트 기본**, **로드맵에 표시**, **작업 수**, **프로젝트 수**.

유형 추가:

| --- | --- |

| **새 프로젝트에서 기본으로 사용** | 새로 만드는 프로젝트에서 켜집니다. 이미 있는 프로젝트에는 영향이 없습니다 |

- 삭제: "'{유형}' 유형과 그 워크플로가 지워집니다. 이 유형을 쓰는 작업이 있으면 삭제할 수 없습니다."

#### 9.5.2 양식 구성 (`/admin/types/{id}/form`)

유형마다 작업 상세에 보이는 속성 그룹과 순서를 정합니다. 유형 행 메뉴 → **양식 구성**.

| 영역 | 조작 |
| --- | --- |
| **속성 그룹** | 그룹 이름을 바꾸고(**그룹 이름**), 그룹을 위·아래로 옮기고, **그룹 추가**(최대 20개), 그룹 삭제(항목은 숨김으로). 항목은 **위로**·**아래로**, 항목 메뉴(`{항목} 옮기기`)에서 '{그룹}' 그룹으로 보내기 또는 **숨기기** |
| **자동 배치** | 어느 그룹에도 넣지 않은 사용자 정의 필드입니다. 작업에 쓰이면 상세 맨 아래 '추가 정보' 그룹에 나옵니다 |
| **숨긴 항목** | 이 유형의 작업 상세에 보이지 않습니다. 값은 지워지지 않습니다 |
| **기본 설명** | 이 유형으로 새 작업을 만들 때 설명 칸에 미리 채워지는 내용 |

- **기본값으로**: 기본 양식으로 되돌립니다. **변경 취소**: 저장하지 않은 변경을 버립니다. 다 고쳤으면 **저장**.
- 비어 있는 그룹은 상세에 보이지 않습니다. 그룹이 하나도 없으면 모든 항목이 숨겨지고 사용자 정의 필드는 '추가 정보'에만 나옵니다.
- 저장할 때 알 수 없는 항목, 같은 항목 두 번, 같은 이름의 그룹은 거부됩니다.

### 9.7 워크플로 (`/admin/workflows`)

역할마다 어떤 상태에서 어떤 상태로 바꿀 수 있는지 정합니다. 사용자는 자기 역할에 허용된 전환만 고를 수 있고, 보드에서 카드를 옮길 때도 같은 규칙이 적용됩니다.

1. 위에서 **유형**과 **역할**을 고릅니다(프로젝트 역할만, 내장 역할 제외).
2. 표(행: 현재 상태, 열: 바꿀 상태 — **현재 상태 → 바꿀 상태**)의 칸을 체크합니다. 행·열 머리의 **모두**/**해제**로 한 상태에서 가는(오는) 전환을 한꺼번에 허용·해제합니다.
3. **저장**. 잘못 체크했으면 저장 전에 **되돌리기**.

- 저장하지 않은 채 다른 유형·역할로 바꾸면 "저장하지 않은 변경을 버릴까요?"가 나옵니다(**버리고 이동**).
- 허용된 전환이 하나도 없으면 "허용된 전환이 없습니다 — {역할} 역할은 {유형} 작업의 상태를 바꿀 수 없습니다."가 나옵니다. 참관자처럼 의도한 경우가 아니면 전환을 체크합니다.
- **다른 유형·역할에 복사**: 지금 저장된 전환을 **대상 유형**과 **대상 역할**에 그대로 덮어씁니다. 저장하지 않은 변경이 있으면 쓸 수 없습니다.
- 기본값: 관리자(프로젝트 관리자)·멤버는 모든 유형에서 모든 상태 간 전환 가능, 참관자는 상태를 바꾸지 못합니다.

목록 열: 순서, 이름, **형식**, **유형**, **사용 범위**(모든 프로젝트 / 프로젝트 N개), **필수**.

필드 만들기:

1. **새 필드**를 누릅니다("새 사용자 정의 필드").
2. 칸을 채웁니다.

| 칸 | 설명 |

### 9.10 진행률 추적 (`/admin/progress`)

| 영역 | 선택지 | 설명 |
| --- | --- | --- |
| **계산 방식** | **작업량 기준** | 완료 %를 직접 입력하거나, 작업량과 남은 작업 중 하나를 바꾸면 나머지를 계산합니다 |
| | **상태 기준** | 완료 %는 상태마다 정한 값(관리 › 상태)을 따르고 직접 바꿀 수 없습니다. 남은 작업은 작업량에서 계산합니다 |
| **닫힌 상태가 되면 완료 100%, 남은 작업 0으로** | 체크 | 완료·취소처럼 닫힌 상태의 작업은 진행률을 끝난 것으로 봅니다 |
| **상위 작업의 합계 완료 %** | **작업량 가중** | (합계 작업량 − 합계 남은 작업) ÷ 합계 작업량. 큰 작업이 더 크게 반영됩니다 |
| | **단순 평균** | 자신과 하위 작업의 완료 %를 평균합니다. 작업량이 없어도 됩니다 |

- 이 합계 방식은 작업 목록의 **합계 표시**(그룹 합계·전체 합계 행)의 완료 %에도 쓰입니다(1.2). 합계 제외 상태(9.6)는 빠집니다.
- **작업량 가중**에서는 작업량은 있고 남은 작업이 비어 있는 작업을 아직 시작하지 않은 것(남은 작업 = 작업량)으로 셉니다. 1.1까지는 이런 작업이 끝난 것으로 계산되어 합계가 높게 나왔습니다(예: 신규 작업만 있는 그룹 100%).

- **저장**하면 모든 작업의 완료 %와 남은 작업을 새 규칙으로 다시 계산합니다("저장했습니다. 작업 N개를 다시 계산했습니다."). **이 재계산은 활동 기록을 남기지 않습니다.** 작업이 많을 때는 사용이 적은 시간에 바꿉니다.
- 상태 기준으로 바꾸기 전에 9.6에서 상태마다 **완료 %**를 정해 둡니다.

### 9.11 달력과 날짜 (`/admin/calendar`)

1.0의 화면 이름은 **근무일 및 휴무일**이었습니다. 1.1에서 이름이 **달력과 날짜**로 바뀌고 **날짜 형식** 절이 더해졌습니다. 주소는 같습니다.

#### 9.11.1 근무 주

- **근무 요일**: 월요일–일요일 체크(기본 월–금).
- **하루 근무 시간**: 작업량을 일 단위로 보여 줄 때 하루로 치는 시간(1–24, 기본 8).
- **저장**. 근무 요일을 바꾸면 "근무 요일을 바꿀까요? — 모든 프로젝트의 작업 완료일이 다시 계산되고, 바뀐 작업마다 활동 기록이 남습니다." → **바꾸고 다시 계산**.
- 근무 요일이나 휴무일을 바꾸면 모든 프로젝트의 작업 완료일이 새 달력으로 다시 계산됩니다. 시작일과 기간은 유지됩니다.

#### 9.11.2 공휴일 및 휴무일

1. 연도를 고릅니다(**이전 해**/**다음 해**).
2. **날짜**와 **이름**(예: 창립기념일)을 넣고 **휴무일 추가**. "휴무일을 추가하고 일정을 다시 계산했습니다".
3. 지울 때는 행의 **{이름} 삭제**. "휴무일을 지우고 일정을 다시 계산했습니다".

- 여기 있는 날은 일정 계산에서 건너뜁니다. 설날·추석·대체공휴일처럼 해마다 바뀌는 날은 **연초에 입력**합니다.
- 휴무일 추가·삭제도 일정 재계산을 일으키므로 업무 시간 외에 하는 것을 권합니다.

#### 9.11.3 날짜 형식

화면 아래쪽 **날짜 형식** 절에서 모든 사람에게 쓰이는 날짜·시간 표기와 주 시작 요일을 정합니다. 안내 문구는 "모든 사람의 화면, 활동 기록, 메일에 같은 형식이 쓰입니다."입니다. 개인별로 바꾸는 설정은 없습니다.

| 칸 | 선택지 |
| --- | --- |
| **날짜** | **기본(한국어: 오늘 날짜)**(예: 2026.10.21, `YYYY.MM.DD` 꼴), **YYYY.MM.DD**, **YYYY-MM-DD**, **YYYY/MM/DD**, **YYYY년 M월 D일**, **DD.MM.YYYY**, **MM/DD/YYYY**. 선택지 옆 괄호에 오늘 날짜를 그 형식으로 보여 줌 |
| **시간** | **기본(한국어: 15:05)**, **24시간 (15:05)**, **12시간 (오후 3:05)** |
| **주 시작 요일** | **기본(한국어: 일요일)**, **월요일**, **토요일**, **일요일**. 도움말 "캘린더, 팀 플래너, 날짜 선택 달력의 첫 열" |

1. 세 칸을 고릅니다. 아래 "미리 보기: {날짜} {시간}" 줄에 고른 형식이 바로 보입니다.
2. **저장**("날짜 형식을 저장했습니다"). 값을 바꿨을 때만 누를 수 있습니다.

적용 범위:

- 화면의 모든 날짜·시각(목록·상세·알림 등), 캘린더, 팀 플래너, 날짜 대화상자의 달력, Gantt의 주 눈금.
- 서버가 쓰는 날짜: 활동 기록의 날짜 변경 내역, 사용자 정의 필드의 날짜 값, 메일. 요약 메일의 항목 시각도 날짜 형식과 12/24시간 설정을 따릅니다(예: `2026.10.21 15:05`, 12시간이면 `2026.10.21 오후 3:05`).
- 날짜 필터 **이번 주**는 주 시작 요일부터 7일입니다(기본 일요일~토요일).
- 적용되지 않는 것: 내보내기 파일(날짜 `YYYY-MM-DD`, 최근 수정 시각 `YYYY-MM-DD HH:mm` 고정), "3시간 전" 같은 상대 시각, 요일까지 쓰는 긴 날짜 표기(예: 휴무일 목록의 "2026년 10월 21일 수요일").

참고:

- 새로 설치한 DB의 값은 날짜 **기본**, 시간 **기본**, 주 시작 요일 **일요일**입니다(부록 A).
- 일정 계산(근무일·기간)에는 영향이 없습니다. 바꿔도 작업 날짜는 다시 계산되지 않습니다.
- 사용자 화면은 이 설정을 최대 5분 동안 다시 읽지 않습니다. 바꾼 직후 다른 사람의 열린 화면에는 새로 고칠 때까지 옛 형식이 남을 수 있습니다.
- 서버가 쓰는 날짜(메일, 활동 기록)는 저장한 앱 인스턴스에는 바로, 다른 인스턴스(웹만 도는 추가 인스턴스 등)에는 30초 안에 반영됩니다.
- API: 읽기 `GET /api/v1/settings/display`(로그인한 사용자, 로그인 전에는 401), 저장 `PUT /api/v1/admin/settings/display`(관리자만, 아니면 403 "관리자만 할 수 있습니다."). 잘못된 값은 422("날짜 형식을 고르세요.", "시간 형식을 고르세요.", "주 시작 요일을 고르세요.").
- 이 설정의 변경 이력은 남지 않습니다(10.4).

#### 9.11.4 시간 기록 활동 (1.6)

같은 화면 아래쪽 **시간 기록 활동** 절입니다. 안내 문구: "시간을 기록할 때 고르는 활동입니다. 기본 활동은 내 공수 입력표에서 쓰입니다. 끈 활동은 새 기록에 쓸 수 없고 지난 기록에는 남습니다."

- 새로 설치하거나 V17로 올리면 **개발**(기본), **설계**, **회의**, **테스트**, **문서**, **관리**, **기타** 7개가 있습니다.
- **추가**: **활동 이름**(1~60자, 같은 이름은 안 됨)을 넣고 **활동 추가**. 맨 뒤에 붙습니다.
- **기본으로**: 그 활동을 기본으로 정합니다(**기본** 표시). 기본은 하나뿐이라 앞의 기본은 풀립니다. **내 공수** 입력표로 입력한 시간과, 시간 탭에서 활동을 고르지 않은 기록이 기본 활동으로 들어갑니다.
- **끄기**·**켜기**: 끈 활동(**꺼짐** 표시)은 새 기록의 선택지에서 빠지고, 이미 그 활동으로 남긴 기록과 공수 보고서의 **활동별** 묶음에는 그대로 남습니다. **기본 활동은 끌 수 없습니다**("기본 활동은 끌 수 없습니다. 다른 활동을 기본으로 정한 뒤 끄세요."). 꺼진 활동은 기본으로 정할 수 없습니다.
- 삭제는 없습니다. 쓰지 않는 활동은 끕니다. 이름을 바꾸면 지난 기록에도 새 이름으로 보입니다(화면에는 이름 바꾸기가 없고 API `PATCH /api/v1/admin/time-activities/{id}`의 `name`으로만 됩니다).
- 활동은 인스턴스 전체에 하나의 목록입니다. 프로젝트마다 다른 활동을 쓰는 설정은 없습니다.

### 9.13 사내 SSO 공급자 등록

같은 화면(`/admin/authentication`)의 **사내 SSO (OpenID Connect)** 영역입니다. 회사 계정 시스템(Keycloak, Microsoft Entra ID, Google Workspace 등)으로 로그인하게 합니다. 공급자마다 로그인 화면에 "{버튼 이름}(으)로 로그인" 버튼이 하나씩 생깁니다. 이메일·비밀번호 로그인은 그대로 남습니다(끄는 설정은 없음). `.env`에 넣을 값은 없고, 공급자 정보는 DB에 저장됩니다.

#### 9.13.1 순서

1. 공급자 **식별자**를 정합니다. 예: `company`. 영문 소문자·숫자·하이픈 40자까지. 콜백 주소에 들어가며 만든 뒤에는 바꿀 수 없습니다.
2. IdP에 클라이언트(앱)를 등록합니다(9.13.2).
3. openPMS에서 **관리 → 로그인·비밀번호 → 사내 SSO (OpenID Connect) → SSO 공급자 추가**에 값을 넣고 **저장**합니다(9.13.3). 목록에 **콜백 주소**가 보입니다.
4. 로그아웃한 뒤 로그인 화면의 버튼으로 시험합니다. 먼저 기존 계정이 있는 사람으로 해 봅니다.

콜백 주소 = `OPENPMS_BASE_URL` + `/api/v1/auth/oidc/callback/{식별자}`. 예: `https://pms.example.co.kr/api/v1/auth/oidc/callback/company`. IdP에 등록한 값과 글자 하나까지 같아야 합니다. `OPENPMS_BASE_URL`을 바꾸면 IdP의 리디렉션 URI도 같이 바꿉니다.

#### 9.13.2 IdP에 등록할 것

| 항목 | 값 |
| --- | --- |
| 클라이언트 종류 | 비밀값이 있는(confidential) 웹 앱, 권한 코드 흐름 |
| 리디렉션 URI | 위의 콜백 주소 |
| 범위(scope) | `openid email profile` (openPMS 기본값). `openid`는 필수 |
| PKCE | openPMS는 항상 S256으로 보냅니다. IdP에서 필수로 켜도 됩니다 |
| 토큰에 담길 값 | `sub`, `email`, 이름(`name`, 없으면 `family_name`·`given_name`) |
| 로그아웃 주소 | 등록하지 않습니다(openPMS는 IdP 로그아웃을 부르지 않음) |

- `app` 컨테이너가 IdP의 발견 문서·토큰·키(JWKS)·userinfo 주소에 직접 닿아야 합니다. 사내 방화벽·DNS를 확인합니다.
- IdP가 사내 CA 인증서로 https를 쓰면 JRE가 그 CA를 믿어야 합니다. 지금 이미지에는 사내 CA를 넣는 단계가 없습니다.
- Keycloak: 발급자 `https://<호스트>/realms/<realm>`. Client authentication·Standard flow 켬, Valid redirect URIs에 콜백 주소, 시크릿은 Credentials 탭. 사용자의 Email verified가 꺼져 있으면 기존 계정에 연결되지 않습니다.
- Microsoft Entra ID: 발급자 `https://login.microsoftonline.com/<테넌트 ID>/v2.0`(`common`·`organizations`는 저장이 거부됨). 플랫폼 "웹", 클라이언트 암호를 시크릿 칸에. **클라이언트 암호에는 만료일이 있으므로** 만료 전에 새 암호로 바꿉니다. 엔터프라이즈 앱에서 사용자 할당을 필수로 하면 할당된 사람만 들어옵니다.

#### 9.13.3 openPMS에 넣을 것 ("SSO 공급자 추가" 대화상자)

| 칸 | 내용 |
| --- | --- |
| **버튼 이름** | 로그인 화면에 '…(으)로 로그인'으로 보입니다. 60자까지. 예: `사내 계정` |
| **식별자** | 9.13.1의 값. 처음 만들 때만 입력 |
| **발급자(Issuer) 주소** | 이 주소 뒤에 `/.well-known/openid-configuration`을 붙여 엔드포인트와 서명 키를 읽어 옵니다. 저장할 때 확인하며, 문서 안의 issuer가 입력값과 같아야 합니다(끝의 `/`까지) |
| **클라이언트 ID** | IdP에서 받은 값 |
| **클라이언트 시크릿** | IdP에서 받은 값. 저장한 뒤에는 화면·API에 다시 나오지 않습니다. 수정할 때 비워 두면 저장된 값을 그대로 씁니다 |
| **범위(scope)** | 공백으로 구분. openid는 꼭 들어가야 합니다 |
| **이메일 클레임** | 기본 `email` |
| **이름 클레임** | 기본 `name`. 없으면 성·이름(family_name, given_name), 그다음 이메일 앞부분 |
| **계정이 없으면 처음 로그인할 때 만들기** | 기본 꺼짐. 끄면 관리자가 미리 초대한 사람만 로그인합니다. 켜면 새 계정은 관리자가 아니고, 프로젝트 멤버로 추가해야 프로젝트가 보입니다 |
| **사용** | 끄면 로그인 버튼이 사라집니다. 연결 정보는 남습니다 |

- 목록 열: **버튼 이름**(꺼져 있으면 "꺼짐" 표시), **콜백 주소**, **계정 자동 생성**, **연결된 사람** 수. 등록된 공급자가 없으면 "등록된 SSO 공급자가 없습니다. 지금은 이메일과 비밀번호로만 로그인합니다."가 나옵니다.
- 수정: 행 메뉴 → **수정**("SSO 공급자 수정").
- 삭제: 행 메뉴 → **삭제** → "SSO 공급자 삭제 — '{이름}'을(를) 삭제합니다. 연결된 N명의 계정은 남지만, 비밀번호가 없는 사람은 비밀번호 재설정이나 다른 공급자로 로그인해야 합니다." 지우기 전에 해당 사람들에게 계정 설정에서 비밀번호를 만들어 두라고 안내하면 이메일·비밀번호로 계속 들어올 수 있습니다(9.13.5).

#### 9.13.4 누가 로그인되나

1. 이 공급자의 `sub`에 이미 연결된 계정.
2. 없으면 이메일이 같은 계정(대소문자 무시). 이때 연결을 만듭니다. 공급자가 `email_verified=false`를 보내면 거부합니다(`unverified`). 값이 없으면 확인된 것으로 봅니다.
3. 없고 계정 자동 생성이 켜져 있으면 새 계정.
4. 그 밖에는 거부합니다(`no_account`). 관리자가 먼저 초대해야 합니다.

- 한 번 연결되면 IdP에서 이메일이 바뀌어도 같은 계정으로 들어옵니다.
- 잠긴 계정(관리자 잠금, 로그인 실패 잠금 시간 중)은 거부합니다(`locked`). 초대 상태인 계정은 SSO로 로그인하면 활성이 됩니다.
- SSO 로그인도 폼 로그인과 같은 openPMS 세션을 쓰고, 유지 시간은 `OPENPMS_SESSION_TIMEOUT`입니다.

#### 9.13.5 운영 시 주의

- IdP에서 사람을 막아도 이미 열린 openPMS 세션은 끝날 때까지 남습니다. 즉시 내보내려면 openPMS에서도 **잠그기**(9.2.4)를 합니다.
- 이메일로 자동 연결하므로, 사용자가 자기 이메일을 직접 바꿀 수 있는 IdP는 등록하지 않습니다(다른 사람 계정에 연결될 위험).
- 자동 생성을 켜면 그 IdP에 로그인할 수 있는 모든 사람이 계정을 얻습니다. IdP에서 이 앱을 쓸 사람·그룹만 할당합니다.
- **SSO로만 들어온 사람의 비밀번호**(1.2): 자동 생성 계정은 비밀번호가 없습니다. 그 사람이 **계정 설정**을 열면 "비밀번호" 절에 "{공급자}(으)로 로그인하고 있어 비밀번호가 없습니다…" 안내와 **비밀번호 만들기 링크 받기** 버튼이 있습니다. 누르면 본인 이메일로 "[openPMS] 비밀번호 만들기" 메일이 가고, 링크(재설정과 같은 일회용 링크, 유효 시간은 **재설정 링크 유효 시간(분)**)에서 비밀번호를 정합니다. 그 뒤로는 이메일·비밀번호로도 로그인할 수 있습니다.
  - 링크가 본인 메일로만 가므로, 남의 열린 세션을 빌린 사람이 비밀번호를 더할 수 없습니다. 관리자가 대신 만들어 주는 기능은 없습니다.
  - 이미 비밀번호가 있으면 "이미 비밀번호가 있습니다."가 나옵니다. 같은 사람은 1분에 3번까지 요청할 수 있습니다.
  - 비밀번호와 SSO 연결이 둘 다 있는 사람은 비밀번호 절 안내에 "사내 계정({공급자})으로도 로그인할 수 있습니다."가 붙습니다.

#### 9.13.6 오류 코드

실패하면 브라우저가 `/login?sso_error=<코드>`로 돌아오고 로그인 화면이 이유를 보여 줍니다.

| 코드 | 화면 안내 | 확인할 것 |
| --- | --- | --- |
| `no_account` | openPMS 계정이 없습니다. 관리자에게 초대를 요청하세요. | 그 이메일로 초대하거나 자동 생성을 켬. IdP 이메일과 openPMS 이메일이 같은지 |
| `locked` | 잠긴 계정입니다. 관리자에게 잠금 해제를 요청하세요. | 9.2.4 |
| `unverified` | 로그인 공급자가 이메일 주소를 확인되지 않은 주소로 알려 왔습니다. | IdP에서 그 사용자의 이메일을 확인 처리 |
| `no_email` | 로그인 공급자가 이메일 주소를 보내지 않았습니다. | 범위에 `email`, 이메일 클레임 이름, IdP 사용자의 메일 주소 |
| `cancelled` | 로그인을 취소했거나 공급자가 허용하지 않았습니다. | IdP의 사용자·그룹 할당, 동의 설정 |
| `unavailable` | 지금은 이 방법으로 로그인할 수 없습니다. | **사용** 여부, `app` 컨테이너에서 IdP로 가는 네트워크·DNS·TLS 인증서 |
| `failed` | 로그인 공급자와 확인하지 못했습니다. 다시 시도하세요. | 시크릿(틀림·만료), `OPENPMS_BASE_URL`이 사용자가 여는 주소와 같은지, 서버 시계, 로그의 `SSO sign-in failed` |

- IdP 화면에 `redirect_uri` 오류가 나오면 IdP에 등록한 리디렉션 URI와 openPMS 목록의 **콜백 주소**를 글자 단위로 비교합니다.
- 저장할 때 발급자 칸에 오류가 나면 발급자 주소 오타, 끝의 `/`, 서버에서 IdP로 나가는 네트워크를 봅니다.

### 9.14 프로젝트 템플릿·복사와 상위 프로젝트

관리 메뉴가 아니라 각 프로젝트의 **프로젝트 설정** → 정보 화면과 **새 프로젝트** 화면에서 합니다. 프로젝트 설정을 바꾸려면 그 프로젝트의 **프로젝트 정보·상태 수정** 권한(`project.edit`, 기본: 프로젝트 관리자)이 있어야 하고, 새 프로젝트를 만들려면 관리자이거나 전역 권한 **프로젝트 만들기**(9.2.6)가 있어야 합니다.

#### 9.14.1 템플릿 프로젝트 만들기

1. 템플릿으로 쓸 프로젝트(예: "표준 프로젝트 양식")를 만들고 모듈, 사용 유형, 사용자 정의 필드, 멤버, 버전, 카테고리, 기본 작업, 보드, 공개 보기를 갖춰 둡니다.
2. 그 프로젝트의 **프로젝트 설정** → **템플릿으로 쓰기**를 체크하고 **저장**합니다.
3. 이제 그 프로젝트를 볼 수 있는 사람의 **새 프로젝트** 화면에 **템플릿에서 시작**이 켜지고, 템플릿 목록에 이 프로젝트가 나옵니다. 템플릿이 하나도 없으면 "아직 템플릿이 없습니다. 프로젝트 설정에서 '템플릿으로 쓰기'를 켜면 여기에 나옵니다."가 보입니다.

- 템플릿은 보통 프로젝트와 똑같이 동작합니다(작업을 만들고 바꿀 수 있음). 실수로 바뀌지 않게 템플릿 프로젝트의 멤버는 관리 담당자로 좁히는 것을 권합니다.
- 보관한 템플릿은 목록에 나오지 않습니다. 쓰지 않을 템플릿은 **템플릿으로 쓰기**를 풀거나 보관합니다.
- 템플릿 목록에는 만드는 사람이 볼 수 있는 템플릿만 나옵니다. 모두가 쓰게 하려면 템플릿을 공개 프로젝트로 두거나, 쓸 사람(그룹)을 멤버로 넣습니다.

#### 9.14.2 템플릿에서 프로젝트 만들기 (사용자 안내용)

1. **새 프로젝트** → **템플릿에서 시작** → **템플릿**을 고릅니다.
2. **함께 복사할 것**에서 고릅니다(처음엔 모두 체크): **멤버와 역할**, **버전**, **카테고리**, **작업(계층·관계 포함)**, **보드**, **공개 보기**.
3. 이름·식별자를 넣고 **만들기**. 설명을 비워 두면 템플릿의 설명을 씁니다.

| 항상 복사 | 고르면 복사 | 복사하지 않음 |
| --- | --- | --- |
| 켜진 모듈, 작업 유형, 사용자 정의 필드 사용 설정, 프로젝트 특성 값, 설명(비워 둔 경우) | 멤버와 역할, 버전, 카테고리, 작업(상위-하위와 작업끼리의 관계 유지), 보드(하위 프로젝트별 보드 제외), 공개 보기 | 첨부 파일, 코멘트·활동 기록, 주시자, 작업 공유, 하위 프로젝트 |

- 만든 사람은 새 프로젝트의 프로젝트 관리자가 됩니다.
- 복사한 작업에는 "만듦" 기록 하나만 남고, **누구에게도 알림이 가지 않습니다**(담당자에게도). 작업의 작성자는 만든 사람입니다. 1.5부터 웹훅에는 복사한 작업마다 **작업 생성** 이벤트가 갑니다(9.15.2).
- 멤버를 복사하지 않으면 새 프로젝트 멤버가 아닌 담당자·책임자는 비워지고, 그런 사람의 담당자 보드 열도 빠집니다. 복사한 버전·카테고리는 보기·보드의 필터에서도 새 프로젝트의 것을 가리킵니다.
- 복사는 만들기 요청 안에서 한 번에 처리합니다. 중간에 실패하면 프로젝트도 만들어지지 않습니다. 작업이 아주 많은(수천 건) 템플릿은 만들기가 오래 걸릴 수 있습니다(재 보지 않음).
- 화면 문구는 "공개 보기"이지만, 만드는 사람이 템플릿에 저장해 둔 비공개 보기도 그 사람의 비공개 보기로 함께 복사됩니다.

#### 9.14.3 상위 프로젝트 (하위 프로젝트 만들기·옮기기)

- **새 프로젝트**와 **프로젝트 설정**의 **상위 프로젝트**에서 고릅니다. **없음(최상위 프로젝트)**을 고르면 최상위가 됩니다.
- 고를 수 있는 것은 내가 **수정**할 수 있는 프로젝트뿐이고, 그 프로젝트 자신과 그 아래 하위 프로젝트는 나오지 않습니다(순환 방지. 서버도 같은 검사를 하고 어기면 "자기 자신이나 하위 프로젝트를 상위로 정할 수 없습니다.").
- 프로젝트를 다른 상위 아래로 옮기면 상위 프로젝트 목록·"하위 프로젝트 포함" 보기·하위 프로젝트별 보드에 나오는 위치가 바뀝니다. 멤버와 권한은 프로젝트마다 따로이므로 옮겨도 바뀌지 않습니다.
- 하위 프로젝트가 있는 프로젝트는 삭제할 수 없습니다(먼저 하위를 옮기거나 지움).

#### 9.14.4 프로젝트 복사 (1.4)

템플릿으로 표시하지 않은 프로젝트도 그대로 복사해 새 프로젝트를 만들 수 있습니다.

1. 원본 프로젝트의 **프로젝트 설정** → 정보 → **프로젝트 복사**.
2. "{프로젝트} 복사" 대화상자에서 **프로젝트 이름**(기본 "{이름} (사본)"), **식별자**(기본 `<원본>-copy`), 복사할 항목을 고릅니다.
3. **복사해서 만들기**. 새 프로젝트의 개요로 이동합니다.

- 필요한 권한: 원본 프로젝트의 **프로젝트 정보·상태 수정**(`project.edit`)과 **프로젝트 만들기**(관리자 또는 전역 권한, 9.2.6). 둘 중 하나라도 없으면 403입니다.
- 복사 규칙은 템플릿에서 만들기(9.14.2 표)와 같습니다. 개요 위젯 구성과 내부 코멘트 켜기 설정도 함께 가져갑니다. 복사한 작업에는 알림도 웹훅도 가지 않습니다.
- 새 프로젝트는 템플릿이 아니고(**템플릿으로 쓰기** 꺼짐), 만든 사람이 프로젝트 관리자가 됩니다.

#### 9.14.5 프로젝트 개요 위젯 (1.4)

프로젝트 개요(`/projects/{식별자}`)는 위젯 대시보드입니다: **설명**, **작업 현황**, **프로젝트 상태**, **멤버**, **버전 진행**, **곧 완료일(14일 안)**, **최근 바뀐 작업(7일)**, **내게 할당된 작업**.

- 프로젝트 수정 권한(`project.edit`)이 있는 사람에게 **위젯 편집**이 보입니다. 보일 위젯을 켜고 끄고 순서를 정하면 바로 저장되고("저장됨"), 그 프로젝트를 보는 **모든 사람에게 같은 개요**가 보입니다. 개인별 구성은 없습니다.
- 새 프로젝트와 1.3에서 올린 프로젝트의 기본은 설명·작업 현황·프로젝트 상태·멤버입니다.
- 템플릿·복사로 만든 프로젝트는 원본의 위젯 구성을 가져갑니다.

### 9.15 API 토큰과 웹훅 (`/admin/integrations`)

1.4에서 생긴 관리 묶음 **연동** → **API와 웹훅** 화면입니다. 관리자만 엽니다. 위쪽이 API 토큰, 아래쪽이 웹훅입니다.

#### 9.15.1 API 토큰

사내 시스템(배포 봇, 보고 도구 등)이 openPMS API를 부를 때 쓰는 개인 토큰입니다. **토큰은 만든 사람의 권한으로 동작**합니다. 관리자가 만든 읽기·쓰기 토큰은 관리자 권한을 가집니다.

관리자가 하는 일:

| 칸·버튼 | 설명 |
| --- | --- |
| **API 토큰 쓰기** | 기본 켬. 끄면 새 토큰을 만들 수 없고, **있는 토큰도 모두 바로 거절**됩니다(401). 다시 켜면 폐기하지 않은 토큰은 다시 동작합니다. 연동을 쓰지 않는 회사는 끕니다 |
| 토큰 목록 | 모든 사람의 쓰는 중인 토큰: 이름, **만든 사람**, 권한 범위, **최근 사용**, 만료. 토큰 값은 관리자에게도 보이지 않습니다. 없으면 "아직 아무도 토큰을 만들지 않았습니다." |
| **폐기** | 그 토큰을 바로 못 쓰게 합니다(되돌릴 수 없음). 그 토큰을 쓰던 연동은 401을 받습니다. 폐기·만료된 토큰 행은 30일 뒤 예약 작업(`token-cleanup`, 매일 03:30)이 지웁니다 |

사람이 토큰을 만드는 법(사용자 안내용): 계정 설정 → **API 토큰** → **토큰 만들기**.

| 칸 | 설명 |
| --- | --- |
| **토큰 이름** | 1~60자. 어디에 쓰는지 알아볼 수 있게(예: 배포 알림 봇) |
| **권한 범위** | **읽기 전용**(조회만: GET, 목록 조회, 내보내기) 또는 **읽기·쓰기**(내 권한 안에서 만들고 고침) |
| **만료** | 30일 뒤, 90일 뒤, 365일 뒤, **만료 없음** |

- **만들기**를 누르면 "토큰을 만들었습니다" 대화상자에 토큰 값(`opms_…`)이 **한 번만** 보입니다. 잃어버리면 새로 만들어야 합니다. DB에는 SHA-256 해시만 저장합니다.
- 한 사람이 폐기하지 않은 토큰을 20개까지 가질 수 있습니다.
- 사용법: 요청 헤더에 `Authorization: Bearer <토큰>`. 세션 쿠키와 CSRF 토큰이 필요 없습니다. 경로는 화면과 같은 `/api/v1/...`입니다.
- 토큰으로 부를 수 없는 경로: 로그인·로그아웃 등 `/api/v1/auth/**`(현재 사용자 `/api/v1/auth/me`는 됨), 비밀번호, 토큰 관리(`/api/v1/me/api-tokens`, `/api/v1/admin/api-tokens`), 연동 설정(**API 토큰 쓰기** `/api/v1/admin/settings/api`, 웹훅 `/api/v1/admin/webhooks`·`/api/v1/admin/webhook-deliveries`). 관리자의 토큰도 마찬가지입니다. 토큰이 새도 비밀번호를 바꾸거나 토큰을 더 만들거나 웹훅을 바꿀 수 없게 하기 위함입니다.
- 토큰마다 1분에 300회까지입니다(넘으면 429).
- 토큰 주인을 잠그거나 삭제하면 그 사람의 토큰도 바로 거절됩니다. 퇴사자 처리(9.2.4·9.2.5)가 곧 토큰 정지입니다. 연동이 특정 사람에게 묶이므로, 퇴사·휴직 전에 연동 담당자를 바꿔 새 토큰을 만들게 합니다(서비스 계정 기능은 없음).
- API 설명: 도움말 메뉴 → **API 문서**(`/help/api`: 인증, 규칙, 오류, 주요 경로)와 OpenAPI 3.1 문서 `/api/v1/openapi.json`(로그인 없이 열림, 주요 경로만).
- 버전 정책: `/api/v1` 안에서는 응답 필드를 더하기만 합니다. 필드를 빼거나 뜻을 바꾸는 변경은 `/api/v2`로 냅니다. 연동 개발자는 모르는 필드를 무시하도록 만듭니다.

#### 9.15.2 웹훅

작업이 생기거나 바뀌거나 지워지거나 코멘트가 달리면 다른 시스템의 주소로 JSON을 보냅니다. 1.5부터 자동 일정으로 날짜가 밀린 작업, 첨부 추가·삭제, 템플릿·프로젝트 복사로 생긴 작업도 보냅니다.

웹훅 추가: **웹훅 추가** → 칸을 채우고 **저장**.

| 칸 | 설명 |
| --- | --- |
| **이름** | 1~100자 |
| **받는 주소** | `http://` 또는 `https://` 주소. 리다이렉트는 따라가지 않으므로 최종 주소를 넣습니다. 클라우드 메타데이터 주소(169.254.x, `[fe80:…]`, metadata.google.internal, 1.5부터 그 주소로 풀리는 이름도)는 "이 주소로는 보낼 수 없습니다."로 거절됩니다. `OPENPMS_WEBHOOK_BLOCK_PRIVATE=true`면 사설·루프백 주소도 "사내망·루프백 주소로는 보낼 수 없습니다(운영 설정에서 막혀 있음)."로 거절됩니다(1.5) |
| **보낼 이벤트** | **작업 생성**, **작업 변경**(바뀐 항목과 이전·이후 값 포함), **작업 삭제**, **코멘트**. 처음엔 모두 체크 |
| **프로젝트** | 고르지 않으면 모든 프로젝트의 이벤트를 보냅니다 |
| **켜기** | 끄면 새 이벤트를 쌓지 않습니다 |

- 저장하면 "서명 키" 대화상자에 서명 키(`whsec_…`)가 **한 번만** 보입니다. 받는 쪽에 저장해 둡니다. 목록에는 끝 네 글자만 보입니다. 행 메뉴 **서명 키 새로 만들기**로 바꾸면 옛 키는 바로 쓸 수 없습니다(받는 쪽도 같이 바꿈).
- 받는 쪽 확인 방법: 요청 본문을 서명 키로 HMAC-SHA256 한 hex 값이 `X-OpenPMS-Signature` 헤더(`sha256=…`)와 같은지 봅니다. 그 밖의 헤더: `X-OpenPMS-Event`(이벤트 이름), `X-OpenPMS-Delivery`(전송 id, 중복 처리용).
- **테스트 전송**: `ping` 이벤트를 바로 한 번 보냅니다. "테스트 전송이 받아들여졌습니다 (HTTP 200)" 또는 "테스트 전송이 실패했습니다".
- **최근 전송 기록**: 웹훅마다 최근 30건(이벤트, 상태 **성공**·**실패**·**다시 보낼 예정**과 다음 시각, 시도 횟수, 응답 코드나 오류). 실패한 전송은 **다시 보내기**로 바로 한 번 더 보냅니다.
- 보내는 방식: 예약 작업이 15초마다 보냅니다(`OPENPMS_JOBS_ENABLED=true`인 인스턴스에서만). 연결 5초·응답 10초 안에 2xx가 오면 성공입니다. 실패하면 1분, 5분, 30분, 120분 뒤 다시 보내고 그래도 안 되면 **실패**로 남깁니다. 테스트 전송과 다시 보내기는 한 번만 시도합니다.
- 이벤트는 그 변경이 저장(커밋)될 때만 생깁니다. 저장이 실패한 변경은 보내지 않습니다.
- **내부 코멘트는 보내지 않습니다**(9.4.6).
- 작업을 다른 프로젝트로 옮기면(하위 프로젝트별 보드에서 카드를 옮긴 경우 포함) **작업 변경** 이벤트로 보냅니다(바뀐 항목에 프로젝트).
- 1.5부터: 선행 작업이나 근무일 변경으로 날짜가 자동으로 밀린 작업마다 **작업 변경**(바뀐 항목에 시작일·완료일), 첨부를 올리거나 지우면 **작업 변경**(바뀐 항목 "첨부 파일"), 템플릿·프로젝트 복사로 생긴 작업마다 **작업 생성**을 보냅니다. 근무일·휴무일을 바꾸면 밀린 작업 수만큼 전송이 생기므로 받는 쪽이 감당할 수 있는지 미리 알립니다.
- 1.5부터 **작업 변경**의 바뀐 항목은 그 요청이 바꾼 것만 담습니다(같은 사람이 5분 안에 연달아 바꾼 기록이 활동 탭에서는 하나로 합쳐져도, 웹훅은 요청마다 그 요청의 변경만).
- 웹훅을 삭제하면 보내지 못한 이벤트와 전송 기록도 함께 지워집니다("보내지 못한 이벤트와 전송 기록도 함께 지워집니다.").
- 네트워크: `app` 컨테이너가 받는 주소에 직접 닿아야 합니다(2.1). https 주소가 사내 CA 인증서를 쓰면 JRE가 그 CA를 믿어야 하는데, 지금 이미지에는 사내 CA를 넣는 단계가 없습니다.
- 보안: 앱은 클라우드 메타데이터 주소(169.254.x, `[fe80:…]`, metadata.google.internal)를 늘 막습니다. 그 밖의 사설·내부 주소(예: `127.0.0.1`, 사내 서버)는 **기본으로는** 넣을 수 있습니다. 관리자만 등록할 수 있지만, 사내 내부 서비스로 요청을 보내는 통로가 될 수 있으므로 받는 주소를 정기적으로 점검하고(10.7), 가능하면 `app` 컨테이너의 나가는 방화벽을 허용 목록으로 둡니다.

**사설 주소 막기 스위치(1.5).** 받는 시스템이 모두 공인·DMZ 주소라면 `.env`에 아래를 넣고 다시 띄웁니다.

```bash
# .env
OPENPMS_WEBHOOK_BLOCK_PRIVATE=true
```

```bash
docker compose up -d
```

- 켜면 루프백(127.x, ::1), 사설(10.x, 172.16–31.x, 192.168.x), 통신사 NAT(100.64.0.0/10), IPv6 사설(fc00::/7), 0.0.0.0 주소를 막습니다. 이름으로 넣은 주소는 그 이름이 풀리는 주소로 판단합니다.
- 새로 등록하거나 주소를 고칠 때 422로 거절되고, **이미 등록된 웹훅도 보낼 때마다 다시 검사**해 막힌 주소면 보내지 않고 전송 기록에 "보내지 않음: …"을 남깁니다(재시도 규칙은 같아서 다섯 번째 뒤 **실패**). 켜기 전에 웹훅 목록의 받는 주소를 확인합니다.
- 받는 사내 시스템이 사설 주소에 있으면 켤 수 없습니다. 이때는 방화벽 egress 허용 목록이 방어선입니다.

**전송 기록 보관.** 성공·실패로 끝난 전송 기록(`webhook_deliveries`)은 만든 지 30일이 지나면 예약 작업 `token-cleanup`(매일 03:30, `OPENPMS_JOBS_ENABLED=true`인 인스턴스)이 지웁니다. 다시 보낼 예정인 전송은 끝날 때까지 남습니다. 30일보다 오래 남겨야 하면 받는 쪽에 보관합니다. 따로 정리할 일은 없습니다.

#### 9.15.3 만들기 요청의 재시도 (`Idempotency-Key`, 1.5)

관리 화면은 없습니다. 운영자가 알아 둘 동작입니다.

- 무언가를 만드는 POST 요청에 `Idempotency-Key: <요청마다 새 임의 값>` 헤더가 있으면, 같은 사람이 같은 키로 다시 보낸 요청은 다시 실행하지 않고 처음 응답을 그대로 돌려줍니다(응답 헤더 `Idempotent-Replayed: true`). 네트워크가 끊겨 응답만 못 받은 경우 작업·코멘트가 두 번 생기지 않게 합니다.
- 화면은 프로젝트 만들기·복사, 작업 만들기·복사, 코멘트에 자동으로 키를 붙이고, 연결이 끊기면 같은 키로 한 번 더 보냅니다. 사내 연동(API 토큰)에도 만드는 요청에는 키를 붙이라고 안내합니다(`/api/v1/openapi.json`의 설명과 화면 **API 문서**(`/help/api`)의 규칙 목록에 안내가 있습니다).
- 같은 키를 다른 내용에 쓰면 422, 처음 요청이 아직 처리 중이면 409입니다(8장). 실패한 요청(2xx가 아닌 응답)은 기억하지 않으므로 고쳐서 같은 키로 다시 보내도 됩니다.
- **보관**: 처음 성공 응답을 DB `idempotency_keys`에 24시간 둡니다(1MB 넘는 응답과 첨부 업로드는 대상이 아님). 하루 지난 행은 예약 작업 `token-cleanup`(매일 03:30, `OPENPMS_JOBS_ENABLED=true`인 인스턴스)이 지웁니다. 사람이 하루에 만드는 것만큼만 쌓이므로 따로 정리할 일은 없습니다. 보관 시간을 바꾸는 설정은 없습니다.
- 응답 본문(만든 작업·코멘트 내용)이 하루 동안 DB에 남으므로 DB 덤프를 비밀값처럼 다루는 원칙(5.3)에 포함됩니다.
- 리버스 프록시가 `Idempotency-Key`·`Idempotent-Replayed` 헤더를 지우지 않게 둡니다(nginx 기본값은 넘김).

### 9.16 시간 기록 (1.6)

사람이 작업에 쓴 시간(공수)을 기록하고 모아 보는 기능입니다. 사용자 쪽 화면은 전역 메뉴 **내 공수**(한 주를 작업 × 요일 칸으로 입력, Ctrl+S 저장), 작업 상세 **시간** 탭(기록마다 날짜·시간·활동·메모), 프로젝트 메뉴 **공수 보고서**(사람별·작업별·활동별·날짜별 합계와 **Excel로 내려받기**)입니다. 사용자용 절차는 「07-사용자매뉴얼」에 있습니다. 비용·단가·예산은 없습니다.

#### 9.16.1 프로젝트별 켜기·끄기 (모듈)

- 프로젝트 → **프로젝트 설정** → **모듈** → **시간 기록**("작업에 쓴 시간을 기록하고 공수 보고서로 모아 봅니다."). **모듈 켜기·끄기** 권한(기본: 프로젝트 관리자)이 필요합니다.
- 새 프로젝트는 켜진 채로 만들어집니다. V17로 올린 인스턴스는 모든 기존 프로젝트에서 켜집니다.
- 끄면 그 프로젝트에서 시간 기록 권한이 모두 빠집니다: **공수 보고서** 메뉴와 **시간** 탭이 사라지고, 그 프로젝트 작업에는 시간을 기록할 수 없으며(**내 공수**의 그 행은 잠김), 그 프로젝트의 기록은 목록·보고서·Excel에 나오지 않습니다. **기록은 지워지지 않고**, 다시 켜면 그대로 보입니다.

#### 9.16.2 권한

역할 편집(9.4.2)의 권한 묶음 **시간 기록**입니다.

| 권한 (화면 이름) | 할 수 있는 일 | 기본 역할 |
| --- | --- | --- |
| **내 시간 기록** (`time.log`) | 자기 시간을 기록하고 고치고 지움(**내 공수**, 시간 탭), 자기 기록 보기 | 프로젝트 관리자, 멤버 |
| **시간 기록 보기** (`time.view`) | 그 프로젝트의 모든 사람의 기록 보기, **공수 보고서**와 Excel | 프로젝트 관리자, 멤버 |
| **시간 기록 관리(다른 사람 것 포함)** (`time.manage`) | 다른 사람의 기록 고치기·지우기, 다른 사람 몫으로 기록(API의 `userId`. 화면은 없음) | 프로젝트 관리자 |

- 권한은 **작업이 있는 프로젝트** 기준입니다. 작업을 다른 프로젝트로 옮기면 그 작업의 기록도 새 프로젝트의 것이 됩니다.
- 참관자·비멤버에게는 기본으로 시간 기록 권한이 없습니다. 참관자가 **내 공수**에 작업을 넣고 저장하면 "이 작업에 시간을 기록할 권한이 없습니다."가 나옵니다.
- 멤버도 기본으로 **시간 기록 보기**가 있어 같은 프로젝트 동료의 공수를 봅니다. 남의 공수를 팀장만 보게 하려면 멤버 역할에서 **시간 기록 보기**를 빼고 팀장용 역할에 줍니다. **공수 보고서**는 볼 수 있는 기록만 셉니다(보기 권한이 없으면 메뉴도 없음).
- 관리자는 모든 프로젝트의 모든 권한을 가지므로 모든 기록을 보고 고칩니다.

#### 9.16.3 규칙과 한도

- 한 기록의 시간은 0보다 크고 24 이하, 소수 둘째 자리까지입니다(입력 화면은 "1:30" = 1.5, "1,5"도 받음). **한 사람의 하루 합계는 24시간까지**입니다("하루에 24시간을 넘게 기록할 수 없습니다.").
- **하루 근무 시간**(9.11.1)을 넘는 것은 막지 않습니다. **내 공수**가 그날 합계를 빨간 글자와 경고 아이콘으로 알릴 뿐입니다.
- **내 공수**는 자기 시간만 입력합니다. 같은 날 같은 작업에 기록이 여러 건이면 그 칸은 입력표에서 바꿀 수 없고 작업의 **시간** 탭에서 고칩니다. 입력표의 저장은 전부 되거나 전부 안 됩니다.
- **공수 보고서**·Excel은 한 번에 1년(366일 미만)까지입니다. 보고서 합계는 볼 수 있는 기록 전부를 DB에서 묶어 세므로 건수 한도가 없습니다(6d816e4). Excel은 50,000행까지입니다(넘는 행은 알림 없이 빠지므로 기간을 나눕니다). 기록 목록 API(작업의 **시간** 탭)는 2,000행까지입니다.
- 지난 주를 잠그거나 승인하는 기능은 없습니다. 권한이 있는 사람은 지난 기록도 고칠 수 있습니다.
- 시간 기록은 작업의 활동 기록(저널)에 남지 않고, 알림·웹훅도 없습니다. 프로젝트 복사·템플릿은 시간 기록을 가져가지 않습니다.
- 작업이나 프로젝트를 삭제하면 그 시간 기록도 함께 지워지고 지난 기간의 공수 보고서 합계가 줄어듭니다(되돌릴 수 없음). 작업 삭제 확인은 기록된 시간을 경고하지만(39c8974: "이 작업에 기록된 시간 {n}시간도 함께 지워지고 공수 보고서에서 빠집니다.", 삭제하는 사람이 볼 수 있는 기록만 셈), 프로젝트 삭제 확인은 시간 기록을 따로 말하지 않습니다. 프로젝트를 지우기 전에 **공수 보고서**에서 Excel을 받아 두세요.

#### 9.16.4 다른 시스템으로 가져가기

- 화면: **공수 보고서** → 기간·묶기 → **Excel로 내려받기**(시트 "공수": 날짜, 사람, 프로젝트, 번호, 작업, 활동, 시간, 메모, 마지막 줄 합계. 파일 이름 "공수 {시작}~{끝}.xlsx").
- API(사내 근태·정산 시스템): 읽기 전용 API 토큰(9.15.1)으로 `GET /api/v1/time-entries?from=&to=&project=`(기록 목록, 2,000행까지), `GET /api/v1/time-entries/report?groupBy=user`(합계, 건수 한도 없음), `GET /api/v1/time-entries/export`(Excel, 50,000행까지)를 부릅니다. 토큰 주인이 볼 수 있는 기록만 나오므로, 모든 사람의 공수가 필요하면 연동 전용 계정에 필요한 프로젝트의 **시간 기록 보기**를 주고 그 계정으로 토큰을 만듭니다. 기록하거나 입력표를 저장하는 연동은 읽기·쓰기 토큰이 필요합니다.

| API 토큰(1.4) | 만든 사람의 연동 시스템. DB `api_tokens.token_hash`에는 SHA-256만 | 원문은 만들 때 한 번만 보이고 서버에 남지 않습니다. 샜다고 의심되면 주인이나 관리자가 **폐기**(9.15.1). 모두 막으려면 **API 토큰 쓰기**를 끔 |
| `Idempotency-Key` 응답(1.5) | DB `idempotency_keys.body`(24시간) | 비밀값은 아니지만 만든 작업·코멘트 내용이 하루 동안 남습니다. DB 덤프와 같이 보호합니다 |
| 웹훅 서명 키(1.4) | DB `webhooks.secret`, 받는 쪽 시스템 | **평문으로 저장됩니다**(서명하려면 원문이 필요). 화면·API에는 만들 때만 보이고 그 뒤 끝 네 글자만. DB 덤프에 들어갑니다. 샜다고 의심되면 **서명 키 새로 만들기**(9.15.2)로 바꾸고 받는 쪽도 바꿉니다 |
| 첫 관리자 설정 링크 | 앱 로그(1회) | 24시간 유효. 로그 접근 제한 |
| `frontend/.env.production` | 저장소 | 비밀값이 아님(`VITE_API=http` 하나) |

- 기본 비밀번호는 없습니다. 개발용 시드 계정은 개발 프로필에만 있고 운영 이미지에는 없습니다.
- 시크릿이 샜다고 의심되면: SSO는 IdP에서 새 시크릿을 만들어 수정 대화상자에 넣고 옛 시크릿을 IdP에서 지웁니다. DB 비밀번호는 8장의 비밀번호 변경 절차를 따릅니다.
- 백업 파일은 `.env`와 같은 수준으로 보호합니다(5.3).

### 10.2 세션

- 세션은 DB(Spring Session JDBC)에 저장되고, 쿠키 `OPENPMS_SESSION`은 HttpOnly, SameSite=Lax, 기본 Secure입니다.
- 유지 시간은 `OPENPMS_SESSION_TIMEOUT`(기본 `8h`)입니다.
- 세션이 끝나는 경우: 유지 시간 경과, 로그아웃, 관리자가 **잠그기**·**삭제**(그 사람의 모든 세션 종료), 비밀번호 재설정(모든 기기 로그아웃).
- 모든 쓰기 요청에는 CSRF 토큰이 필요합니다(없으면 403). 예외: `Authorization: Bearer` API 토큰 요청은 세션을 쓰지 않으므로 CSRF 토큰이 필요 없습니다(9.15.1).

### 10.3 계정 잠금

- 자동: 9.12.2의 실패 횟수에 이르면 잠금 시간 동안 로그인 거부(HTTP 423, SSO는 `locked`). 사용자 목록에 **일시 잠김**으로 보이고 행 메뉴 **잠금 해제**로 바로 풉니다(9.2.4).
- 수동: 9.2.4의 **잠그기**. 퇴사자·장기 부재자·도용 의심 계정은 바로 잠급니다.
- 관리자 계정은 2명 이상 유지하고, 마지막 관리자는 잠글 수 없음을 기억합니다.

### 10.4 감사 (저널)

- 작업 패키지의 모든 변경은 저널(활동 기록)에 남습니다: 누가, 언제, 어떤 필드를 무엇에서 무엇으로 바꿨는지, 코멘트. 작업 상세의 활동 탭에서 봅니다.
- 같은 사람이 같은 작업을 5분 안에 연속으로 바꾸면(그 사이 다른 사람의 기록이 없을 때) 한 기록으로 합쳐집니다.
- 작업 이동(다른 프로젝트), 근무일·휴무일 변경에 따른 일정 재계산도 바뀐 작업마다 기록이 남습니다.
- 사용자를 삭제해도 저널과 작성자 기록은 남고 이름만 "삭제된 사용자"로 바뀝니다.
- 한계(현재 버전):
  - 진행률 설정 변경에 따른 재계산은 활동 기록을 남기지 않습니다.
  - 빈 보드에 작업을 넣고·옮기고·빼는 것, 보드 필터 저장은 작업 패키지를 바꾸지 않으므로 활동 기록이 없습니다. 상태별·담당자별·버전별 보드에서 카드를 옮겨 바뀐 상태·담당자·버전은 작업의 활동 기록에 남습니다.
  - 관리 설정(유형·상태·워크플로·역할·사용자·로그인 정책·SSO 공급자·날짜 형식 등)의 변경 이력을 남기는 별도 감사 로그는 없습니다. 관리 변경은 변경 요청서 등 사내 절차로 기록하는 것을 권합니다.
  - 로그인 성공 시각은 사용자 목록의 **최근 로그인**으로만 볼 수 있습니다. SSO 거부·실패는 앱 로그에 남습니다(7.2).
  - API 토큰으로 한 변경은 저널에 토큰 주인의 이름으로 남고, 화면에서 했는지 토큰으로 했는지는 구분되지 않습니다. 토큰 사용 흔적은 토큰 목록의 **최근 사용**(최대 1분 단위)뿐이고 요청별 기록은 없습니다(1.4).
  - API 토큰 켜기·끄기·폐기, 웹훅 추가·수정·삭제·서명 키 변경도 별도 감사 로그가 없습니다. 웹훅으로 보낸 것은 웹훅마다 전송 기록(9.15.2)으로 봅니다.
  - 내부 코멘트(9.4.6)도 저널에 남지만 보기 권한이 있는 역할만 활동 탭에서 봅니다.
  - 시간 기록(9.16)의 추가·수정·삭제는 저널에 남지 않습니다. 기록에는 마지막 수정 시각만 있고 누가 고쳤는지는 남지 않습니다(관리 권한으로 남의 기록을 고친 경우 포함). 시간 기록 활동의 변경도 이력이 없습니다(1.6).

### 10.5 로그인 요청 제한과 리버스 프록시

- 로그인은 같은 클라이언트 주소에서 1분에 20회, 비밀번호 재설정 요청은 1분에 5회로 제한합니다. 비밀번호 변경은 사람마다 1분에 10회, 비밀번호 만들기 링크는 1분에 3회입니다.
- 1.2부터 앱은 믿는 프록시(`OPENPMS_TRUSTED_PROXIES`, 기본: 이 호스트, Docker 브리지, Podman 네트워크)가 보낸 `X-Forwarded-For`에서 클라이언트 주소를 꺼냅니다. 그래서 프록시 뒤에서도 사람마다 따로 셉니다. 1.1까지는 이 처리가 없어 프록시 뒤의 모든 사람이 한도 하나를 같이 썼습니다.
- 조건: 프록시가 `X-Forwarded-For`·`X-Forwarded-Proto`를 보내고, 프록시가 들어오는 주소가 `OPENPMS_TRUSTED_PROXIES`에 맞아야 합니다(3.4). 하나라도 빠지면 1.1과 같이 한도를 같이 씁니다.
- 사용자가 `X-Forwarded-For`에 가짜 주소를 앞에 붙여 보내도, 앱은 프록시가 붙인 실제 주소를 씁니다.
- **배포 때 확인**: 운영 이미지(90006c2, rootless Podman)로는 2026-10-11에 게시 포트를 거쳐 시험했습니다(주소 29개는 429 없음, 주소 하나는 21번째에 429, 가짜 주소를 앞에 붙여도 429 유지). 이 시험에서 Podman 네트워크가 기본값에 없어 헤더가 무시되던 것을 찾아 고쳤습니다. 실제 사내 프록시로는 아직 시험하지 않았습니다. 설치 후 출근 시간 등 로그인이 몰릴 때 429가 여러 사람에게 한꺼번에 나오지 않는지 봅니다.
- 요청 제한은 앱 인스턴스 메모리에서 셉니다. 인스턴스를 늘리면 인스턴스마다 따로 셉니다.
- API 토큰 요청(1.4)은 클라이언트 주소가 아니라 토큰마다 1분에 300회로 셉니다(9.15.1).

### 10.6 그 밖의 보안 구성

- 앱은 권한 없는 사용자 `openpms`(uid 10001)로 돕니다. jar는 root 소유이고, 이 사용자에게 넘긴 폴더는 첨부 파일용 `/data/files`뿐입니다.
- 앱은 127.0.0.1에만 열리고, DB는 호스트에 포트를 열지 않습니다.
- 운영 웹 빌드는 `VITE_API=http`가 없으면 빌드를 거부합니다(가짜 데이터 계층이 실린 이미지가 나가는 일을 막음).
- 오류 응답에 메시지와 스택 추적을 넣지 않습니다. 서버는 콘텐츠 보안 정책(CSP)을 보냅니다.
- 다른 프로젝트의 비공개 데이터는 존재 여부도 숨깁니다(403 대신 404).
- 외부와 주고받는 연동(1.4): API 토큰은 로그인·비밀번호·토큰 경로와 연동 설정(토큰 스위치·웹훅)을 부를 수 없고 읽기 전용 범위가 있습니다. 웹훅은 서명(HMAC-SHA256)을 붙이고 리다이렉트를 따라가지 않으며 내부 코멘트를 보내지 않습니다. 받는 주소는 클라우드 메타데이터 주소를 늘 막고, 1.5부터 `OPENPMS_WEBHOOK_BLOCK_PRIVATE=true`면 사설·루프백 주소도 막습니다. 끈 상태(기본)에서는 나가는 방화벽으로 범위를 좁힙니다(9.15.2).

- 전역 역할 "프로젝트 생성자": 프로젝트 만들기. 1.3부터 관리 → 사용자 → 행 메뉴 **전역 역할**로 사람에게 줍니다(9.2.6). 전역 권한 "사용자·그룹 관리"는 기본 역할에 들어 있지 않습니다.
- "작업 공유" 권한은 마이그레이션 V6에서 기본 "프로젝트 관리자" 역할에 더해졌습니다. 다른 역할에 필요하면 9.4.2로 켭니다.

- 시간 기록 권한 3개는 마이그레이션 V17(1.6)에서 기본 "프로젝트 관리자"(셋 다)와 "멤버"(내 시간 기록·시간 기록 보기)에 더해졌습니다. 프로젝트에서 **시간 기록** 모듈을 끄면 그 프로젝트에서는 누구에게도 적용되지 않습니다(9.16).
- 이 표는 새로 설치한 DB의 기본값이며, 관리자가 바꿀 수 있습니다.
