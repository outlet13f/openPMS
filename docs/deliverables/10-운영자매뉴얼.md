## 1. 개요

### 1.1 목적

openPMS를 사내 서버에 설치·배포하고, 백업·업그레이드·감시·장애 대응을 하고, 관리 화면에서 사용자와 업무 규칙을 관리하는 절차를 설명합니다.

### 1.2 시스템 구성

| 구성 요소 | 내용 |
| --- | --- |
| `app` 컨테이너 | 이미지 하나에 웹 화면(SPA)과 API가 같이 들어 있습니다. Spring Boot가 빌드된 화면을 같은 출처에서 제공합니다. 컨테이너 안 포트 8090 |
| `db` 컨테이너 | PostgreSQL 17 (`docker.io/library/postgres:17`). 호스트에 포트를 열지 않고 `app`만 접속합니다 |
| 볼륨 `db` | 데이터베이스 파일 (`/var/lib/postgresql/data`) |
| 볼륨 `files` | 첨부 파일 (`/data/files`) |

```
[사용자 브라우저] --HTTPS--> [사내 리버스 프록시: TLS]
                                   |
                                   v  127.0.0.1:8090
                     [app: SPA + /api/v1, 예약 작업, /data/files]
                                   |
                                   v
                     [db: PostgreSQL 17]
```

- 이미지는 3단계로 만듭니다: 웹 화면 빌드(Node 24) → jar 빌드(JDK 21) → 실행용 이미지(JRE 21만).
- 두 컨테이너 모두 `restart: unless-stopped`입니다. 서버를 재부팅하면 다시 뜹니다(Docker 데몬 또는 Podman 서비스가 켜져 있을 때).
- `app`은 `db`의 헬스 체크(`pg_isready`)가 통과한 뒤 시작합니다.
- 앱 안에서 예약 작업(날짜 알림, 알림 메일, 정리 작업)이 돕니다(`OPENPMS_JOBS_ENABLED`).

## 2. 설치

### 2.1 요구 사항

| 항목 | 내용 |
| --- | --- |
| 컨테이너 런타임 | Docker + Compose, 또는 Podman (`podman compose`) |
| 빌드 메모리 | 2GB면 충분합니다(Gradle 힙을 768MB로 제한) |
| 실행 메모리 | JVM은 컨테이너 메모리의 75%까지 씁니다(`-XX:MaxRAMPercentage=75`) |
| 디스크 | 이미지 약 405MB, 그 밖에 DB·첨부 파일·백업 공간 |
| 빌드 시 네트워크 | 베이스 이미지(node, eclipse-temurin, postgres)와 npm·Gradle 의존성을 내려받습니다. 사내 미러를 쓴다면 미리 맞춰 둡니다 |
| 리버스 프록시 | TLS를 끝내는 사내 프록시(nginx 등). 업로드 한도 30MB 이상(첨부 한도 25MB, 앱 요청 한도 30MB) |
| SMTP | 사내 SMTP 릴레이(초대·비밀번호 재설정·알림 메일) |

### 2.2 설치 절차

1. 저장소를 서버에 받고 저장소 최상위 폴더로 이동합니다.
2. 설정 파일을 만들고 권한을 줄입니다.

   ```bash
   cp .env.example .env
   chmod 600 .env
   ```

3. `.env`를 채웁니다(3장). 꼭 채울 값: `OPENPMS_BASE_URL`, `OPENPMS_DB_PASSWORD`, SMTP 값, `OPENPMS_MAIL_FROM`, `OPENPMS_ADMIN_EMAIL`. DB 비밀번호는 길고 무작위로 만듭니다(예: `openssl rand -base64 32`).
4. 이미지를 빌드하고 띄웁니다.

   ```bash
   docker compose up -d --build
   ```

   Podman이면 `docker` 자리에 `podman`을 씁니다(`podman compose up -d --build`).
5. 리버스 프록시가 공개 주소(https)를 `http://127.0.0.1:8090`으로 넘기도록 설정합니다(3.4).
6. 첫 관리자를 설정합니다(2.3).
7. 헬스 체크로 확인합니다: `curl -s http://127.0.0.1:8090/actuator/health` → `{"status":"UP"}`.

### 2.3 첫 관리자 설정 링크

openPMS에는 기본 관리자 비밀번호가 없습니다. 첫 기동 때 로그에 일회용 설정 링크가 한 번 나옵니다.

1. 로그에서 링크를 찾습니다.

   ```bash
   docker compose logs app | grep "No administrator yet"
   ```

   다음과 같은 줄이 나옵니다(주소와 토큰은 예시).

   ```
   No administrator yet. Set up admin@example.co.kr within 24 hours: https://pms.example.co.kr/invitations/<토큰>
   ```

2. 링크를 브라우저에서 엽니다. "openPMS 관리자 계정을 설정합니다. 이름과 비밀번호를 정하면 바로 시작합니다." 화면에서 **이름**, **새 비밀번호**를 정하고 **수락하고 시작하기**를 누릅니다. 이 계정이 첫 관리자입니다.
3. 이후 사용자는 **관리 → 사용자 → 사용자 초대**로 초대합니다(9.2).

링크 규칙:

- 활성 관리자가 없고 `OPENPMS_ADMIN_EMAIL`이 있을 때만 만듭니다.
- 24시간 유효하고 한 번만 쓸 수 있습니다.
- 관리자가 생기기 전에는 앱을 다시 시작할 때마다 새 링크가 나오고, 이전 링크는 쓸 수 없게 됩니다(410).
- 관리자가 생긴 뒤에는 다시 시작해도 링크가 나오지 않습니다.
- 그 주소가 이미 초대 상태가 아닌 계정(활성 등)이면 바꾸지 않고 경고만 남깁니다(`OPENPMS_ADMIN_EMAIL ... not changing it`).
- 링크가 유효한 24시간 동안 이 링크를 가진 사람은 관리자 계정을 만들 수 있습니다. 로그 접근을 제한하고, 설정을 마치면 바로 확인합니다.

## 3. 환경 설정

### 3.1 `.env` 환경 변수

`.env`는 `compose.yaml` 옆에 둡니다. `app`은 `.env` 전체를 받고, `db`는 `OPENPMS_DB_PASSWORD`만 받습니다.

| 변수 | 뜻 | `.env.example` 값 | 비고 |
| --- | --- | --- | --- |
| `OPENPMS_BASE_URL` | 사용자가 여는 공개 주소. 메일 속 링크, 첫 관리자 링크, SSO 콜백 주소에 씁니다. 예: `https://pms.example.co.kr` | 비어 있음 | 필수 |
| `OPENPMS_DB_PASSWORD` | 함께 뜨는 PostgreSQL의 `openpms` 사용자 비밀번호 | 비어 있음 | 필수. 비어 있으면 compose가 시작을 거부 |
| `OPENPMS_SMTP_HOST` | 사내 SMTP 릴레이 주소 | 비어 있음 | 필수 |
| `OPENPMS_SMTP_PORT` | SMTP 포트 | `25` | |
| `OPENPMS_SMTP_USER` | SMTP 사용자 | 비어 있음 | 인증이 없으면 비워 둠 |
| `OPENPMS_SMTP_PASSWORD` | SMTP 비밀번호 | 비어 있음 | 인증이 없으면 비워 둠 |
| `OPENPMS_SMTP_STARTTLS` | STARTTLS 사용 | `false` | |
| `OPENPMS_MAIL_FROM` | 보내는 사람. 예: `openPMS <no-reply@example.co.kr>` | 비어 있음 | 필수 |
| `OPENPMS_ADMIN_EMAIL` | 첫 관리자 이메일 | 비어 있음 | 첫 설치에 필수 |
| `OPENPMS_PORT` | 호스트에서 앱이 듣는 포트(127.0.0.1에만) | `8090` | 선택 |
| `OPENPMS_SESSION_TIMEOUT` | 로그인 세션 유지 시간 | `8h` | 선택 |
| `OPENPMS_SECURE_COOKIES` | 세션 쿠키에 `Secure`를 붙임 | `true` | 선택. 프록시가 평문 http일 때(시험용)만 `false` |
| `OPENPMS_JOBS_ENABLED` | 날짜 알림·알림 메일·정리 작업을 이 인스턴스에서 돌림 | `true` | 선택. 웹만 도는 추가 인스턴스는 `false` |

주의: `.env`에 변수 줄을 두고 값을 비우면 빈 문자열이 들어갑니다. `application.yml`의 기본값(예: 보내는 사람 `openPMS <no-reply@example.com>`, 기본 주소 `http://localhost:8090`)은 변수가 아예 없을 때만 쓰입니다. 필수 값은 반드시 채웁니다.

### 3.2 `.env`에 넣지 않는 값

| 변수 | 값 | 정하는 곳 |
| --- | --- | --- |
| `OPENPMS_DB_URL` | `jdbc:postgresql://db:5432/openpms` | `compose.yaml` |
| `OPENPMS_DB_USER` | `openpms` | `compose.yaml` |
| `OPENPMS_FILES_DIR` | `/data/files` | `Dockerfile` |

### 3.3 애플리케이션 고정 설정 (`application.yml`)

| 항목 | 값 | 설명 |
| --- | --- | --- |
| 세션 쿠키 | 이름 `OPENPMS_SESSION`, HttpOnly, SameSite=Lax, Secure(기본) | 세션은 DB(Spring Session JDBC)에 저장. 재시작해도 로그인 유지 |
| 오류 응답 | 메시지·스택 추적을 넣지 않음 | |
| 업로드 한도 | 파일 30MB, 요청 31MB | 첨부 한도(25MB)는 업로드마다 따로 검사 |
| SMTP 시간 제한 | 연결·읽기·쓰기 각 10초 | 응답 없는 릴레이가 스레드를 붙잡지 않게 함 |
| 외부에 여는 actuator | `health`만 | liveness·readiness 프로브 사용 |
| 메일 헬스 | 끔 | SMTP가 잠깐 죽어도 앱은 `UP` |
| DB 마이그레이션 | Flyway, 시작할 때 자동 | 마이그레이션 V1–V10 |
| 가상 스레드 | 켬 | |
| 로그인 요청 제한 | 같은 원격 주소에서 1분에 20회(`openpms.logins-per-minute`, 기본값) | 비밀번호 재설정 요청은 1분에 5회. 10.5 참고 |

`dev` 프로필(개발 데이터, 평문 http 쿠키, 예약 작업 끔, 로그인 제한 완화)은 개발용입니다. 운영에서는 켜지 않습니다.

### 3.4 리버스 프록시·TLS

- 앱은 호스트의 `127.0.0.1:${OPENPMS_PORT}`(기본 8090)에서만 듣습니다. 다른 서버에서 바로 들어올 수 없습니다.
- TLS는 사내 리버스 프록시가 끝내고, 프록시가 `http://127.0.0.1:8090`으로 넘깁니다.
- `OPENPMS_BASE_URL`은 반드시 사용자가 브라우저에 치는 공개 주소(https)로 둡니다. 틀리면 메일과 설정 링크가 엉뚱한 곳(예: localhost)을 가리키고, SSO 로그인이 `failed`가 됩니다.
- `OPENPMS_SECURE_COOKIES=true`(기본)이면 세션 쿠키가 https에서만 갑니다. 평문 http로 시험할 때만 `false`로 바꾸고, 운영에서는 다시 `true`로 둡니다.
- 프록시 업로드 한도(nginx의 `client_max_body_size`)는 30MB 이상으로 둡니다.
- `/actuator/**`(헬스 체크)는 로그인 없이 응답합니다. 외부에 열 필요가 없으면 프록시에서 막는 것을 권합니다.

## 4. 일상 운영 명령

모두 저장소 최상위 폴더(`compose.yaml`이 있는 곳)에서 실행합니다. Podman이면 `docker`를 `podman`으로 바꿉니다.

| 작업 | 명령 |
| --- | --- |
| 시작(처음·변경 후) | `docker compose up -d` |
| 이미지 다시 빌드 후 시작 | `docker compose up -d --build` |
| 상태 확인 | `docker compose ps` (`db`가 healthy인지) |
| 앱 로그 보기 | `docker compose logs -f app` |
| 앱만 재시작 | `docker compose restart app` |
| 앱만 멈춤·시작 | `docker compose stop app` / `docker compose start app` |
| 전체 멈춤 | `docker compose stop` |
| DB 콘솔 | `docker compose exec db psql -U openpms -d openpms` |
| 헬스 체크 | `curl -s http://127.0.0.1:8090/actuator/health` |

`.env`를 바꾼 뒤에는 `docker compose up -d`로 컨테이너를 다시 만들어야 값이 반영됩니다.

## 5. 백업과 복원

백업 대상은 **DB 덤프**와 **`files` 볼륨(첨부 파일)** 두 가지입니다. 둘을 같은 시각에 받습니다.

### 5.1 DB 백업

```bash
docker compose exec -T db pg_dump -U openpms -Fc openpms > openpms-$(date +%F).dump
```

- `-Fc`는 PostgreSQL 사용자 지정 형식(압축)입니다. 복원은 `pg_restore`로 합니다.
- 파일로 받을 때는 반드시 `-T`(TTY 끄기)를 붙입니다. TTY가 붙으면 바이너리 덤프가 깨질 수 있습니다(`compose.yaml` 머리말 주석에는 `-T`가 있습니다).
- 매일 받도록 호스트 cron에 등록합니다.

### 5.2 첨부 파일 백업

```bash
docker compose exec -T app tar czf - -C /data/files . > files-$(date +%F).tar.gz
```

### 5.3 백업 파일 관리

- DB 덤프에는 SSO 클라이언트 시크릿(평문), 사용자 정보, 비밀번호 해시가 들어갑니다. 백업 파일은 `.env`처럼 다룹니다: 접근할 수 있는 사람을 줄이고, 암호화된 곳에 보관합니다.
- 보관 기간과 위치는 사내 백업 정책을 따릅니다.

### 5.4 DB 복원

앱을 멈추고 DB를 새로 만든 뒤 덤프를 넣습니다.

```bash
docker compose stop app
docker compose exec -T db dropdb -U openpms openpms
docker compose exec -T db createdb -U openpms -O openpms openpms
docker compose exec -T db pg_restore -U openpms -d openpms --no-owner < openpms-2026-10-10.dump
docker compose start app
```

### 5.5 복원 연습 (운영 DB를 건드리지 않음)

정기적으로 새 DB에 넣어 보고 지웁니다.

```bash
docker compose exec -T db createdb -U openpms restore_check
docker compose exec -T db pg_restore -U openpms -d restore_check --no-owner < openpms-2026-10-10.dump
docker compose exec -T db psql -U openpms -d restore_check -c "select count(*) from projects; select count(*) from work_packages;"
docker compose exec -T db dropdb -U openpms restore_check
```

### 5.6 첨부 파일 복원

```bash
docker compose exec -T app tar xzf - -C /data/files < files-2026-10-10.tar.gz
```

## 6. 업그레이드

1. **먼저 백업합니다**(DB와 첨부 파일 모두, 5장).
2. 새 소스를 받습니다(`git pull` 등).
3. 이미지를 다시 빌드하고 띄웁니다.

   ```bash
   docker compose up -d --build
   ```

4. 앱이 시작할 때 Flyway가 새 DB 마이그레이션을 자동으로 적용합니다. 로그와 헬스 체크로 확인합니다.

   ```bash
   docker compose logs -f app
   curl -s http://127.0.0.1:8090/actuator/health
   ```

5. 브라우저로 로그인해 홈·작업 목록·관리 화면이 열리는지 확인합니다.

- 마이그레이션이 실패하면 앱이 뜨지 않습니다. 원인을 고치거나, 이전 소스로 되돌려 빌드하고 백업에서 DB를 복원합니다(5.4).
- 세션은 DB에 있으므로 재시작해도 사용자는 다시 로그인하지 않아도 됩니다.
- 운영 웹 빌드는 `frontend/.env.production`(`VITE_API=http`)이 없으면 실패합니다. 빌드가 `production build without VITE_API=http`로 실패하면 8장을 봅니다.

## 7. 모니터링과 헬스 체크

### 7.1 헬스 체크 경로

앱이 127.0.0.1에만 열려 있으므로 호스트에서 확인합니다.

| 경로 | 용도 |
| --- | --- |
| `/actuator/health` | 전체 상태 (`UP`/`DOWN`) |
| `/actuator/health/liveness` | 살아 있는지(프로세스 재시작 판단용) |
| `/actuator/health/readiness` | 요청을 받을 준비가 됐는지 |

```bash
curl -s http://127.0.0.1:8090/actuator/health
# {"status":"UP"}
```

- 사내 감시 도구가 위 경로를 주기적으로 호출하도록 등록합니다.
- 메일 헬스는 일부러 껐습니다. `DOWN`이면 메일이 아니라 DB 연결 같은 다른 원인을 먼저 봅니다.

### 7.2 로그에서 볼 것

| 로그 내용 | 뜻 | 조치 |
| --- | --- | --- |
| `No administrator yet. Set up ...` | 활성 관리자가 없음, 설정 링크 | 2.3 |
| `OPENPMS_ADMIN_EMAIL ... not changing it` | 첫 관리자 주소가 이미 다른 상태의 계정 | 8장 |
| `SSO sign-in through <식별자> refused: <코드>` | SSO 로그인 거부(정상적인 거부 포함) | 9.13.6 |
| `SSO sign-in failed: ...` | IdP와의 실패(토큰 교환, 서명 등) | 9.13.6 |
| `OpenID provider <식별자> unavailable: ...` | 발견 문서를 읽지 못함 | 네트워크·DNS·인증서 |
| 메일 발송 실패 | SMTP 릴레이 응답 없음(10초 뒤 실패) | SMTP 설정. 알림 메일은 예약 작업이 다시 보냄 |

### 7.3 정기 점검

| 주기 | 점검 |
| --- | --- |
| 매일 | 헬스 `UP`, 백업 파일 생성, 디스크 여유 |
| 매주 | 앱 로그의 오류·SSO 실패, 잠긴 계정(9.2) |
| 매월 | 복원 연습(5.5), 관리자 계정 목록 점검, 퇴사자 잠금·삭제 |
| 연초 | 공휴일 및 휴무일 입력(9.11), Entra ID 클라이언트 암호 만료일 확인(9.13) |

## 8. 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| `set OPENPMS_DB_PASSWORD in .env` 오류로 시작이 안 됨 | `.env`가 `compose.yaml` 옆에 있는지, `OPENPMS_DB_PASSWORD`를 채웠는지 |
| 로그에 설정 링크가 없음 | `OPENPMS_ADMIN_EMAIL`이 비어 있지 않은지. 이미 활성 관리자가 있으면 나오지 않습니다. 그 주소가 이미 활성 계정이면 `not changing it` 경고만 나옵니다 |
| 설정 링크가 410(만료) | 24시간이 지났거나, 이미 썼거나, 그 뒤 앱을 다시 시작해 새 링크로 바뀐 경우. 관리자가 아직 없으면 `docker compose restart app` 후 로그의 새 링크를 씁니다 |
| 메일·설정 링크가 localhost 등을 가리킴 | `OPENPMS_BASE_URL`을 공개 주소로 고치고 `docker compose up -d` |
| 로그인해도 곧바로 로그인 화면으로 돌아옴 | 평문 http로 접속 중인데 `OPENPMS_SECURE_COOKIES=true`인지. 운영은 https로 접속합니다 |
| 로그인 상태인데 화면이 로그인 페이지에 머묾, 저장이 안 됨 | 화면이 실제 API가 아닌 브라우저 안 가짜 데이터로 빌드된 경우. 최신 소스로 이미지를 다시 빌드합니다 |
| 빌드가 `production build without VITE_API=http`로 실패 | `frontend/.env.production`이 빌드에 들어가지 않음. 파일이 있는지, `.dockerignore`의 `!frontend/.env.production` 줄이 있는지 |
| 헬스가 `DOWN` | `docker compose ps`로 `db`가 healthy인지, `docker compose logs app`에서 DB 연결 오류. SMTP는 원인이 아닙니다(메일 헬스 꺼짐) |
| 메일이 오지 않음 | SMTP 값(`HOST`·`PORT`·`USER`·`PASSWORD`·`STARTTLS`)과 `OPENPMS_MAIL_FROM`. 알림 메일은 `OPENPMS_JOBS_ENABLED=true`일 때만 나갑니다 |
| 큰 파일 업로드 실패 | 프록시 업로드 한도(30MB 이상). 앱의 첨부 한도는 25MB |
| `.env`의 DB 비밀번호를 바꿨더니 앱이 DB에 못 붙음 | PostgreSQL 이미지는 `db` 볼륨을 처음 만들 때만 비밀번호를 정합니다. DB 안에서 `ALTER USER openpms PASSWORD '...'`를 먼저 하고 `.env`를 같은 값으로 고칩니다 |
| 사용자가 "잠긴 계정입니다. 관리자에게 잠금 해제를 요청하세요."를 봄 | 관리자 잠금이거나 로그인 실패 잠금 시간 중입니다. 9.2.4 |
| 여러 사용자가 동시에 로그인 오류(요청이 너무 많음) | 프록시 뒤에서는 로그인 요청 제한이 프록시 주소 하나로 묶일 수 있습니다. 10.5 |
| 관리 화면 대신 "볼 수 없는 화면입니다 / 관리자만 볼 수 있는 화면입니다." | 관리자가 아닌 계정입니다. 다른 관리자가 **관리자로 지정**합니다(9.2) |
| SSO 관련 오류 | 9.13.6 오류 코드표 |

## 9. 관리 화면 운영 절차

### 9.1 관리 화면 공통

- 들어가는 곳: 위 헤더의 계정 메뉴 → **관리**, 또는 사이드바의 **관리**(관리자에게만 보임). 주소 `/admin`.
- 관리 첫 화면은 다음 묶음으로 메뉴를 보여 줍니다.

| 묶음 | 메뉴 (주소) | 설명 |
| --- | --- | --- |
| 작업 설정 | **유형** (`/admin/types`) | 작업 유형과 색, 마일스톤 여부 |
| | **상태** (`/admin/statuses`) | 상태 이름과 닫힘·읽기 전용 규칙 |
| | **워크플로** (`/admin/workflows`) | 역할별로 허용하는 상태 전환 |
| | **우선순위** (`/admin/priorities`) | 우선순위 목록과 기본값 |
| | **사용자 정의 필드** (`/admin/custom-fields`) | 작업에 더하는 회사 고유 항목 |
| | **진행률 추적** (`/admin/progress`) | 완료 %를 계산하는 방식과 상위 작업의 합계 |
| 사람과 권한 | **사용자** (`/admin/users`) | 초대, 잠금, 관리자 지정 |
| | **그룹** (`/admin/groups`) | 사람을 묶어 멤버십을 한 번에 |
| | **역할 및 권한** (`/admin/roles`) | 역할마다 할 수 있는 일 |
| | **로그인·비밀번호** (`/admin/authentication`) | 비밀번호 규칙, 로그인 실패 잠금, 재설정·초대 링크, 사내 SSO |
| 달력 | **근무일 및 휴무일** (`/admin/calendar`) | 일정 계산에 쓰는 근무 요일과 공휴일 |

- 접근 권한: 관리자만 볼 수 있습니다. **사용자**·**그룹** 화면은 전역 권한 "사용자·그룹 관리"(`global.manage_users`)를 가진 사람도 엽니다. 관리자가 아닌 사람이 열면 "관리자만 볼 수 있는 화면입니다."가 나옵니다(API도 403).
- 목록 행 끝의 **…**(`{이름} 메뉴`) 버튼에 **수정**, **삭제** 같은 행 동작이 있습니다.
- 순서가 있는 목록(유형·상태·우선순위·사용자 정의 필드)은 행의 순서 메뉴에서 **맨 위로**, **위로**, **아래로**, **맨 아래로**로 순서를 바꿉니다.
- 색을 고르는 칸은 `#RRGGBB` 형식이고, 흰 배경 대비를 보여 줍니다. 4.5:1 미만이면 "흰 배경에서 글자로 읽기 어려운 색입니다(4.5:1 미만). 더 진한 색을 고르세요."가 나옵니다. 더 진한 색을 고릅니다.
- 저장하지 않은 변경이 있는 화면에서 다른 곳으로 가면 브라우저가 떠날지 묻습니다.
- 관리 화면을 나갈 때는 사이드바의 **관리 나가기**를 누릅니다.

### 9.2 사용자 (`/admin/users`)

목록 열: **이름**, **이메일**, **상태**, **프로젝트 수**, **최근 로그인**. 관리자에게는 "관리자", 내 계정에는 "나" 표시가 붙습니다.

- **상태로 거르기**: 전체 / 활성 / 초대됨 / 잠김
- **이름이나 이메일로 찾기**: 검색

#### 9.2.1 사용자 초대

1. **사용자 초대**를 누릅니다.
2. **이름**, **이메일**을 입력합니다. 관리자로 만들 사람이면 **관리자로 지정**을 체크합니다.
3. **초대 보내기**를 누릅니다. "{이메일}로 초대를 보냈습니다"가 나옵니다.
4. 상대가 초대 메일의 링크로 이름과 비밀번호를 정하면 계정이 활성이 됩니다. 초대 링크 유효 시간은 9.12의 **초대 링크 유효 시간(시간)**(기본 168시간)입니다.
5. 프로젝트를 보려면 프로젝트 관리자가 그 사람을 프로젝트 멤버로 추가해야 합니다(프로젝트 → 멤버 → **멤버 추가**).

#### 9.2.2 초대 다시 보내기

- 상태가 **초대됨**인 사람의 행 메뉴 → **초대 다시 보내기**. 이전에 보낸 링크는 더 이상 쓸 수 없습니다.
- 초대를 수락하기 전에는 관리자가 계정을 활성으로 바꿀 수 없습니다.

#### 9.2.3 관리자 지정·해제

- 행 메뉴 → **관리자로 지정** / **관리자 해제**. 관리자만 할 수 있고, 내 계정에는 이 메뉴가 없습니다.
- 관리자는 최소 2명 이상 두는 것을 권합니다. 마지막 활성 관리자는 잠그거나 삭제할 수 없습니다("마지막 관리자입니다.").

#### 9.2.4 잠그기·잠금 해제

- 퇴사·휴직·계정 도용 의심 시: 행 메뉴 → **잠그기**. "{이름}님의 계정을 잠갔습니다"가 나오고, **그 사람의 모든 세션이 즉시 끝납니다.** 잠긴 계정은 폼 로그인(423)도 SSO(`locked`)도 거부됩니다.
- 해제: 상태가 **잠김**인 행 메뉴 → **잠금 해제**. 로그인 실패 횟수와 실패 잠금 시간도 함께 초기화됩니다.
- 내 계정은 잠글 수 없습니다.
- **로그인 실패 잠금(자동 잠금)**: 9.12의 횟수만큼 비밀번호를 틀리면 **잠금 시간(분)** 동안 로그인이 거부됩니다. 이때 사용자 목록의 상태는 **활성**으로 보입니다(잠금 시간은 상태에 나타나지 않음). 잠금 시간이 지나면 저절로 풀립니다. 기다리지 않고 풀려면 그 사람의 행 메뉴에서 **잠그기** → **잠금 해제**를 차례로 하거나, 본인이 비밀번호 재설정을 마치면 풀립니다.

#### 9.2.5 사용자 삭제

1. 행 메뉴 → **삭제**.
2. 확인 대화상자 "사용자를 삭제할까요?": "{이름}님의 계정은 '삭제된 사용자'로 익명화됩니다. 활동 기록은 남고, 멤버십·주시·담당은 모두 풀립니다. 되돌릴 수 없습니다." → **삭제**.
- 삭제는 익명화입니다. 이름은 "삭제된 사용자", 이메일은 무효 주소로 바뀌고 비밀번호와 관리자 권한이 지워집니다. 멤버십, 주시, 공유, 알림, 그룹 소속, 담당자·책임자 지정이 풀리고 세션이 끝납니다. 작업 활동(저널)과 작성자 기록은 남습니다.
- 감사 목적상 기록을 남겨야 하면 삭제 대신 **잠그기**를 씁니다.
- 내 계정과 마지막 관리자는 삭제할 수 없습니다.

### 9.3 그룹 (`/admin/groups`)

팀 단위로 사람을 묶어 두면 프로젝트 멤버를 한 번에 추가할 수 있습니다. 목록 열: **이름**, **멤버**(명 수).

| 작업 | 절차 |
| --- | --- |
| 그룹 만들기 | **그룹 만들기** → **이름** → **저장** |
| 멤버 관리 | 행 메뉴 → **멤버 관리** → "{그룹} 멤버" 대화상자에서 활성 사용자를 체크·해제 → **저장** |
| 이름 바꾸기 | 행 메뉴 → **이름 바꾸기** → **저장** |
| 삭제 | 행 메뉴 → **삭제** → "'{그룹}' 그룹을 삭제합니다. 사람 계정은 그대로 남습니다." → **삭제** |

- 프로젝트에 그룹을 추가하는 것은 프로젝트 → 멤버 → **멤버 추가**에서 "추가할 사람과 그룹"으로 그룹을 고르고 **역할**을 정합니다.
- 프로젝트에서 그룹을 빼면 그 그룹 구성원은 그룹을 통해 받은 권한을 잃습니다. 따로 멤버로 추가된 사람은 그대로 남습니다.

### 9.4 역할 및 권한 (`/admin/roles`)

목록 열: **이름**, **범위**(프로젝트 역할 / 전역 역할), **권한 수**, **멤버십 수**. 내장 역할에는 "내장" 표시가 붙습니다.

#### 9.4.1 역할 추가

1. **역할 추가**를 누릅니다.
2. **이름**을 입력하고 **범위**를 고릅니다.
   - **프로젝트 역할**: 프로젝트 멤버에게 붙는 역할입니다.
   - **전역 역할**: 프로젝트와 상관없이 사람에게 붙는 역할입니다(프로젝트 만들기 등).
3. **만들기**. 만든 뒤 바로 그 역할의 권한 편집 화면으로 이동합니다. 프로젝트 역할은 "프로젝트 보기"·"작업 보기"가 미리 체크되어 있습니다.

#### 9.4.2 권한 편집

1. 행 메뉴 → **권한 편집**.
2. 권한 묶음(프로젝트, 작업, 보기, 보드, 전역)별 체크박스를 체크·해제합니다. 묶음 전체는 **이 묶음 모두**.
3. **저장**.

- 내장 역할 "비멤버"는 공개 프로젝트를 멤버가 아닌 사람이 볼 때 쓰는 역할입니다. 이름은 바꿀 수 없고 권한만 고칠 수 있습니다.
- 새 프로젝트 역할을 만들면 워크플로(9.7)도 정해야 그 역할의 사람이 상태를 바꿀 수 있습니다.
- 권한 목록과 기본 역할의 권한은 부록 B.

#### 9.4.3 역할 삭제

- 행 메뉴 → **삭제** → "'{역할}' 역할과 그 워크플로가 지워집니다. 이 역할을 가진 멤버가 있으면 삭제할 수 없습니다." → **삭제**.

#### 9.4.4 현재 버전의 제약

- 전역 역할(예: 기본 "프로젝트 생성자")을 만들고 권한을 고칠 수는 있지만, **전역 역할을 사람에게 배정하는 화면은 아직 없습니다**(`replica/parity.md`, 멤버·권한 partial). 관리자는 전역 권한과 상관없이 모든 관리 작업을 할 수 있습니다.

| 영역 | 조작 |
| --- | --- |
| **속성 그룹** | 그룹 이름을 바꾸고(**그룹 이름**), 그룹을 위·아래로 옮기고, **그룹 추가**(최대 20개), 그룹 삭제(항목은 숨김으로). 항목은 **위로**·**아래로**, 항목 메뉴(`{항목} 옮기기`)에서 '{그룹}' 그룹으로 보내기 또는 **숨기기** |

### 9.7 워크플로 (`/admin/workflows`)

역할마다 어떤 상태에서 어떤 상태로 바꿀 수 있는지 정합니다. 사용자는 자기 역할에 허용된 전환만 고를 수 있고, 보드에서 카드를 옮길 때도 같은 규칙이 적용됩니다.

1. 위에서 **유형**과 **역할**을 고릅니다(프로젝트 역할만, 내장 역할 제외).
2. 표(행: 현재 상태, 열: 바꿀 상태 — **현재 상태 → 바꿀 상태**)의 칸을 체크합니다. 행·열 머리의 **모두**/**해제**로 한 상태에서 가는(오는) 전환을 한꺼번에 허용·해제합니다.
3. **저장**. 잘못 체크했으면 저장 전에 **되돌리기**.

- 저장하지 않은 채 다른 유형·역할로 바꾸면 "저장하지 않은 변경을 버릴까요?"가 나옵니다(**버리고 이동**).
- 허용된 전환이 하나도 없으면 "허용된 전환이 없습니다 — {역할} 역할은 {유형} 작업의 상태를 바꿀 수 없습니다."가 나옵니다. 참관자처럼 의도한 경우가 아니면 전환을 체크합니다.
- **다른 유형·역할에 복사**: 지금 저장된 전환을 **대상 유형**과 **대상 역할**에 그대로 덮어씁니다. 저장하지 않은 변경이 있으면 쓸 수 없습니다.
- 기본값: 관리자(프로젝트 관리자)·멤버는 모든 유형에서 모든 상태 간 전환 가능, 참관자는 상태를 바꾸지 못합니다.

### 9.10 진행률 추적 (`/admin/progress`)

| 영역 | 선택지 | 설명 |
| --- | --- | --- |
| **계산 방식** | **작업량 기준** | 완료 %를 직접 입력하거나, 작업량과 남은 작업 중 하나를 바꾸면 나머지를 계산합니다 |
| | **상태 기준** | 완료 %는 상태마다 정한 값(관리 › 상태)을 따르고 직접 바꿀 수 없습니다. 남은 작업은 작업량에서 계산합니다 |

- 상태 기준으로 바꾸기 전에 9.6에서 상태마다 **완료 %**를 정해 둡니다.

### 9.11 근무일 및 휴무일 (`/admin/calendar`)

#### 9.11.1 근무 주

- **근무 요일**: 월요일–일요일 체크(기본 월–금).
- **하루 근무 시간**: 작업량을 일 단위로 보여 줄 때 하루로 치는 시간(1–24, 기본 8).
- **저장**. 근무 요일을 바꾸면 "근무 요일을 바꿀까요? — 모든 프로젝트의 작업 완료일이 다시 계산되고, 바뀐 작업마다 활동 기록이 남습니다." → **바꾸고 다시 계산**.
- 근무 요일이나 휴무일을 바꾸면 모든 프로젝트의 작업 완료일이 새 달력으로 다시 계산됩니다. 시작일과 기간은 유지됩니다.

#### 9.11.2 공휴일 및 휴무일

1. 연도를 고릅니다(**이전 해**/**다음 해**).
2. **날짜**와 **이름**(예: 창립기념일)을 넣고 **휴무일 추가**. "휴무일을 추가하고 일정을 다시 계산했습니다".
3. 지울 때는 행의 **{이름} 삭제**. "휴무일을 지우고 일정을 다시 계산했습니다".

- 여기 있는 날은 일정 계산에서 건너뜁니다. 설날·추석·대체공휴일처럼 해마다 바뀌는 날은 **연초에 입력**합니다.
- 휴무일 추가·삭제도 일정 재계산을 일으키므로 업무 시간 외에 하는 것을 권합니다.

### 9.13 사내 SSO 공급자 등록

같은 화면(`/admin/authentication`)의 **사내 SSO (OpenID Connect)** 영역입니다. 회사 계정 시스템(Keycloak, Microsoft Entra ID, Google Workspace 등)으로 로그인하게 합니다. 공급자마다 로그인 화면에 "{버튼 이름}(으)로 로그인" 버튼이 하나씩 생깁니다. 이메일·비밀번호 로그인은 그대로 남습니다(끄는 설정은 없음). `.env`에 넣을 값은 없고, 공급자 정보는 DB에 저장됩니다.

#### 9.13.1 순서

1. 공급자 **식별자**를 정합니다. 예: `company`. 영문 소문자·숫자·하이픈 40자까지. 콜백 주소에 들어가며 만든 뒤에는 바꿀 수 없습니다.
2. IdP에 클라이언트(앱)를 등록합니다(9.13.2).
3. openPMS에서 **관리 → 로그인·비밀번호 → 사내 SSO (OpenID Connect) → SSO 공급자 추가**에 값을 넣고 **저장**합니다(9.13.3). 목록에 **콜백 주소**가 보입니다.
4. 로그아웃한 뒤 로그인 화면의 버튼으로 시험합니다. 먼저 기존 계정이 있는 사람으로 해 봅니다.

콜백 주소 = `OPENPMS_BASE_URL` + `/api/v1/auth/oidc/callback/{식별자}`. 예: `https://pms.example.co.kr/api/v1/auth/oidc/callback/company`. IdP에 등록한 값과 글자 하나까지 같아야 합니다. `OPENPMS_BASE_URL`을 바꾸면 IdP의 리디렉션 URI도 같이 바꿉니다.

#### 9.13.2 IdP에 등록할 것

| 항목 | 값 |
| --- | --- |
| 클라이언트 종류 | 비밀값이 있는(confidential) 웹 앱, 권한 코드 흐름 |
| 리디렉션 URI | 위의 콜백 주소 |
| 범위(scope) | `openid email profile` (openPMS 기본값). `openid`는 필수 |
| PKCE | openPMS는 항상 S256으로 보냅니다. IdP에서 필수로 켜도 됩니다 |
| 토큰에 담길 값 | `sub`, `email`, 이름(`name`, 없으면 `family_name`·`given_name`) |
| 로그아웃 주소 | 등록하지 않습니다(openPMS는 IdP 로그아웃을 부르지 않음) |

- `app` 컨테이너가 IdP의 발견 문서·토큰·키(JWKS)·userinfo 주소에 직접 닿아야 합니다. 사내 방화벽·DNS를 확인합니다.
- IdP가 사내 CA 인증서로 https를 쓰면 JRE가 그 CA를 믿어야 합니다. 지금 이미지에는 사내 CA를 넣는 단계가 없습니다.
- Keycloak: 발급자 `https://<호스트>/realms/<realm>`. Client authentication·Standard flow 켬, Valid redirect URIs에 콜백 주소, 시크릿은 Credentials 탭. 사용자의 Email verified가 꺼져 있으면 기존 계정에 연결되지 않습니다.
- Microsoft Entra ID: 발급자 `https://login.microsoftonline.com/<테넌트 ID>/v2.0`(`common`·`organizations`는 저장이 거부됨). 플랫폼 "웹", 클라이언트 암호를 시크릿 칸에. **클라이언트 암호에는 만료일이 있으므로** 만료 전에 새 암호로 바꿉니다. 엔터프라이즈 앱에서 사용자 할당을 필수로 하면 할당된 사람만 들어옵니다.

#### 9.13.3 openPMS에 넣을 것 ("SSO 공급자 추가" 대화상자)

| 칸 | 내용 |
| --- | --- |
| **버튼 이름** | 로그인 화면에 '…(으)로 로그인'으로 보입니다. 60자까지. 예: `사내 계정` |
| **식별자** | 9.13.1의 값. 처음 만들 때만 입력 |
| **발급자(Issuer) 주소** | 이 주소 뒤에 `/.well-known/openid-configuration`을 붙여 엔드포인트와 서명 키를 읽어 옵니다. 저장할 때 확인하며, 문서 안의 issuer가 입력값과 같아야 합니다(끝의 `/`까지) |
| **클라이언트 ID** | IdP에서 받은 값 |
| **클라이언트 시크릿** | IdP에서 받은 값. 저장한 뒤에는 화면·API에 다시 나오지 않습니다. 수정할 때 비워 두면 저장된 값을 그대로 씁니다 |
| **범위(scope)** | 공백으로 구분. openid는 꼭 들어가야 합니다 |
| **이메일 클레임** | 기본 `email` |
| **이름 클레임** | 기본 `name`. 없으면 성·이름(family_name, given_name), 그다음 이메일 앞부분 |
| **계정이 없으면 처음 로그인할 때 만들기** | 기본 꺼짐. 끄면 관리자가 미리 초대한 사람만 로그인합니다. 켜면 새 계정은 관리자가 아니고, 프로젝트 멤버로 추가해야 프로젝트가 보입니다 |
| **사용** | 끄면 로그인 버튼이 사라집니다. 연결 정보는 남습니다 |

- 목록 열: **버튼 이름**(꺼져 있으면 "꺼짐" 표시), **콜백 주소**, **계정 자동 생성**, **연결된 사람** 수. 등록된 공급자가 없으면 "등록된 SSO 공급자가 없습니다. 지금은 이메일과 비밀번호로만 로그인합니다."가 나옵니다.
- 수정: 행 메뉴 → **수정**("SSO 공급자 수정").
- 삭제: 행 메뉴 → **삭제** → "SSO 공급자 삭제 — '{이름}'을(를) 삭제합니다. 연결된 N명의 계정은 남지만, 비밀번호가 없는 사람은 비밀번호 재설정이나 다른 공급자로 로그인해야 합니다."

#### 9.13.4 누가 로그인되나

1. 이 공급자의 `sub`에 이미 연결된 계정.
2. 없으면 이메일이 같은 계정(대소문자 무시). 이때 연결을 만듭니다. 공급자가 `email_verified=false`를 보내면 거부합니다(`unverified`). 값이 없으면 확인된 것으로 봅니다.
3. 없고 계정 자동 생성이 켜져 있으면 새 계정.
4. 그 밖에는 거부합니다(`no_account`). 관리자가 먼저 초대해야 합니다.

- 한 번 연결되면 IdP에서 이메일이 바뀌어도 같은 계정으로 들어옵니다.
- 잠긴 계정(관리자 잠금, 로그인 실패 잠금 시간 중)은 거부합니다(`locked`). 초대 상태인 계정은 SSO로 로그인하면 활성이 됩니다.
- SSO 로그인도 폼 로그인과 같은 openPMS 세션을 쓰고, 유지 시간은 `OPENPMS_SESSION_TIMEOUT`입니다.

#### 9.13.5 운영 시 주의

- IdP에서 사람을 막아도 이미 열린 openPMS 세션은 끝날 때까지 남습니다. 즉시 내보내려면 openPMS에서도 **잠그기**(9.2.4)를 합니다.
- 이메일로 자동 연결하므로, 사용자가 자기 이메일을 직접 바꿀 수 있는 IdP는 등록하지 않습니다(다른 사람 계정에 연결될 위험).
- 자동 생성을 켜면 그 IdP에 로그인할 수 있는 모든 사람이 계정을 얻습니다. IdP에서 이 앱을 쓸 사람·그룹만 할당합니다.

#### 9.13.6 오류 코드

실패하면 브라우저가 `/login?sso_error=<코드>`로 돌아오고 로그인 화면이 이유를 보여 줍니다.

| 코드 | 화면 안내 | 확인할 것 |
| --- | --- | --- |
| `no_account` | openPMS 계정이 없습니다. 관리자에게 초대를 요청하세요. | 그 이메일로 초대하거나 자동 생성을 켬. IdP 이메일과 openPMS 이메일이 같은지 |
| `locked` | 잠긴 계정입니다. 관리자에게 잠금 해제를 요청하세요. | 9.2.4 |
| `unverified` | 로그인 공급자가 이메일 주소를 확인되지 않은 주소로 알려 왔습니다. | IdP에서 그 사용자의 이메일을 확인 처리 |
| `no_email` | 로그인 공급자가 이메일 주소를 보내지 않았습니다. | 범위에 `email`, 이메일 클레임 이름, IdP 사용자의 메일 주소 |
| `cancelled` | 로그인을 취소했거나 공급자가 허용하지 않았습니다. | IdP의 사용자·그룹 할당, 동의 설정 |
| `unavailable` | 지금은 이 방법으로 로그인할 수 없습니다. | **사용** 여부, `app` 컨테이너에서 IdP로 가는 네트워크·DNS·TLS 인증서 |
| `failed` | 로그인 공급자와 확인하지 못했습니다. 다시 시도하세요. | 시크릿(틀림·만료), `OPENPMS_BASE_URL`이 사용자가 여는 주소와 같은지, 서버 시계, 로그의 `SSO sign-in failed` |

- IdP 화면에 `redirect_uri` 오류가 나오면 IdP에 등록한 리디렉션 URI와 openPMS 목록의 **콜백 주소**를 글자 단위로 비교합니다.
- 저장할 때 발급자 칸에 오류가 나면 발급자 주소 오타, 끝의 `/`, 서버에서 IdP로 나가는 네트워크를 봅니다.

## 10. 보안 운영

### 10.1 비밀값 관리

| 비밀값 | 위치 | 관리 |
| --- | --- | --- |
| DB 비밀번호, SMTP 비밀번호 | `.env`(권한 600) | git에서 제외(`.gitignore`), 이미지에도 들어가지 않음(`.dockerignore`). 저장소에는 값이 빈 `.env.example`만 있음 |
| SSO 클라이언트 시크릿 | DB `oidc_providers.client_secret` | **평문으로 저장됩니다**(암호화하지 않음). API·화면에는 내보내지 않고 저장 여부만 보여 줌. 그래서 DB 덤프에도 들어갑니다 |
| 첫 관리자 설정 링크 | 앱 로그(1회) | 24시간 유효. 로그 접근 제한 |
| `frontend/.env.production` | 저장소 | 비밀값이 아님(`VITE_API=http` 하나) |

- 기본 비밀번호는 없습니다. 개발용 시드 계정은 개발 프로필에만 있고 운영 이미지에는 없습니다.
- 시크릿이 샜다고 의심되면: SSO는 IdP에서 새 시크릿을 만들어 수정 대화상자에 넣고 옛 시크릿을 IdP에서 지웁니다. DB 비밀번호는 8장의 비밀번호 변경 절차를 따릅니다.
- 백업 파일은 `.env`와 같은 수준으로 보호합니다(5.3).

### 10.2 세션

- 세션은 DB(Spring Session JDBC)에 저장되고, 쿠키 `OPENPMS_SESSION`은 HttpOnly, SameSite=Lax, 기본 Secure입니다.
- 유지 시간은 `OPENPMS_SESSION_TIMEOUT`(기본 `8h`)입니다.
- 세션이 끝나는 경우: 유지 시간 경과, 로그아웃, 관리자가 **잠그기**·**삭제**(그 사람의 모든 세션 종료), 비밀번호 재설정(모든 기기 로그아웃).
- 모든 쓰기 요청에는 CSRF 토큰이 필요합니다(없으면 403).

### 10.3 계정 잠금

- 자동: 9.12.2의 실패 횟수에 이르면 잠금 시간 동안 로그인 거부(HTTP 423, SSO는 `locked`).
- 수동: 9.2.4의 **잠그기**. 퇴사자·장기 부재자·도용 의심 계정은 바로 잠급니다.
- 관리자 계정은 2명 이상 유지하고, 마지막 관리자는 잠글 수 없음을 기억합니다.

### 10.4 감사 (저널)

- 작업 패키지의 모든 변경은 저널(활동 기록)에 남습니다: 누가, 언제, 어떤 필드를 무엇에서 무엇으로 바꿨는지, 코멘트. 작업 상세의 활동 탭에서 봅니다.
- 같은 사람이 같은 작업을 5분 안에 연속으로 바꾸면(그 사이 다른 사람의 기록이 없을 때) 한 기록으로 합쳐집니다.
- 작업 이동(다른 프로젝트), 근무일·휴무일 변경에 따른 일정 재계산도 바뀐 작업마다 기록이 남습니다.
- 사용자를 삭제해도 저널과 작성자 기록은 남고 이름만 "삭제된 사용자"로 바뀝니다.
- 한계(현재 버전):
  - 진행률 설정 변경에 따른 재계산은 활동 기록을 남기지 않습니다.
  - 관리 설정(유형·상태·워크플로·역할·사용자·로그인 정책·SSO 공급자 등)의 변경 이력을 남기는 별도 감사 로그는 없습니다. 관리 변경은 변경 요청서 등 사내 절차로 기록하는 것을 권합니다.
  - 로그인 성공 시각은 사용자 목록의 **최근 로그인**으로만 볼 수 있습니다. SSO 거부·실패는 앱 로그에 남습니다(7.2).

### 10.5 로그인 요청 제한과 리버스 프록시

- 로그인은 같은 원격 주소에서 1분에 20회, 비밀번호 재설정 요청은 1분에 5회로 제한합니다.
- 앱은 원격 주소를 연결한 쪽의 주소로 봅니다. `application.yml`에 프록시 헤더(`X-Forwarded-For`) 처리 설정이 없으므로, 리버스 프록시 뒤에서는 모든 사용자가 같은 주소(프록시)로 보일 수 있습니다. 그러면 출근 시간처럼 로그인이 몰릴 때 사용자 전체가 1분에 20회 한도를 함께 쓰게 됩니다. **배포 때 실제로 확인하고**, 문제가 있으면 개발팀에 프록시 헤더 처리 추가를 요청합니다.

### 10.6 그 밖의 보안 구성

- 앱은 권한 없는 사용자 `openpms`(uid 10001)로 돕니다. jar는 root 소유이고, 이 사용자에게 넘긴 폴더는 첨부 파일용 `/data/files`뿐입니다.
- 앱은 127.0.0.1에만 열리고, DB는 호스트에 포트를 열지 않습니다.
- 운영 웹 빌드는 `VITE_API=http`가 없으면 빌드를 거부합니다(가짜 데이터 계층이 실린 이미지가 나가는 일을 막음).
- 오류 응답에 메시지와 스택 추적을 넣지 않습니다. 서버는 콘텐츠 보안 정책(CSP)을 보냅니다.
- 다른 프로젝트의 비공개 데이터는 존재 여부도 숨깁니다(403 대신 404).
