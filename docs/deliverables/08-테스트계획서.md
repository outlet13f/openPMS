## 1. 개요

### 1.1 목적

이 문서는 openPMS의 테스트 범위, 전략, 환경, 기준, 테스트 케이스를 정의합니다. 이 계획에 따라 수행한 결과는 「09-테스트결과서」에 적습니다.

### 1.2 배경

openPMS는 OpenProject 17.9.1의 화면과 동작을 사내용으로 다시 만든 프로젝트 관리 시스템입니다. 원본 소스 코드는 읽거나 옮기지 않았습니다(클린룸). 테스트도 원본 인스턴스에는 어떤 자동 요청도 보내지 않고, openPMS 자체의 화면과 API만 대상으로 합니다.

### 1.3 용어

| 용어 | 뜻 |
| --- | --- |
| 흐름(F00–F11) | 사용자 업무 흐름 단위. 예: F01 작업 패키지 만들기 |
| 화면(S01–S37) | 화면 목록의 화면 번호. 예: S06 작업 목록 |
| 복원 지점(restore point) | 시드 데이터를 넣은 DB의 사본(`openpms_seed`). 테스트는 이 사본에서 시작합니다 |
| axe | 웹 접근성 자동 검사 도구(axe-core). WCAG 2.1 A/AA 규칙으로 검사합니다 |
| 테스트 IdP | SSO 테스트용 OpenID Connect 공급자(`frontend/e2e/fake-idp.mjs`). 운영용이 아닙니다 |
| 점검 묶음 | 개발 세션 중 작성·실행한 브라우저 점검 스크립트 27묶음. 저장소에는 아직 없습니다 |

## 2. 테스트 대상과 범위

### 2.1 대상

| 구분 | 대상 | 위치 |
| --- | --- | --- |
| 프런트엔드 | React + Vite + TypeScript 단일 페이지 앱 | `frontend/` |
| 백엔드 | Spring Boot 4 + jOOQ, REST API `/api/v1` | `backend/` |
| DB | PostgreSQL 17, Flyway 마이그레이션 V1–V10 | `backend/src/main/resources/db/migration` |
| 배포 | 이미지 1개(SPA + API) + PostgreSQL 17, compose | `Dockerfile`, `compose.yaml`, `.env.example` |

### 2.2 범위에 넣는 기능

로그인(폼·사내 SSO), 작업 패키지 생성·수정·상태 전환, 보기 저장·공유, 일정(근무일·선후행·Gantt), 관계·계층, 보드, 코멘트·멘션·알림, 프로젝트·멤버, 관리(유형·상태·워크플로·우선순위·사용자 정의 필드·진행률·사용자·그룹·역할·로그인 정책·근무일), 내보내기, 공유, 예약 작업(날짜 알림·메일), 접근성, 배포.

### 2.3 범위에서 빼는 것

- 원본에서 범위 밖으로 정한 모듈: 시간 추적·비용, 미팅, 위키, 뉴스, 문서, 포럼, 백로그, 포트폴리오, BIM, 리포지토리 연동, 외부 파일 저장소, LDAP·SAML·SCIM 등(`replica/parity.md` "일부러 뺀 것").
- 결제: 사내 도구라 결제 기능이 없습니다.
- 성능·부하 테스트: 이번 단계 범위가 아닙니다(10장 위험 참고).

## 3. 테스트 전략과 레벨

| 레벨 | 목적 | 도구·방법 | 실행 | 자동화 |
| --- | --- | --- | --- | --- |
| 단위·통합 | 도메인 규칙(일정·진행률), 권한, API 검증, 예약 작업, 인증 링크, SSO | JUnit 5, Spring MockMvc, 테스트 안의 작은 IdP | `backend/scripts/dev.sh test` | 자동 |
| E2E 흐름 | 업무 흐름이 화면에서 끝까지 동작하는지 | Playwright(Chrome) + 실제 API | `npm run e2e` (`frontend/`) | 자동 |
| 접근성 | WCAG 2.1 A/AA 위반이 없는지 | `@axe-core/playwright`, 화면마다 | e2e 스위트 안에서 | 자동 |
| 시각 패리티 | 원본과 레이아웃·기능 비교 | `replica/parity.md`(기능 매트릭스 점수, 레이아웃 비교) | `/replica-diff` | 반자동 |
| 수동 | 자동화하지 않은 항목(실제 메일, 실제 IdP, 스크린 리더 낭독) | 사람이 확인 | 배포 때 | 수동 |
| 배포 스모크 | 운영 이미지가 뜨고 핵심 흐름이 동작하는지 | Podman으로 이미지 기동, 브라우저 점검, 백업·복원 | `replica/deploy.md` "검증 기록" | 수동 |

### 3.1 단위·통합 테스트 (JUnit)

- 위치: `backend/src/test/java/**` (16개 클래스, 51개 테스트 메서드).
- 실행: `backend/scripts/dev.sh test`. 복원 지점(`openpms_seed`)을 템플릿으로 버리는 DB `openpms_test`를 새로 만들고, 그 DB에 대해 JDK 21 컨테이너에서 `./gradlew test`를 실행합니다. 개발 DB는 건드리지 않습니다.
- 사전 준비: 복원 지점을 한 번 만들어 둡니다(`dev.sh snapshot-db`, 앱 정지 상태).
- `*Test`(예: `ScheduleTest`, `ProgressTest`, `FileStorageTest`)는 DB 없이 도는 순수 단위 테스트이고, `*IT`는 Spring 컨텍스트와 DB를 쓰는 통합 테스트입니다.
- 테스트가 시드 계정의 비밀번호나 설정을 바꾸면 `finally`에서 되돌립니다.

### 3.2 E2E 테스트 (Playwright + axe)

- 위치: `frontend/e2e/*.spec.ts` (흐름 스펙 11개 + 접근성 스펙 1개, 77개 테스트).
- 실행 구성: 백엔드 API는 `127.0.0.1:8090`(`backend/scripts/dev.sh run`), 화면은 Vite의 실제 API 모드(http 모드) `:5174`(`npm run dev:api`), 그다음 `npm run e2e`.
- Playwright 설정(`frontend/playwright.config.ts`): Chrome 헤드리스, 뷰포트 1424×900, 로캘 `ko-KR`, 시간대 `Asia/Seoul`, 워커 1개(순차 실행), 테스트 제한 60초, 실패 시 trace 보관.
- DB 격리: 스펙 파일마다 `beforeAll`에서 `dev.sh restore-db`로 복원 지점에 되돌립니다. 그래서 파일은 하나씩 순서대로 실행합니다.
- 공통 실패 조건(`frontend/e2e/support.ts`): 테스트 중 브라우저 콘솔 오류, 페이지 예외, 5xx 응답이 하나라도 있으면 그 테스트는 실패입니다. 테스트가 일부러 일으킨 4xx만 예외입니다.
- 접근성: 흐름 스펙은 거치는 화면마다, 접근성 스펙은 나머지 화면마다 axe를 `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` 태그로 돌리고 위반이 0건이어야 통과합니다. 어두운 테마는 6개 화면을 다시 검사합니다.
- SSO 스펙(`f00-sso.spec.ts`)은 테스트 IdP 컨테이너가 떠 있어야 합니다. 떠 있지 않으면 4건을 건너뜁니다(실패가 아님). 77/77을 주장하려면 테스트 IdP를 띄운 상태여야 합니다.
- 테스트 계정은 개발 프로필에만 있는 시드 계정입니다. 비밀번호는 이 문서에 적지 않습니다.

### 3.3 접근성·시각 패리티

- 접근성: 3.2의 axe 검사(자동) + 스크린 리더 실제 낭독(수동, NVDA로 S06·S07·S15).
- 시각·기능 패리티: `replica/parity.md`. 기능 매트릭스(`replica/features.csv`, 141개 항목)를 must·should·could 가중치로 점수화하고, 원본 캡처(`replica/screens/`)와 클론 캡처(`replica/clone-screens/`)를 같은 뷰포트(1424×865, 390×844)에서 레이아웃 모드로 비교합니다. 색은 일부러 다르므로 점수에 넣지 않습니다.

### 3.4 배포 스모크 테스트

- 기준: `replica/deploy.md`.
- 방법: 운영 이미지를 빌드해 Podman으로 띄우고(버리는 DB), 마이그레이션·헬스·첫 관리자 링크·브라우저 핵심 흐름·세션 유지·첨부 저장소·백업과 복원을 확인합니다(8.5).

## 4. 테스트 환경

### 4.1 개발·테스트 환경

| 구성 | 내용 |
| --- | --- |
| 컨테이너 런타임 | Podman (`backend/scripts/dev.sh`가 컨테이너를 관리) |
| DB | `openpms-db` 컨테이너, PostgreSQL 17, `127.0.0.1:55432`. DB: `openpms`(작업), `openpms_seed`(복원 지점), `openpms_test`(JUnit용 사본) |
| 메일 | `openpms-mail` 컨테이너(Mailpit), 웹 화면 `http://127.0.0.1:8025` |
| 백엔드 | `openpms-app` 컨테이너, 개발 프로필(`dev`), `127.0.0.1:8090`. 개발 프로필은 개발 데이터 마이그레이션(`db/dev`)을 더하고, 쿠키 Secure를 끄고, 예약 작업을 기본으로 끕니다 |
| 프런트엔드 | Vite 개발 서버, 실제 API 모드 `--mode api --port 5174` |
| 브라우저 | Chrome (Playwright `channel: "chrome"`) |
| 테스트 IdP | `openpms-idp` 컨테이너(Node 24), 개발 네트워크 안 발급자 `http://openpms-idp:18080`, 브라우저용 `http://localhost:18081`. 실행 명령은 `frontend/e2e/fake-idp.mjs` 머리말 |
| JDK | JDK 21 컨테이너 안에서 Gradle 실행 |

### 4.2 테스트 데이터

- 시드 데이터: 기준 데이터(V3) + 개발 데이터(개발 프로필, `scripts/gen_dev_data.py`로 생성). 프로젝트 "웹 플랫폼 개편"(`web-platform`, 비공개), "모바일 앱 2.0"(`mobile-app`) 등과 작업 21개, 역할별 사용자(관리자, 프로젝트 관리자, 멤버, 참관자, 잠긴 계정, 다른 프로젝트 사용자).
- 운영 이미지에는 데모 데이터가 없습니다(V3는 기준 데이터만).

### 4.3 배포 스모크 환경

- 빌드한 운영 이미지를 Podman으로 띄움, 호스트 포트 18090, 버리는 DB.

## 5. 진입·종료 기준

### 5.1 진입 기준

| 레벨 | 기준 |
| --- | --- |
| 단위·통합 | 컴파일 성공, 복원 지점(`openpms_seed`) 준비, DB 컨테이너 기동 |
| E2E | API(:8090)와 Vite 실제 API 모드(:5174) 기동, 복원 지점 준비. SSO 케이스는 테스트 IdP 기동 |
| 배포 스모크 | 이미지 빌드 성공, `.env` 작성(필수 값 채움) |
| 수동 | 대상 환경(사내 SMTP·IdP 등) 준비 |

### 5.2 종료(합격) 기준

1. JUnit 전체 통과(실패 0, 건너뜀 0).
2. E2E 전체 통과(테스트 IdP를 띄운 상태에서 건너뜀 0). 콘솔 오류·5xx 0건, axe 위반 0건.
3. 열린 결함 중 S1·S2가 0건. S3·S4는 고치거나, 남길 경우 사유와 계획을 결과서에 적음.
4. 기능 패리티 must 항목 전부 완료, 기능 점수 80 이상(`replica/parity.md` 판정 기준).
5. 배포 스모크 테스트 통과(헬스 `UP`, 첫 관리자 링크, 핵심 흐름, 백업·복원).

### 5.3 중단·재개 기준

- 중단: 환경 문제로 다수 케이스가 같은 원인으로 실패할 때(예: DB 복원 실패, API 미기동), S1 결함으로 주요 흐름이 막힐 때.
- 재개: 원인을 고친 뒤 해당 레벨 전체를 처음부터 다시 실행합니다.

### 5.4 회귀 기준

- 기능이 바뀌면 JUnit 전체와 E2E 전체를 다시 실행합니다. 일부만 돌린 결과로 합격을 판정하지 않습니다.

## 6. 결함 관리와 심각도 기준

### 6.1 결함 기록

- 재현한 결함만 `replica/bugs.md`에 `BUG-NNN`으로 기록합니다. 의심만 가는 것은 `replica/test-plan.md`의 "확인할 것"에 둡니다.
- 기록 항목: ID, 심각도, 제목, 흐름·케이스, 화면, 단계, 기대, 실제, 증거(실패한 테스트), 원인, 상태, 고친 내용·커밋.
- 상태: 열림 → 고침(커밋 번호) → 회귀 테스트로 확인.

### 6.2 심각도 기준 (S1–S4)

`replica/bugs.md`는 S1–S4 척도를 씁니다. 각 등급의 정의는 이 문서에서 다음과 같이 정합니다.

| 등급 | 이름 | 정의 | 예 | 출시 영향 |
| --- | --- | --- | --- | --- |
| S1 | 치명 | 데이터 손실·유출, 보안 우회, 핵심 흐름을 전혀 쓸 수 없음. 우회 방법 없음 | 권한 없는 사람이 비공개 프로젝트를 봄, 로그인 불가 | 출시 불가 |
| S2 | 중대 | 주요 기능이 잘못 동작하고 우회가 어렵거나 많은 사용자에게 영향 | 저장한 값이 사라짐, 상태 전환 규칙이 무시됨 | 출시 불가 |
| S3 | 보통 | 기능은 되지만 불편하거나 일부 사용자(키보드·스크린 리더 등)에게 장애. 우회 가능 | 더블 클릭 시 중복 생성, 오류 칸으로 포커스가 가지 않음, axe 위반 | 고치거나 사유를 적고 출시 |
| S4 | 경미 | 표시·문구·정렬 등 업무에 지장이 없는 문제 | 오타, 여백 | 출시 가능 |

## 7. 역할과 책임

| 역할 | 담당 | 책임 |
| --- | --- | --- |

## 8. 테스트 케이스 목록

- 자동화 여부: **자동(e2e)** Playwright, **자동(JUnit)** JUnit, **자동(e2e·테스트 IdP)** 테스트 IdP가 필요한 e2e, **점검 묶음** 세션 브라우저 점검 스크립트(저장소에 없음), **수동** 사람이 확인.
