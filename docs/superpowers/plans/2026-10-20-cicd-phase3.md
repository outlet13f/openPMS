# CI/CD 연동 3단계 — 릴리스 검증 보드와 릴리스 기록 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** QA·운영팀이 프로젝트 메뉴 **릴리스**에서 "스테이징에는 있고 운영에는 아직 없는 커밋에 연결된 작업"을 손으로 모으지 않고 한 보드(검증 대기 / 재검증 필요 / 실패 / 통과)로 보고, 작업마다 통과·실패(사유)를 남기며, 실패하면 담당자에게 알림이 가게 한다. 고른 버전과 겹쳐 빠짐·끼어듦을 보이고, 운영 배포가 반영되면 그 배포 하나가 읽기 전용 **릴리스 기록**(들어간 작업 + 마지막 검증 + 경고)이 된다. openPMS는 배포를 막거나 바꾸지 않는다.

**Architecture:** 2단계 `com.openpms.cicd` 위에 얹는다. 보드는 요청 때 읽기만 하는 계산(`CicdReleaseBoard`)으로, 원본 환경 S와 대상 환경 T의 `cicd_environment_commits` 차이(T 첫 배포 이전은 기준 시각으로 뺌)에서 작업을 찾고 검증 이력(`cicd_verifications`, 추가만 함)과 V29에서 더하는 `added_at`으로 칸·재검증을 정한다. 검증·빼기(`CicdVerifications`)는 트랜잭션 하나에서 이력·저널·알림을 쓰고, 릴리스 기록(`CicdReleases`)은 2단계 배포 반영(`CicdDeployments.apply`·`giveUp`)의 **같은 트랜잭션**에서 쓴다(HTTP 없음, 잠금 순서 그대로). 알림 띠는 개발 탭의 환경 상태 판단을 `CicdEnvironmentSignals`로 꺼내 함께 쓴다.

**Tech Stack:** Spring Boot 4 / Java 21(가상 스레드) / jOOQ / Flyway / PostgreSQL 17 / db-scheduler, React 19 / Vite / TypeScript / TanStack Query / Tailwind v4, JUnit 5 + MockMvc, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-20-cicd-phase3-release-design.md`. 앞 단계: `docs/superpowers/specs/2026-10-16-cicd-phase2-design.md`, `docs/superpowers/plans/2026-10-16-cicd-phase2.md`.

## 설계서 보완 (코드 조사 뒤 정함, Task 1 Step 8에서 설계서에도 적음)

1. **`added_at`의 값과 채우는 곳.** 새 행도 백필과 같게 "들여온 배포의 `deployed_at`"이다(요청 시각이 아님 — 기준 시각·`basis_at`·`added_before`가 모두 배포 시각끼리 비교되게). V28 뒤의 쓰는 곳(`CicdDeployments.bringIn` `CicdDeployments.java:366`, `CicdFirstDeploy.write` `CicdFirstDeploy.java:194`, 개발 데이터 `V1012__dev_cicd_builds_deployments.sql:94`, 테스트 `DevTabBuildsIT.into`·`PerfBudgetIT.seedDevTab:149` 등)가 `added_at`을 모르므로, **BEFORE INSERT 트리거**가 비어 있으면 그 행의 `deployment_id` 배포 시각으로 채운다. 새 개발 DB에서는 V1012가 V29 **뒤에** 돌기 때문에 트리거 없이 `not null`만 걸면 `reset-db`가 깨진다. `on conflict … do update set deployment_id`는 INSERT 값만 바꿀 뿐 기존 행의 `added_at`을 건드리지 않는다.
2. **검증 요청에 대상 환경.** 설계서 4.2의 본문 `{ workPackageId, environmentId, result, reason }`로는 "그 보드(S→T)의 목록에 있나"를 판단할 수 없다. 본문에 `targetEnvironmentId`를 더한다(빼기·되돌리기도 같음).
3. **"T의 첫 배포"(기준 시각).** 저장소마다 `environment_id = T`이고 `status = 'success'`인 배포 중 `deployed_at`이 가장 이른 것(`inclusion`은 따지지 않음 — 확인 중·커밋 모름이어도 그때 나간 것은 나간 것).
4. **작업의 "원본 환경에 가장 늦게 들어온 시각"**(`basis_at`, `added_before`, 재검증·다시 나타남 판단)은 그 작업의 커밋(설계서 3절 정의) 중 **원본 환경 S에 지금 든 것 전부**의 `added_at` 최댓값이다(차이 커밋만이 아님). 저장소는 S의 프로젝트에 붙은(떼지 않은) 것만.
5. **경고의 우선순위.** 칸과 같게: 결과 없음 → `unverified`, 재검증 필요 → `stale`(실패였어도), 실패 → `failed`, 통과 → null.
6. **빠짐에서 뺀 작업 제외.** "이미 운영에 있음"으로 뺀 작업(유효한 것)은 빠짐에도 세지 않는다.
7. **버전 고르기.** 고를 수 있는 버전은 그 프로젝트의 버전(`versions.project_id = P`)뿐이다(버전 API `GET /projects/{id}/versions`와 같음). 계획 작업은 `version_id = V`인 모든 프로젝트의 작업 중 보는 사람에게 보이는 것(공유 버전 포함). 기본값: `status = 'open'`인 P의 버전 중 `end_date >= 오늘`(보는 사람의 시간대, `ctx.today()`)인 것의 가장 이른 끝 날짜 → 없으면 지난 것 중 가장 늦은 끝 날짜 → 없으면 끝 날짜 없는 것 중 이름순 첫째 → 없으면 "버전 없음". 쿼리 `version=none`은 "버전 없음".
8. **릴리스 기록의 원본 환경 열.** 기록 화면이 "스테이징 검증"처럼 보이도록 `cicd_releases.source_environment_id`(기록 시점의 기본 원본, 없으면 null)를 둔다.
9. **오류로 5번 실패한 대상 환경 배포**(`CicdDeployments.broken`, 머리를 옮기고 `failed`)도 `giveUp`처럼 "내용 확인 실패" 기록을 남긴다 — 단 그 환경의 첫 배포(머리가 없었음)는 남기지 않는다.
10. **실패 알림.** 받는 사람 = 작업의 담당자와 공동 담당자(`Assignees.ids(assignees.of(wpId))`) 중 활성 사용자이고 **그 작업을 볼 수 있는** 사람, 남긴 본인 제외. 사람마다의 알림 설정 끄기는 없다(멘션·주시처럼 늘 켜짐). 메일은 기존 알림 메일(즉시·요약) 설정을 따른다.
11. **작업 활동 한 줄.** 저널 항목 하나(`changes = {}`, 메모 없음, `cause = {"kind": "verification_passed" | "verification_failed", "environment": "<환경 이름>", "reason": "<실패 사유>"}`). 활동 화면의 기존 `cause` 표시(`activity.tsx:68`)를 넓힌다. 실패 알림은 이 저널을 `journal_id`로 가리킨다. 웹훅은 만들지 않는다(웹훅은 `webhooks.enqueue`를 부를 때만 나가고 `Journals.write`는 부르지 않음).
12. **QA 역할의 권한:** `project.view`(프로젝트를 열려면 필요), `wp.view`, `wp.comment`, `wp.edit_own_comments`, `cicd.view`, `release.verify`. 고정 id는 `backend/scripts/ids.py role-qa` = `55ecb595-b468-52b0-bfbd-52f40d6333a4`.
13. **개발 탭 검증 줄**은 작업에 검증 결과가 있을 때만 보인다(없으면 줄 없음). 프로젝트(환경 줄과 같은 프로젝트)마다 기본 대상·기본 원본으로 고른다.
14. **판 번호 3.0**(README 개정 이력이 1.9 → 2.0처럼 넘어감). 매뉴얼 07은 새 16.8 **릴리스 검증 보드**·16.9 **릴리스 기록**, 10은 새 6.15(V29로 올릴 때)·9.18.14 **릴리스 검증과 QA 역할**. `topics.ts`: `…/releases/records` → 16.9, `…/releases` → 16.8.
15. **가짜 데이터 계층에는 배포 처리가 없다**(2단계도 시드만). 그래서 가짜 계층의 릴리스 기록은 시드로만 있고, 보드·칸·재검증·권한·알림·빼기 규칙은 서버와 같게 계산한다.
