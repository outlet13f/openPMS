단계 사이에 오가는 것

단계이름앞 단계에서 받는 것뒤 단계로 넘겨주는 것
1장애·서비스 요청기존 작업 패키지·워크플로·저널·알림·웹훅서비스 데스크 프로젝트, service_tickets, SLA 시계, 포털, 처리 그룹 → 2~6단계 모두
2서비스 카탈로그1: 포털, SLA 멈춤 상태, 처리 그룹승인 엔진 ticket_approvals, 포털 내 승인함 → 5(CAB 승인)
3문제 관리1: 장애(service_tickets)알려진 오류·임시 해결책 → 6(문서로 만들기). 장애·문제에서 변경 만들기 → 5
4CMDB1: 티켓(CI 연결)CI와 work_package_cis → 5(충돌 막기, CMDB 반영). 업무 서비스 CI → 6(문서 분류), 1(포털 서비스 고르기)
5변경 관리2: 승인 엔진, 4: CI, 1·3: 장애·문제CI 변경 반영 → 4(CMDB 갱신). 실패한 변경의 장애 만들기 제안 → 1
6지식 베이스1: 포털, 3: 알려진 오류, 4: 업무 서비스(선택)포털 자가 해결 → 1(접수 감소), 답변에 문서 넣기 → 1·3
ITIL 전체 프로세스를 6단계로 나누어 단계마다 설계서 → 구현 계획 → 구현을 돈다. CI 기반 충돌 확인을 위해 CMDB(4)를 변경(5)보다 먼저 만든다(2026-10-14 결정).

단계설계서핵심
1장애·서비스 요청 (기반)SLA, 포털, 처리 그룹
2설계: ITSM 2단계 — 서비스 카탈로그와 승인요청 양식, 승인
3설계: ITSM 3단계 — 문제 관리근본 원인, 알려진 오류
4설계: ITSM 4단계 — CMDB (구성 관리)구성 항목, 영향 분석
5설계: ITSM 5단계 — 변경 관리CAB 승인, 실행 계획서
6설계: ITSM 6단계 — 지식 베이스포털 검색, 문서 추천

3공통 틀

  • 장애·요청·문제·변경은 작업 패키지 유형 + 1:1 확장 테이블로 만든다. 목록·필터·보드·저널·알림·웹훅·첨부·워크플로를 그대로 쓴다
  • CMDB의 구성 항목과 지식 베이스 문서는 작업이 아니므로 별도 테이블로 둔다
  • 멤버가 아닌 직원의 진입로(포털, 내 승인함)는 별도 컨트롤러로 두고, 본인 것만 보이며 남의 것은 404
  • 승인 엔진(ticket_approvals)은 2단계에서 만들고 5단계 CAB 승인에서 다시 쓴다
  • 스키마 V20–V25, 개발 데이터 V1004–V1009(순서대로 만든다는 가정의 예정 번호)
