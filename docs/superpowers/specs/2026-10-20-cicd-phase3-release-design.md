## 1 목적과 범위

### 왜

지금은 "스테이징에 무엇이 올라가 있고, 그중 무엇을 검증했고, 이번 운영 배포에 무엇이 들어갔는지"를 openPMS 안에서 확인할 방법이 없다(사용자: "만들어야 해"). 2단계가 환경마다 들어간 커밋(`cicd_environment_commits`)과 배포(`cicd_deployments`)를 이미 알고 있으므로, 그 위에 검증과 릴리스 기록을 올린다.

### 누구를 위한 것인가 (사용자가 정한 순서)

1. **QA·운영팀** — 스테이징 검증을 시작하기 전에 연다. "지금 스테이징에 올라간 것 중 운영에 아직 없는 작업이 정확히 무엇인가"를 보고, 작업마다 통과·실패를 남긴다. **이번 단계의 중심.**
2. PM·개발 리더 — 운영 배포 전 점검(병합 안 된 MR·실패한 빌드·미검증 작업 요약). 이번 단계 밖.
3. 현업·사내 사용자 — 읽기 쉬운 릴리스 노트. 이번 단계 밖.
4. 경영진·고객 — 버전별 일정·진척 요약. 이번 단계 밖.

### 합의한 것 (사용자 결정)

| 항목 | 결정 |
|---|---|
| 검증 범위 | **환경 차이 + 버전 대조**: 실제 범위 = 비교 원본 환경(기본 스테이징)에는 있고 대상 환경(기본 운영)에는 없는 커밋에 연결된 작업. 고른 openPMS 버전(작업의 대상 버전)을 계획으로 겹쳐 **빠짐**(계획에 있는데 원본 환경에 없음)·**끼어듦**(계획에 없는데 올라옴)을 보여 줌 |
| 결과 기록 | 작업마다 **통과·실패**를 openPMS에 남김 |
| 실패 뒤 | 실패 **사유**(필수)를 적고, 작업 **담당자에게 알림**. 작업 상태는 사람이 바꿈(자동 전환 없음) |
| 누가 | 새 권한 **릴리스 검증**(`release.verify`)과 새 역할 **QA**(보기 + 검증). 개발 리더·프로젝트 관리자도 이 권한을 받음. 보기는 `cicd.view`가 있는 멤버 |
| 화면 배치 | **검증 보드**(시안 B): 칸 = 검증 대기 / 재검증 필요 / 실패 / 통과. 위 줄에 빠짐·끼어듦·작업 연결 없는 커밋 요약(펼치면 목록) |
| 재검증 | 통과나 실패를 남긴 뒤 그 작업에 연결된 커밋이 원본 환경에 **새로** 들어오면 자동으로 **재검증 필요** |
| 운영 배포 뒤 | 대상 환경에 들어간 작업은 보드에서 빠지고, 대상 환경 배포 하나가 **읽기 전용 릴리스 기록** 하나가 됨(들어간 작업 + 작업마다 마지막 검증 결과 + 누가 언제). 검증 없이·실패인 채 들어간 작업은 **경고** 표시 |
| 이번 범위 | QA 검증 보드 + 릴리스 기록만. PM 점검·릴리스 노트 내보내기·CI 관문 API는 다음 |
| 운영 기록의 빈틈 | 대상 환경의 커밋 기록은 비어 있을 수 있다(연동 전에 나간 커밋, 첫 배포의 확인 범위 밖, 확인 실패한 배포). **기준 시각 + 손 제외**: 대상 환경 첫 배포 이전에 원본 환경에 들어온 커밋은 보드에서 빼고, 그래도 남는 것은 QA가 카드에서 "이미 운영에 있음"으로 뺀다(뺀 기록이 남음). 확인 실패한 대상 환경 배포는 릴리스 기록에 "내용 확인 실패" 한 줄로 남긴다 |
| 빠짐 기준 | 버전의 **열린** 작업(닫힌 상태 제외) 가운데 보드에 없고 아직 대상 환경에 모두 들어가지 않은 것. **개발 중**(커밋·MR 연결 있음)과 **코드 연결 없음** 두 묶음으로 나눠 보임 |

### 목표

- QA가 스테이징 검증을 시작할 때 테스트할 작업 목록을 손으로 모으지 않는다.
- 검증 결과가 작업·릴리스에 남아, 나중에 "이 운영 배포에 무엇이 검증 없이 나갔나"를 답할 수 있다.
- 다시 고쳐 올라온 작업을 놓치지 않는다(재검증 필요).

### 범위 밖 (이번 단계에서 하지 않음)

- PM·개발 리더용 운영 배포 전 점검 요약, 릴리스 노트(Markdown·PDF) 내보내기, 경영진 요약.
- CI 관문 API(배포 파이프라인이 "실패·미검증 작업이 있나"를 묻는 길)와 상태 자동 전환 — 4단계 자동화로.
- 실패 때 버그 작업 자동 생성, 작업 상태 자동 되돌리기.
- 테스트 케이스·테스트 단계 관리(검증은 작업 단위 통과·실패 + 사유뿐).
- 변경 관리 연결(5단계, 보류 그대로).

### 하면 안 되는 것 (기술적으로 돌아가도 실패)

- **배포를 막거나 바꾸지 않는다.** openPMS는 보고 기록할 뿐이다(관문은 4단계에서 따로 정함).
- 보는 사람이 볼 수 없는 작업·프로젝트가 보드·요약·릴리스 기록의 숫자나 제목으로 드러나면 안 된다(1·2단계와 같은 원칙).
- 검증 결과를 조용히 잃으면 안 된다: 재검증이 필요해져도 이전 결과(누가 언제 무엇을)는 이력으로 남는다.
- 2단계의 환경 상태가 아직 확인 중·일부·확인 실패인데 보드가 "완전한 목록"처럼 보이면 안 된다(아래 4.3의 알림 띠).

## 2 사용 흐름

1. QA가 프로젝트 메뉴 **릴리스**를 연다(모듈 `cicd`가 켜져 있고 `cicd.view`가 있을 때 보임).
2. 위 줄에서 **버전**(선택, 기본은 열린 버전 중 끝 날짜가 가장 가까운 것 — 없으면 "버전 없음")과 **비교 원본 환경 → 대상 환경**을 고른다. 기본 대상은 `production = true`인 환경 중 첫째, 기본 원본은 대상 바로 앞 순서(`position`)의 숨기지 않은 환경. 고른 값은 주소(쿼리 문자열)에 남아 공유할 수 있다.
3. 보드에 카드가 칸별로 놓인다. 카드: `#번호 제목`, 담당자, 작업 상태, 원본 환경에 들어온 배포(시각·배포 링크), 마지막 검증(결과·사람·시각·실패 사유 앞부분), 끼어듦 표시.
4. 카드에서 **통과** 또는 **실패**(사유 입력 대화상자, 필수 1–2,000자)를 누른다. 끌어다 놓기는 쓰지 않는다(접근성·실수 방지; 단추로만).
5. 실패하면 작업의 담당자(공동 담당자 포함)에게 알림이 간다.
6. 같은 작업의 새 커밋이 원본 환경에 들어오면 카드가 **재검증 필요**로 옮겨 간다.
7. 대상 환경 배포가 반영되면 그 배포로 들어간 작업은 보드에서 빠지고, **릴리스 기록** 목록(같은 화면의 둘째 탭 "릴리스 기록")에 한 줄이 생긴다. 기록을 열면 들어간 작업과 각 작업의 마지막 검증, 경고가 보인다.

## 3 데이터 (마이그레이션 V29, 개발 데이터 V1013)

### 검증 결과 `cicd_verifications` (추가만 하는 이력)

| 열 | 뜻 |
|---|---|
| `id` | uuid |
| `work_package_id` | 작업 (작업 삭제 시 함께 삭제) |
| `environment_id` | 검증한 원본 환경 (`cicd_environments`, cascade — 환경은 배포가 없을 때만 지워지고(`CicdEnvironments.remove`), 커밋이 들어간 원본 환경에는 늘 배포가 있으므로 실제로 지워지지 않음) |
| `result` | `passed` · `failed` |
| `reason` | 실패 사유(실패면 필수 1–2,000자, 통과면 빈 문자열) |
| `verified_by` | 사용자 (`on delete set null`) |
| `verified_at` | 시각 |
| `basis_at` | 검증할 때 그 작업의 연결 커밋 가운데 원본 환경에 가장 늦게 들어온 시각(`cicd_environment_commits`의 들어온 시각 최댓값). 재검증 판단 기준 |

- 행을 고치거나 지우지 않는다(이력). "현재 결과" = 작업 × 원본 환경마다 `verified_at`이 가장 늦은 행.
- 색인: `(work_package_id, environment_id, verified_at desc)`.

**재검증 필요**는 저장하지 않고 계산한다: 현재 결과가 있고, 그 작업의 연결 커밋 중 원본 환경에 `basis_at`보다 늦게 들어온 것이 있으면 재검증 필요. (환경 머리가 옮겨 갔다 돌아오는 롤백으로 다시 들어온 커밋도 "새로 들어옴"으로 친다 — 내 판단: 롤백 뒤에는 다시 보는 게 안전하다.)

**들어온 시각**: `cicd_environment_commits`에는 지금 들어온 시각이 없다(V28: `environment_id, repository_id, commit_id, deployment_id`뿐). V29에서 `added_at timestamptz not null`을 더하고, 기존 행은 그 행의 `deployment_id` 배포의 `deployed_at`으로 채운다(두 열 모두 not null이라 빈 값이 없음). 2단계의 upsert(`CicdDeployments.bringIn`, `CicdFirstDeploy`의 `on conflict do update set deployment_id`)는 **`added_at`을 옮기지 않는다** — 빠지지 않고 다시 확인된 커밋은 "새로 들어옴"이 아니다. 롤백으로 지워졌다가 다시 들어온 커밋은 새 행이라 새 `added_at`을 갖는다(→ 재검증 필요).

**작업의 커밋**(이 문서 전체에서 "작업에 연결된 커밋"): 2단계 개발 탭·첫 배포와 같은 정의 — 작업의 커밋 연결(`work_package_cicd_links.commit_id`) + 연결된 **병합된** MR의 병합 커밋(`merge_commit_sha`, `DevTabController.LINKED`·`CicdDeployments.CANDIDATES`). MR 안의 개별 커밋은 작업에 세지 않는다(2단계와 같음).

### 보드에서 뺀 작업 `cicd_board_exclusions`

| 열 | 뜻 |
|---|---|
| `work_package_id` · `environment_id`(원본) · `target_environment_id`(대상) | 어느 보드에서 뺐나 |
| `excluded_by` · `excluded_at` | 누가 언제 (`release.verify` 필요) |
| `added_before` | 뺄 때 그 작업의 커밋 중 원본 환경에 가장 늦게 들어온 시각 |

- "이미 운영에 있음"으로 뺀 작업은 그 보드에서 숨긴다. 그 뒤 그 작업의 새 커밋이 원본 환경에 들어오면(`added_at > added_before`) 다시 보드에 나타난다(검증 대기 또는 재검증 필요).
- 뺀 작업은 요약 줄의 "뺀 작업 n"을 펼쳐 보고 되돌릴 수 있다(행 삭제, 되돌리기도 `release.verify`).

### 릴리스 기록 `cicd_releases` · `cicd_release_items`

`cicd_releases` — 대상 환경(= 그 프로젝트의 `production = true` 환경 전부)에 배포가 **반영되어 커밋이 더해질 때** 하나 생긴다.

| 열 | 뜻 |
|---|---|
| `id` | uuid |
| `project_id` | 환경의 프로젝트 |
| `environment_id` | 대상 환경 |
| `deployment_id` | 그 배포 (`cicd_deployments`) — 유일 |
| `repository_id` | 배포의 저장소 |
| `deployed_at` | 배포 시각 |
| `created_at` | 기록 시각 |
| `partial` | 비교가 한쪽 1,000개 상한에 걸려 들어간 작업이 덜 찼을 수 있음 |

`cicd_release_items` — 그 배포로 대상 환경에 **새로 들어간** 커밋(`cicd_deployment_commits`의 더해진 쪽)에 연결된 작업마다 한 행. 기록할 때의 스냅숏이며 뒤에 바뀌지 않는다.

| 열 | 뜻 |
|---|---|
| `release_id` | 릴리스 |
| `work_package_id` | 작업 (`on delete set null`, 제목은 아래 스냅숏) |
| `subject` · `number` | 기록 시점의 작업 제목·번호 |
| `verification_id` | 기록 시점에 원본 환경의 현재 검증 결과 (없으면 null) |
| `warning` | `unverified`(결과 없음) · `failed`(현재 결과가 실패) · `stale`(재검증 필요 상태) · null |

- 원본 환경은 기록 시점의 기본 원본(대상 바로 앞 순서의 숨기지 않은 환경)으로 정한다. 그런 환경이 없으면 `warning`은 `unverified`(검증할 곳이 없음).
- 롤백 배포(커밋이 빠지기만 함)는 릴리스 기록을 만들지 않는다(내 판단: 들어간 것이 없으므로). 빠진 것은 2단계 배포 이력에 이미 있다.
- 첫 배포(이전 배포 없음, `first`)는 **기록 안 함** — 무엇이 "이번에" 들어갔는지 알 수 없다(내 판단).
- 확인 실패한 대상 환경 배포(2단계 `giveUp`으로 `failed`, 머리는 옮겨지지만 커밋은 쓰이지 않음)는 `cicd_releases`에 `content_failed = true`인 행 하나(작업 행 없음)를 남기고, 기록 목록에 "내용 확인 실패 — 이 배포에 들어간 작업을 알 수 없음"으로 보인다(사용자 결정). 그래서 `cicd_releases`에 `content_failed boolean not null default false` 열을 둔다.

### 권한과 역할

- 새 권한 `release.verify`(프로젝트 범위, 모듈 `cicd`에 묶음 — 2단계 `Ctx.MODULE_OF`처럼).
- 이미 설치된 곳: `cicd.manage`를 가진 역할(개발 리더·프로젝트 관리자 계열)에 `release.verify`를 더한다(V26의 "권한으로 더하기" 방식).
- 새 역할 **QA**(프로젝트 범위, builtin 아님, 고정 uuid): `wp.view`, `cicd.view`, `release.verify` + 작업에 댓글을 달 수 있는 권한(기존 권한 이름은 건축가가 확인). 같은 이름이 이미 있으면 V26처럼 기존 행에 ` (기존)`을 붙인다.

### 알림

- `notifications.reason` check에 `verification_failed`를 더한다. 받는 사람: 작업의 담당자와 공동 담당자(실패를 남긴 본인은 뺌). 메일은 기존 알림 메일 설정을 따른다.
- 활동 기록: 검증을 남기면 작업 활동에 "스테이징 검증: 통과/실패(사유)" 한 줄이 보이게 한다(내 판단). 저널 구조에 맞는 방법은 건축가가 정한다(저널 항목 또는 활동 목록에 검증 이력을 합쳐 보여 주기). 웹훅 이벤트는 만들지 않는다.

### 개발 데이터 V1013

- web-platform: 스테이징에 있고 운영에 없는 작업 4–6개(통과 2·실패 1·재검증 필요 1·대기 나머지), 버전 대조용으로 빠짐 1·끼어듦 1, 작업 연결 없는 커밋 1, 릴리스 기록 2개(하나는 경고 포함). QA 역할의 개발 사용자 하나.

### 보완 (구현 계획에서 정함)

- **`added_at`의 값과 채우는 곳.** 새 행도 백필과 같게 "들여온 배포의 `deployed_at`"이다(요청 시각이 아님 — 기준 시각·`basis_at`·`added_before`가 모두 배포 시각끼리 비교되게). 2단계의 쓰는 곳(`CicdDeployments.bringIn`, `CicdFirstDeploy.write`, 개발 데이터 V1012, 기존 테스트)은 이 열을 모르므로 **BEFORE INSERT 트리거**가 비어 있으면 그 행의 `deployment_id` 배포 시각으로 채운다. 새 개발 DB에서는 V1012가 V29 **뒤에** 돌기 때문에 트리거 없이 `not null`만 걸면 `reset-db`가 깨진다. `on conflict … do update set deployment_id`는 기존 행의 `added_at`을 건드리지 않는다. (보완 1)
- **작업의 "원본 환경에 가장 늦게 들어온 시각"**(`basis_at`, `added_before`, 재검증·다시 나타남 판단)은 그 작업의 커밋(위 "작업의 커밋" 정의) 중 **원본 환경 S에 지금 든 것 전부**의 `added_at` 최댓값이다(차이 커밋만이 아님). 저장소는 S의 프로젝트에 붙은(떼지 않은) 것만. (보완 4)
- **릴리스 기록의 원본 환경 열.** 기록 화면이 "스테이징 검증"처럼 보이도록 `cicd_releases.source_environment_id`(기록 시점의 기본 원본, 없으면 null)를 둔다. (보완 8)
- **QA 역할의 권한:** `project.view`(프로젝트를 열려면 필요), `wp.view`, `wp.comment`, `wp.edit_own_comments`, `cicd.view`, `release.verify`. 고정 id는 `backend/scripts/ids.py role-qa` = `55ecb595-b468-52b0-bfbd-52f40d6333a4`. (보완 12)

## 4 처리와 규칙

### 4.1 보드 목록 계산 (요청 때, 읽기만)

1. 프로젝트 P의 환경 중 원본 S와 대상 T(둘 다 P의 환경, 숨긴 환경도 고를 수는 있되 기본값으로는 고르지 않음).
2. 저장소: P에 붙은(떼지 않은, `detached_at is null`) 저장소. S·T는 P의 환경이므로 저장소의 **현재** 프로젝트가 P인 것만(2단계 규칙).
3. 차이 커밋 = 저장소마다 `S에 들어간 커밋 − T에 들어간 커밋`(`cicd_environment_commits`). 단 **기준 시각**: 저장소마다 T의 첫 배포(그 저장소·T의 `deployed_at`이 가장 이른 배포) 시각보다 **앞서** S에 들어온 커밋(`added_at`)은 뺀다(이미 나갔다고 봄 — 사용자 결정). T에 그 저장소의 배포가 하나도 없으면 기준 시각 없이 모두 센다.
4. 작업 = 차이 커밋에 연결된(위 "작업의 커밋" 정의, `dismissed_at is null`) 작업 가운데 **보는 사람이 볼 수 있는 것만**. 연결은 P와 그 하위 프로젝트 작업에 걸릴 수 있으므로(1단계 `projectTree`) 작업마다 그 작업 프로젝트의 작업 보기 권한을 거른다. "이미 운영에 있음"으로 뺀 작업(`cicd_board_exclusions`, 새 커밋이 없을 때)은 뺀다.
5. 작업 연결 없는 커밋 = 차이 커밋 중 보는 사람에게 보이는 연결이 하나도 없는 것. 숫자와 목록 모두 이 기준(보이지 않는 작업에 연결된 커밋은 "연결 없음"으로도 세지 않는다 — 다른 프로젝트 작업의 존재가 드러나지 않게. 내 판단: 이 둘을 구별하지 않고 그냥 뺀다). 병합 커밋 방식으로 합친 MR의 개별 커밋은 작업에 세지 않으므로 여기에 나타날 수 있다 — 화면 도움말에 "MR 안의 커밋은 MR의 병합 커밋으로 작업에 이어짐"을 적는다(내 판단).
6. 버전 대조(버전 V를 골랐을 때): 계획 = `version_id = V`이고 **열린 상태**(닫힌 상태가 아닌)인 보이는 작업. **빠짐** = 계획에 있는데 4의 목록에 없고, 그 작업의 커밋이 아직 T에 모두 들어가지는 않은 작업(커밋이 하나도 없는 작업 포함). 빠짐은 두 묶음으로 보인다: **개발 중**(커밋·MR 연결이 하나라도 있음)과 **코드 연결 없음**(사용자 결정). **끼어듦** = 4의 목록에 있는데 `version_id`가 V가 아닌 작업. 공유 버전(`sharing`)으로 다른 프로젝트 작업이 V를 가질 수 있으나, 보이는 작업만 센다.
7. 칸: 현재 결과 없음 → 검증 대기 / 재검증 필요 → 재검증 필요 / 현재 결과 실패 → 실패 / 통과 → 통과.

#### 보완 (구현 계획에서 정함)

- **"T의 첫 배포"(기준 시각).** 저장소마다 `environment_id = T`이고 `status = 'success'`인 배포 중 `deployed_at`이 가장 이른 것(`inclusion`은 따지지 않음 — 확인 중·커밋 모름이어도 그때 나간 것은 나간 것). (보완 3)
- **경고의 우선순위.** 칸과 같게: 결과 없음 → `unverified`, 재검증 필요 → `stale`(실패였어도), 실패 → `failed`, 통과 → null. (보완 5)
- **빠짐에서 뺀 작업 제외.** "이미 운영에 있음"으로 뺀 작업(유효한 것)은 빠짐에도 세지 않는다. (보완 6)
- **버전 고르기.** 고를 수 있는 버전은 그 프로젝트의 버전(`versions.project_id = P`)뿐이다(버전 API `GET /projects/{id}/versions`와 같음). 계획 작업은 `version_id = V`인 모든 프로젝트의 작업 중 보는 사람에게 보이는 것(공유 버전 포함). 기본값: `status = 'open'`인 P의 버전 중 `end_date >= 오늘`(보는 사람의 시간대)인 것의 가장 이른 끝 날짜 → 없으면 지난 것 중 가장 늦은 끝 날짜 → 없으면 끝 날짜 없는 것 중 이름순 첫째 → 없으면 "버전 없음". 쿼리 `version=none`은 "버전 없음". (보완 7)

### 4.2 검증 남기기

- `POST /api/v1/projects/{project}/releases/verifications` 본문 `{ workPackageId, environmentId, result, reason }`.
- 권한: 보드 프로젝트 P의 `release.verify`(하위 프로젝트 작업이라도 P의 권한으로 검증 — 보드가 P의 것이므로, 내 판단). 작업은 그 작업 프로젝트에서 볼 수 있어야 하고 아니면 404. 보드 보기는 P의 `cicd.view`(카드는 작업 보기 권한으로 거름, 4.1-4).
- 작업이 지금 그 보드의 4 목록에 있어야 한다(아니면 422 — 이미 운영에 들어갔거나 연결이 빠짐).
- "이미 운영에 있음"으로 빼기·되돌리기(`…/releases/exclusions`)도 같은 권한 규칙.
- `basis_at`은 서버가 계산한다. 같은 사람이 같은 결과를 두 번 눌러도 이력 한 줄이 더 생길 뿐 해가 없다(멱등 키는 기존 `Idempotency-Key` 규칙을 따름).
- 실패면 알림을 같은 트랜잭션에서 만든다(HTTP 없음).

#### 보완 (구현 계획에서 정함)

- **검증 요청에 대상 환경.** 위 본문 `{ workPackageId, environmentId, result, reason }`로는 "그 보드(S→T)의 목록에 있나"를 판단할 수 없다. 본문에 `targetEnvironmentId`를 더한다(빼기·되돌리기도 같음). (보완 2)
- **실패 알림.** 받는 사람 = 작업의 담당자와 공동 담당자 중 활성 사용자이고 **그 작업을 볼 수 있는** 사람, 남긴 본인 제외. 사람마다의 알림 설정 끄기는 없다(멘션·주시처럼 늘 켜짐). 메일은 기존 알림 메일(즉시·요약) 설정을 따른다. (보완 10)
- **작업 활동 한 줄.** 저널 항목 하나(`changes = {}`, 메모 없음, `cause = {"kind": "verification_passed" | "verification_failed", "environment": "<환경 이름>", "reason": "<실패 사유>"}`). 활동 화면의 기존 `cause` 표시를 넓힌다. 실패 알림은 이 저널을 `journal_id`로 가리킨다. 웹훅은 만들지 않는다(웹훅은 `webhooks.enqueue`를 부를 때만 나가고 저널 쓰기는 부르지 않음). (보완 11)

### 4.3 알림 띠 (목록이 덜 찼을 수 있을 때)

S 또는 T에 대해 2단계 개발 탭 환경 줄과 **같은 판단**(`DevTabController` 환경 상태 계산)을 쓴다: 확인 중인 배포(`checking`)가 있음, 머리인 배포가 확인 실패(`failed`), 첫 배포가 200개 상한에 걸림(`first_cutoff_at`이 있음), 들어간 커밋 일부가 `partial` 배포에서 옴. 하나라도 해당하면 보드 위에 "스테이징 배포를 아직 확인하는 중이라 목록이 바뀔 수 있습니다" 같은 띠를 보인다(상태별 문구는 건축가가 정함). 같은 판단 코드를 두 곳에 베끼지 말고 함께 쓰게 꺼낸다.

### 4.4 릴리스 기록 만들기

- 2단계 배포 반영(`CicdDeployments`)이 대상 환경(`production = true`)의 머리를 옮기고 더해진 커밋을 `cicd_environment_commits`에 쓰는 **같은 트랜잭션**에서 `cicd_releases`·`cicd_release_items`를 쓴다(HTTP 없음 — 비교는 이미 트랜잭션 밖에서 끝남). 2단계 잠금 순서(머리 행 `for update` 하나)를 바꾸지 않는다.
- 같은 배포로 두 번 쓰지 않는다(`deployment_id` 유일).
- 대상 환경이 여러 개(`production = true`가 둘 이상)면 각각 기록한다.

#### 보완 (구현 계획에서 정함)

- **오류로 5번 실패한 대상 환경 배포**(`CicdDeployments.broken`, 머리를 옮기고 `failed`)도 `giveUp`처럼 "내용 확인 실패" 기록을 남긴다 — 단 그 환경의 첫 배포(머리가 없었음)는 남기지 않는다. (보완 9)

### 4.5 성능

- 보드 한 번에 SQL 개수·응답 크기 예산을 `PerfBudgetIT`에 더한다(개발 탭과 같은 방식, 기준값은 건축가가 재고 정함). 차이 커밋은 저장소마다 한쪽 1,000개 상한(2단계)을 넘지 않으므로 작업 수도 그 안이다.
- 릴리스 기록 목록은 쪽 나눔(기존 목록 API의 쪽 규칙).

- 모든 목록·숫자·기록은 보는 사람의 작업 보기 권한으로 거른다(4.1-4·5, 릴리스 기록의 "볼 수 없는 작업 n개").
- 검증 API는 `release.verify` + 모듈 `cicd` 켜짐 + 작업 보기 권한.
- `/projects/{p}/releases` 아래 경로는 읽기·쓰기 모두 API 토큰에 닫는다(`ApiTokenFilter.CLOSED_PROJECT`에 더함 — 2단계 환경·정리 경로와 같은 취급, 그 목록은 GET도 닫음. 내 판단).
- 실패 사유는 사용자 입력이므로 기존 텍스트 필드처럼 다룬다(길이 상한, 표시 때 이스케이프). 로그에 사유를 남기지 않는다.

## 7 테스트

- JUnit: 차이 계산(여러 저장소, 떼어 낸 저장소, 다른 프로젝트로 옮긴 저장소, 하위 프로젝트 작업, 보이지 않는 작업), 칸 계산과 재검증(새 커밋·롤백 뒤 다시 들어온 커밋), 버전 대조(빠짐·끼어듦·공유 버전), 검증 API 권한(QA·개발 리더·멤버·비멤버·모듈 꺼짐·API 토큰), 실패 알림 받는 사람, 릴리스 기록 생성(일반·롤백·첫 배포·partial·대상 환경 둘), 기록 스냅숏 불변, 알림 띠 판단, `PerfBudgetIT` 보드 예산, `NoPinningTest` 유지.
- JUnit 더: 기준 시각(T 첫 배포 이전 커밋 빠짐, T 배포 없음), 손 제외와 새 커밋 뒤 다시 나타남·되돌리기, `added_at`이 upsert로 안 옮겨짐·롤백 뒤 다시 들어오면 새 시각, 확인 실패한 T 배포의 "내용 확인 실패" 기록, MR 병합 커밋으로만 이어진 작업, 빠짐 두 묶음(닫힌 작업 제외).
- e2e F24는 F23과 **다른 저장소(또는 프로젝트)**를 쓴다: F23-2 뒤 web-platform 운영이 15분 남짓 `checking`이고, 2단계 대기열이 같은 저장소·환경의 뒤 배포를 그 뒤에 세우기 때문(`CicdDeployments` QUEUE).
- e2e F24: 가짜 Git 서버(GitLab 모드)로 스테이징·운영 배포를 만들고 → 보드에 카드 → 통과·실패(사유) → 새 커밋 스테이징 배포 → 재검증 필요 → 운영 배포 → 보드에서 빠지고 릴리스 기록에 경고와 함께 보임. 접근성: 보드·대화상자·기록 화면(밝게·어둡게).

## 8 건축가에게 맡기는 것

- 표·열·색인 이름의 세부, 저널과 검증 이력을 합치는 방법, 알림 띠 문구, API 경로의 세부(위 경로는 예시), 보드 응답 모양, 예산 값.
- 버전 기본값 고르기의 세부(열린 버전이 여럿일 때).

### 보완 (구현 계획에서 정함)

- **가짜 데이터 계층에는 배포 처리가 없다**(2단계도 시드만). 그래서 가짜 계층의 릴리스 기록은 시드로만 있고, 보드·칸·재검증·권한·알림·빼기 규칙은 서버와 같게 계산한다. (보완 15)

## 9 내가 정한 것 (사용자 확인 필요 표시)

- 롤백·첫 배포는 릴리스 기록을 만들지 않음.
- 롤백으로 다시 들어온 커밋도 재검증 필요로 침.
- 보이지 않는 작업에 연결된 커밋은 "연결 없음"으로도 세지 않음.
- 개발 탭에 검증 결과 한 줄과 보드 링크.
- 작업 활동에 검증 한 줄.
- 카드 이동은 끌어다 놓기 없이 단추로만.
- 릴리스 경로는 읽기·쓰기 모두 API 토큰에 닫힘.
- 작업의 커밋 = 2단계 정의(커밋 연결 + 병합된 MR의 병합 커밋), MR 안의 개별 커밋은 세지 않음.
- 하위 프로젝트 작업도 보드 프로젝트의 `release.verify`로 검증.
- 기준 시각은 저장소마다 대상 환경의 가장 이른 배포 시각.
